### 11.1 去哪儿查（按问题类型）

| 想知道什么 | 查哪个文件（相对 `zh_CN/gamedata/excel/`） |
|---|---|
| 干员有哪些基建技能、技能原文、数值、房间类型、解锁阶段 | `building_data.json` → `buffs`（755 条定义）+ `chars[].buffChar[].buffData[]`（`buffId` + `cond{phase,level}`） |
| 干员 id ↔ 中文名 | `character_table.json`（`charId` → `name`） |
| 术语含义、阵营/标签成员名单、设施集合、抽象变量、全局机制 | `gamedata_const.json` → `termDescriptionDict`（`cc.c.skill`、`cc.c.sui2_1`、`cc.c.room1~3`、`cc.g.*`、`cc.tag.*`、`cc.bd*`、`cc.bd.costdrop`…） |
| 中枢减免 / 宿舍基础回复 / 制造贸易人数修正 | `building_data.json` 顶层：`controlData.basicCostBuff`、`dormData.phases[].manpowerRecover`、`dormData.phases[].decorationLimit`、`manufactStationBuff`、`manufactManpowerCostByNum`、`tradingManpowerCostByNum` |
| 战斗技能 / 模组数值 | `skill_table.json` / `uniequip_table.json`（⚠️ 与**基建心情无关**，别混；模组只有剧情文案会提「心情」） |

### 11.2 怎么拉（**不要整仓 clone**，几百 MB）

```powershell
# 1) 无 blob 稀疏克隆：只取目录树，秒级完成
git clone --filter=blob:none --depth 1 --no-checkout https://github.com/Kengxxiao/ArknightsGameData <目标目录>
# 2) 只检出 excel 表（按需惰性下载）
git -C <目标目录> sparse-checkout init --cone
git -C <目标目录> sparse-checkout set zh_CN/gamedata/excel
git -C <目标目录> checkout
# 3) 记录版本（结论要可追溯）
git -C <目标目录> rev-parse HEAD
```

上游只保留 `zh_CN` 一个服（无 en/ja/ko）；`zh_CN/gamedata/excel/` 下 59 个 `.json`。
建议把克隆目录放在**本仓库之外**（如 `%TEMP%` 或项目同级），不要提交进本仓库。

### 11.3 必须知道的四个坑

1. **这是纯数据 dump，没有公式实现**。`zh_CN/gamedata/[uc]lua/` 只有 `hotfixes/*.lua` 片段，
   拿不到完整客户端逻辑。所以「心情消耗/回复/工休怎么算」仍以
   `resources/心情消耗回复和工休时间.docx` 为准；上游只提供
   **技能文本 / 数值 / 解锁 / 名册 / 集合 / 术语**。
2. **buffId 的中括号**：上游是 `control_mp_cost[008]`，本项目 CSV 是 `control_mp_cost_008`
   （`[` → `_`、`]` → 删）。已核对：**209/209 一一对应，无歧义**。
3. **β 替换 α 上游不标**：上游把 α、β 当作两个独立 buff，**没有 `replaces` 字段**。
   本项目 `operators.txt` 的 `enhanced` 列是自行推断的结果，别指望从上游直接读到。
4. **描述带富文本标记**：`<@cc.kw>12</>`（关键字）、`<$cc.c.room1>部分设施</>`（术语引用）、
   `<@cc.vup>+0.1</>`（增益）。清洗正则：
   `re.sub(r'</?(?:@cc\.\w+|\$cc\.\w+)>', '', s)`。

### 11.4 查完之后必须做的三件事

1. 修正 `data/moods_skills.txt` / `operators.txt`（或对应的上游派生物）
   → 重跑 `scripts/classify_skills.py --agd <目标目录>`（新 buff 会落进覆盖台账）
   → 重跑 `scripts/generate_skills_data.py`
   → 跑技能全量核对 `.venv/Scripts/python.exe scripts/verify_skills.py --check`
     （逐条 clause 造场景核对 + 台账双向核对 + **上游描述数字对照**；找不到上游就跳过 L3，
     可用 `--agd <目标目录>` 或环境变量 `ARKNIGHTS_GAMEDATA` 指定）
   → 跑全量 unittest（`.venv/Scripts/python.exe -m unittest discover -s tests`）。
2. 若该数据**推翻了既有假设**，同步更新 `03-特殊机制.md`（建模假设）或
   `documents/04-技能分类大纲.md` §5「决策记录」，避免下次又被当成 bug 或又被猜一遍。
3. 结论要**可追溯**：注明取自哪个文件 + 字段名（+ 必要时 commit hash），而不是只写一个数值。

### 11.5 需要「干员英文名 / 干员 id」时：`data/operator_names.py`（**生成物**，由 `scripts/generate_operator_names.py` 产出）

别的工具（ArknightsInfraCalc-v3 的 `plan_compute` 家族）在 JSON 里可能写**英文名或干员 id**
（`{"operbox": [{"id": "op_001", "name": "Amiya", ...}]}`），而本项目技能库**一律按中文名索引**。
好消息：上游 `character_table.json` 每个干员都同时有 `name`（中文名）与 `appellation`（英文名），
所以这层映射也能**从上游生成**、不必手抄：

```bash

# → data/operator_names.py（列：alias,chinese,source；只保留"目标中文名在本项目技能库里"的条目）
```

- 生成物约 848 条别名（`appellation` 与 `char_*` id 两类来源；整个 `operator_names.py` 是**上百行**，
  两个数字口径不同，别当成矛盾）；
- 运行时查表在 **`store/sources.py` 的 `resolve_name()`**（`mood_soc/importer.py` 只是转发壳）：
  先看是不是本来就是中文名，不是再查别名表；都查不到就**原样保留**并写进导入报告的清单
  （按无技能干员参与计算）；
- ⚠️ 与 `factions.txt` 同一套做法：**派生物、勿手改**，上游更新后重跑上面这条命令即可。

### 2. building_data.json 的 schema（只列心情相关）

```jsonc
{
  "controlData": { "basicCostBuff": -5 },       // 中枢：每名进驻干员全基建心情消耗 -5%（即 -0.05）
  "dormData":    { "phases": [ { "manpowerRecover": 160, "decorationLimit": 1000 }, …, 200/5000 ] },
  "manufactStationBuff": 0.1,                   // 制造站每多 1 人的基础效率（非心情）
  "comfortManpowerRecoverFactor": 25,           // 宿舍氛围→回复系数（=0.0004 的来源之一）
  "manufactManpowerCostByNum": [0, 0, -5, -10], // 制造站按人数的心情消耗修正
  "buffs": {                                    // 755 条 buff 定义；description 是唯一文本来源
    "control_mp_lonely[000]": { "buffId": …, "buffName": "公事公办",
      "buffCategory": "FUNCTION",               // FUNCTION(421) / RECOVERY(86) / OUTPUT(248)
      "roomType": "CONTROL",                    // CONTROL/POWER/MANUFACTURE/TRADING/WORKSHOP/TRAINING/DORMITORY/HIRE/MEETING
      "description": "进驻控制中枢时，<$cc.c.room1>部分设施</>…", "targets": [], "sortId": … }, …
  },
  "chars": {                                    // 429 名干员 ↔ buff
    "char_4064_mlynar": { "charId": …, "buffChar": [   // 一个元素 = 一个基建技能槽
      { "buffData": [ { "buffId": "control_mp_cost[008]",
                        "cond": { "phase": "PHASE_0", "level": 1 } } ] } ] }, …
  }
}
```

要点（详细口径见 §11.3 坑 2~4）：

- **`cond.phase`**：`PHASE_0/1/2` = 精英 0/1/2；**`cond.level`** = 该技能可用所需的最低等级
  （多为 1，三星满级技能为 30）。它同时是「解锁」和「提升」的门槛，仓库**不区分**二者。
- **β 替换 α 要自己推断**：仓库把 α、β 当成两个独立 buff（如火神 `manu_prod_spd&limit&cost[000]` PHASE_0 /
  `[001]` PHASE_2），**没有 `replaces` 字段**——`operators.txt` 的 `enhanced` 列就是这一步推断的结果。
- **buffId 里的 `[ ]`**：仓库是 `control_mp_cost[008]`，本项目 CSV 是 `control_mp_cost_008`（`[`→`_`、`]`→删）。
- **描述里的富文本标记**：`<@cc.kw>12</>`、`<$cc.c.room1>部分设施</>`、`<@cc.vup>+0.1</>`；清洗正则见坑 4。
