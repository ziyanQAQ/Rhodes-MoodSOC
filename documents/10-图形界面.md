## 1. 是什么 / 怎么启动
把本工具从"命令行算一次"变成"**看整周期**"：导入 MAA 排班 → 看板逐位置显示干员与实时心情 →
拖时间滑块看一天里心情怎么走 → 指定干员看整周期曲线。

```bash
.venv/Scripts/python.exe -m ui          # 推荐（在仓库根目录执行）
```

**四种跑法都支持**（都等价，任选）：

| 跑法 | 说明 |
|---|---|
| `python -m ui` | 推荐；把 `ui` 当包加载（在**仓库根目录**执行） |
| `python ui/__main__.py` | **直接运行入口文件**（IDE 里右键 Run 通常就是这种） |
| `python ui/app.py` | 直接运行主窗口模块 |
| IDE 配置任意工作目录 | `ui/__main__.py` 与 `ui/app.py` 都会先把仓库根塞进 `sys.path`，故不依赖 cwd |

> ⚠️ 为什么直接运行 `ui/__main__.py` 曾经报
> `ImportError: attempted relative import with no known parent package`：
> 用文件路径直接跑时，Python **不把 `ui/` 当包**（`__package__` 为空），
> `from .app import main` 这类**相对导入**必然失败——只有 `python -m ui` 才知道包边界。
> 现在的做法是：入口先 `sys.path` 引导（加仓库根），再改用**绝对导入** `from ui.app import main`，
> 于是"当包跑"和"当脚本跑"都成立。

技术底座是 **tkinter（Python 标准库）**，因此"纯标准库、无第三方依赖"这条约束不变
（本项目不引入 PyQt/matplotlib；曲线是 Canvas 手绘的）。

启动后会自动载入示例排班 `resources/arknights-infra-schedule-maa.json`（存在时），
点「导入排班…」即可换成自己的文件。

## 2. 功能怎么用（**设置只有一颗按钮**，外加一个周期数下拉）

工具栏分 **3 组**（组间一条细分隔线）：

```
[导入排班…] [设置…] 周期数[1▾]  │  已开启 · 按班次 · 未开启  │  [▶播放] 速度[1x]＝实时 [回到起点]
 └────── 设置类 ──────────┘     └── 状态摘要（点它也能开设置）──┘   └────── 播放控制 ──────┘
```

> **周期数为什么两处都留**：它调得频（"连跑 2~3 个周期看看能不能永动"），每改一次都要开
> 设置窗口太绕；但**状态只有一份**——工具栏那个下拉与「设置…」→ 时间轴的**共用
> `app.cycles_var` 这一个变量**，哪边改另一边立刻跟着变，不存在两处不一致。
> 其余设置项仍然只有「设置…」一个入口。

| 需求 | 操作 |
|---|---|
| **① 导入排班（4 种 JSON 自动识别）** | 「导入排班…」可多选文件；每个文件**自动判格式**（判据见 §2.1），不用先告诉它是什么。一个文件里含多个班次（MAA 的多个 `plan`、v3 输出的多班 `shifts`）会全部导入；**一个班次一个文件**（12h/6h/6h）同样支持。导入后状态栏给一句摘要（识别成什么格式、读到什么、忽略了什么、哪些是推断的） |
| **② 周期 / 班数 / 每班时长 / 周期数 / 初始时间点** | 「设置…」→ **时间轴**：改周期时长与各班长（**各班长之和必须等于周期**，实时校验，不合法就不落地）+ **周期数 1~7**（上限＝`store.session.MAX_CYCLES`，越界**夹到边界**并把夹过的值回写下拉；成本≈线性：实测重算 1 周期 0.32s → 3 周期 1.16s → **7 周期 2.84s**）。**改完立即生效**，没有"应用"。周期数在**工具栏上也有一个下拉**（同一个变量，见上）。**初始时间点**＝周期起点是几点（如 `01:00` ⇒ 1 点到第二天 1 点为一个周期）：**纯显示口径**，滑块/看板/曲线/逐次表上的时刻全按它渲染，**引擎数值一字不变** |
| **② 逐位置设干员与心情** | 看板：**左键**位置 → 选人 / 更换 / 清空该位置；**右键**位置 → 设置该干员心情。也可在右侧面板「设置心情…」给当前曲线干员设心情 |
| **②a 改房间等级（容量随之变）** | 点看板**房间卡头**（`制造站#1 Lv3`）→ 选 Lv1~Lv5，每个选项后面写明「可放 N 人」（上游 `rooms[].phases[lv].maxStationedNum`）；人数超过容量时卡头右侧 `人数/容量` 变**红**、状态栏给出原因。设置中心 → **干员与心情** 里也有「房间等级」区（逐间改 Lv，并显示「制造/贸易/发电已用 N/9 个建造位」） |
| **②b 进驻事件（换心情）** | 「设置…」→ **换心情**：**① 总开关 + ② 一张"每班一行"的表**（`班次 \| 用 \| 换谁 \| 强制切换`，下方「全选 / 全不选」）——一行说尽这一班的行为，没有"全局值 + 例外"两层。第 1 个勾着「用」的班次充当默认口径，其余班次只有不同才记一笔覆盖。固定口径：「对方心情是多少」照换、「位置不动」（只换心情）。**改动立即生效**，工具栏那行状态摘要与状态栏会同步复述当前配置。场景 JSON 顶层的 `entry_events`（含 `per_shift`）会在导入时自动逐行同步到这张表 |
| **②c 闲置入宿** | 「设置…」→ **闲置入宿**：把**没在上班、也不在宿舍、心情还没满**的干员安排进宿舍恢复。**候选顺序＝表内行序**（与引擎同一口径）：**先"不在工作也不在宿舍"的人**（本班未排班 /「不在基建」名单），**再挂件位（加工站/训练室）入驻者**，每组内部按**心情从低到高**——候选是**依次**处理的，所以"表里排前面的"就是"引擎先安排的那位"。**四级优先级**：**① 任一间宿舍还有未占满的位次 → 直接住进去（有空位就不换人）**；② 宿舍全满 → 换「宿舍 **#4→#3→#2** 的**第 2~5 位**」里实时满心情的那位；③ 还找不到 → 只在**白板**（不属于任何已记录阵营的干员）里挑实时满心情的那位，**满 24 的菲亚梅塔也在此列**（她「患难之交」只要满 24、不靠待在宿舍）；④ ②③ 都挑不到 → **你点名了就与那位互换**（**主动换**：不限心情、不受「只换白板 / 自回型不换出 / 不换挂件」限制）；没点名则与宿舍里**心情最高的白板**互换（**不限 24**，最高 21 就跟 21 那位换）；连白板都没有才不动。**同优先级内「优先 4 最后 1」**：宿舍 `#4→#3→#2→#1`（不足 4 间自动前移），同宿舍内 第 2 位→第 5 位→第 1 位。**三道门（只约束自动挑人）**：有阵营的人不动、"宿舍里能自回"的人（缪尔赛思这类）不换出、**挂件**（用户口径"有阵营效果，或者她在不在宿舍会影响其他干员的技能"）也不换出**；**外加一道心情闸（含点名）**：**目标的实时心情必须严格大于这位闲置者**，否则这一班不动（②③ 目标是满 24 ⇒ 天然满足，实际只在④生效）。被换出的那位**既不工作也不在宿舍**（心情平线）；进来的人**接替他那个位次**。一个总开关 + **一张按时间排的逐次表**（第 1 周期第 1 班 → … → 第 N 周期最后一班；每组组头写时刻、自带全选/全不选；表的主要职责是设**第④级兜底**：「换谁」= 点名与谁互换（候选是那一刻宿舍里的**所有人**，标签带心情如 `巫恋 23.4`）、「去哪」= 空位（宿舍01…＝放进那间宿舍的空位））。**改动立即生效**（防抖 250ms：表与主界面一起刷新）。默认**开启**（文件里没写这个键就结算，**显式写 `false` 或取消勾选才关**）；曲线用绿色「宿」标记标出每次入宿。**先换心情、再判闲置入宿**（判定用换完之后的实时心情）—— 见 `04-特殊机制.md` 第 30 条 |
| **②d 干员与心情（原「批量设置」）** | 「设置…」→ **干员与心情**（含**房间等级**区）：当前布局的**所有干员 + 练度 + 心情**摊成一张可滚动表（房间 · 位次 · 干员 · **练度** · **该时刻的心情**），顶部四个动作区——**时刻**（周期 1~周期数 + `HH:MM` + `◀/▶` 15 分钟 + **「跟随滑块」** + 「清空本时刻」）、心情（全部 24 / 全部 0 / 统一设为 X / **按这一刻回填** / **恢复导入值**）、干员（**批量粘贴名单** / **从池中依次填入** / 清空本班次 / 显示空位）与练度（**全部设为 E2**）。**「跟随滑块」**勾上后**一直跟着主界面滑块**（勾选状态存在 `app.follow_slider` 上，切页/重建都不丢），此时周期/时刻/`◀▶`/班次下拉**只读**（跟随时每帧都会重写时刻框，允许手改只会"输了被覆盖"）；取消勾选后手动指定时刻。**心情列＝指定时刻那一刻的实际心情**：换时刻 ⇒ 列里的数值按轨迹重算；手改某一格 ⇒ 在那一刻给她一个「心情指定事件」（锚点，见 §5 第 12 条）；**干员列跟着时刻走**（时刻落在哪一班就显示那一班的人）。点表格里的干员名可搜索更换。**改动立即生效**（心情输入防抖 **500ms**：一次落地＝一整轮重算，实测 0.2s（周期数 1）~0.7s（周期数 3）；越界不落地并在下方报错）。原来的工具栏「重置心情」＝这里的「恢复导入值」（它会把**全部锚点**一起清掉） |
| **②g 「不在基建」的干员（本班未排班 / 手动添加）** | 「设置…」→**干员与心情** 表格**最后一段**「不在工作设施、也不在宿舍（本班未排班）」：① **自动**列出本班没排到位置的人（含"整个排班都没排到"的板凳干员）；② 「**＋ 添加干员…**」可从全量名册/干员池里挑人加进来 —— 加进去时会**自动把她从所有班次的位置上摘下来**（"名单里的人 ↔ 不在任何房间里"是一条**不变式**，见 §5 第 14 条）。每人一行：**心情可改**（周期起点＝`initial_moods`、其余时刻＝锚点），`—` 那列写**她在别的班在哪**（如 `其他班：2中 3宿`），行尾「×」把她移出名单。口径：**这一刻**她不消耗也不回复；**若她在别的班有活，那些班照常算**（"本班未排班" ≠ "整份排班都不在基建"）。名单写进排班 JSON 顶层 `detached`。**另有两处一眼可辨**：底部「全员一览」的芯片位置标记显示绿色 `不`（`休` = 本班未排班），右侧对点查询的数值区多一行 `⚠ 不在基建…心情整段不变、不参与技能计数` |
| **②h 表格怎么摆 / 怎么滚** | 表格＝**固定表头**（`房间 · 位次 · 干员 · 练度 · 心情 · 说明`，6 列由 `ui/batch.py: TABLE_COLUMNS` 一处定义）+ **房间分组卡片**（每间房一条通栏标题 `制1 制造站#1 · Lv3 · 3/3 人`）+ **共享 grid 等宽列** + **悬停高亮**（指针所在行底色变浅蓝；「不在基建」那段固定淡绿底、不参与悬停，**滚动期间一律不画**）。**搜索框**在表格上方：输入即过滤（匹配干员名或房间名，清空/Esc 恢复；一键动作只作用于看得见的行）。**滚动**：滚轮一次 3 行、`Shift+滚轮`＝整页、`Ctrl+滚轮`＝10 行，`PgUp/PgDn/Home/End`＝翻页与首尾（见 §5 第 16、20、21 条） |
| **②e 练度（精英化）** | **默认口径＝满练**（精英化 2、等级 30）；没练满的干员要显式标注，否则技能会被多算。三处能看出来：① 看板与「全员一览」的芯片**名字后面带 `E1` 角标**（只有非 E2 才有）；② 右侧「对点查询」的数值区多一行 `练度 E1（等级 30）· 已解锁 N 条心情技能；⚠ 因未满练少 M 条：「手工艺品·β」（E2）`；③ 「设置…」→**干员与心情**表格每行的**练度下拉**（E0/E1/E2）＋「全部设为 E2」一键。写回场景时**只有非 E2 才**记成对象 `{"name": "卡夫卡", "elite": 1}`，其余仍是纯字符串（JSON 保持简洁） |
| **②f 干员池（导入 v4 蓝图才有）** | 那类文件只有"蓝图 + 我有谁"，**房间里必然没人**。导入后池会显示在「干员与心情」的「干员池：…」一行：池里的人能在选人搜索窗里搜到、**练度按池里的值**（E1 就写 E1），并且可以一键**「从池中依次填入」**按顺序铺满当前班次的位置（铺完可继续手改）。没有池的文件（MAA / v3 输出）那行会写清"为空"，但按钮仍可点（会提示原因） |
| **③ 时间滑动 → 各位置心情实时变化** | 底部滑块；两侧 `◀`/`▶` 按钮与 `←/→` 键 = **15 分钟一档**，`Home/End` 跳首尾，`空格` **只**播放/暂停——主窗口里的控件都挂了 widget 级 `<space>`（播放/暂停 + `break`），所以空格**不会**去"按下"当前聚焦的工具栏按钮（曾经点过设置按钮后按空格会又弹一次窗）；工具栏按钮同时 `takefocus=False`，不参与 Tab 焦点（步长与快捷键写在滑块右侧提示里）；心情值、心情条、颜色随时刻实时刷新 |
| **④ 对点：输入干员名 → 整周期曲线** | 右侧「对点查询」选人（下拉 / ◀▶ 切换）→ 曲线 + 关键数值（**此刻速率 / 本班平均速率**、起点·周期末、最低·最高及时刻、红脸段数与合计时长、各班最低）。速率写法 `↓2/时`（在降）/ `↑1.5/时`（在升）；这两个数**随滑块 / 播放实时更新**（`refresh_view` 里顺带刷，实测 0.04ms/次） |
| **⑤ 简洁明了** | 界面只有"看板 / 全员一览 / 曲线 / 滑块"四块；设置全部收在一个窗口里（4 个分区），且**改动立即生效**——不再有"点开对话框 → 改 → 点应用"的三步操作；配色与字体集中在 `ui/theme.py` |

> **为什么合并**：合并前工具栏并列 **8 个控件**，其中「重置心情」与批量表里的「恢复导入值」
> 是同一件事、「周期数」与「班次设置」说的都是时间轴，而每个设置都要走"打开 → 改 → 应用 → 关窗"；
> 入口也太散（想改"换谁"得先在工具栏上认出那颗按钮）。现在唯一入口是「设置…」，
> 左侧导航一眼看全四件事，**关掉窗口即接受**。唯一的例外是**周期数**：它调得频，
> 工具栏上留了一个下拉，与设置里那一个**共用同一个变量**（不是两份状态）。

### 2.1 「导入排班」认哪 4 种 JSON（`store/sources.py`）

判定按顺序做，只看**特征字段**，不看文件名：

| 格式 | 判据 | 里面有什么 | 怎么导 |
|---|---|---|---|
| `scenario` | 顶层有 `facilities` | 房间 + 人员（本工具自己的场景 JSON） | 原样透传（一班） |
| `v3_out` | 顶层有 `result`（信封），或 `rotation`/`maa`/`training_advice`/`profile` 之一 | **每班时长**（`rotation.shifts[].duration_hours`）、**谁在哪间房**（`assignment.rooms[]`，带 `elite/level`）、**按设施类型分组的名单**（`maa.plans[].rooms`，含空宿舍 `skip:true`） | **多班排班**（见下） |
| `plan_compute_v4` | `schema_version == 4` 且同时有 `layout` 与 `operbox` | 房间 `kind/level`、宿舍床位/氛围、**干员池**（`elite/level/own`）、`options.rotation`、`fiammetta_enable`、`scenario.initial_global` | 空蓝图（房间建好、**没有人**）+ 干员池 + 班次时长 |
| `maa` | 顶层有 `plans`（数组） | 按类型分组的干员名单 + 班次名里的时长 | 多班排班 |

参考文档：v3 输出的字段契约在 `resources/输出JSON结构说明.md`；v4 输入的示例与注释在
`resources/plan_compute_example_v4_annotated.md`（真实 schema 在 v3 仓库的
`contracts/plan-compute-v4.schema.json`）。

**v3 输出怎么拼**（上游输出里**没有 `kind`、也没有 `level`**，契约 §4.5/§10 明说）：

1. **房间类型 / 房间顺序 / 人员** ← `result.maa.plans[i].rooms`（**按设施类型分组**，类型明确、连空宿舍都在）；
2. **每班时长** ← `rotation.shifts[i].duration_hours`（比 MAA 班次名里的 `12h` 更权威；
   缺了才退回去解析名字，并记一笔"这是推断"）；
3. **练度** ← `assignment.rooms[].operators[]`（`maa` 段只有名字）按**干员名**补齐；
4. **训练挂件** ← `assignment.training_assist` → 放进训练室（挂件位，0 消耗）；
5. **菲亚梅塔** ← 各班 `Fiammetta{enable,target}` → 本工具的「换心情」：任一班开着就开，
   `target` 各班一致就用它当"换谁"，不一致就**逐班照搬**（写 `per_shift` 覆盖，第 3 班关着就关着）。

**拿不到 `maa` 段时依次退化**：同文件里的 `layout`（输入回显，kind/level 权威）→
`efficiencies.room_lines` 的字段组（`trade_*`/`manufacture_*`/`power_*` 判类型）→
`room_id` 前缀；等级没有 layout 就按"实际放进几个人"反推最低可行等级。
**这一切推断都逐条写进导入报告**（`ImportReport.inferred`），状态栏出现「⚠ N 项靠推断」时
可以到报告明细里看是哪几间房：

```python
from store.sources import import_file        # 老路径 mood_soc.importer 是兼容转发壳
imp = import_file("resources/import_v3_out_no_maa.json")
print(imp.report.details())      # 读到 / ⚠ 推断 / ⚠ 名字不认得 / 没有心情技能 / 忽略
```

**干员名**：别的工具可能写英文名或干员 id（`Amiya` / `char_154_morgan`）。
`data/operator_names.py`（由 `scripts/generate_operator_names.py` 从上游
`character_table.json` 生成，848 条）负责译成中文名；报告里把"认得但本项目没有他的心情技能"
（如 能天使，她的基建技能是产出类）与"名字完全不认得"**分成两档**，分量不同。

附带的小工具：
**▶ 播放 + 速度 1x / 60x / 600x / 3600x / 14400x**——速度单位是 **模拟秒 / 真实秒（s/s）**，
`1x` 就是实时（1 秒推进 1 模拟秒），`3600x` ＝ 1 小时/秒（24h 周期 24 秒放完）；
工具栏只放短提示（`＝实时` / `＝1 小时/秒`…），完整解释写在状态栏。
推进量按**真实流逝时间**计算，所以标称与实际一致（实测 1x→1.0、60x→58.5、3600x→3488、14400x→13773 s/s）。
**班次按钮**（跳到该班次起点）在底部滑块上方。按钮文字**只写「序号 + 时段」**
（`1. 00:00 – 12:00`）——班次名与时长（`Shift 1 · 12h`）**只在看板头部出现一次**：
早先按钮写的是 `1. Shift 1 · 12h（12h）`，MAA 的班次名里本来就带 `12h`、按钮又补一次，
而且看板头部已经写着同一个名字，等于同一条班次在上下两处各显示一遍。

**修过的显示 bug**（2026-09，都有回归用例 `test_反复重建班次条不残留` 钉着）：

- **「班次」标签会越攒越多**：`_build_shift_buttons` 原先只销毁按钮、标签每调一次新建一个
  ⇒ 导入一次 / 改一次初始时间点 / 改一次班次时长就多攒一个，底部显示成
  `班次 班次 班次 1. …`（实测 1→2→3→4）。现在**重建前清空整行**。
- **时段文案里的「（第N天）」到处乱标**：现在**只在"起止不在同一天"时标在结束那侧** ——
  起点 21:00 时 `1. 21:00 – 09:00（第2天）`（真跨天）、`2. 09:00 – 15:00`（不标），
  与图表横轴 `theme.fmt_clock_short` 的口径一致（原先两头都标，按钮宽 486px → 798px）。
- 曲线**班次带**的标题（`ui/chart.py: _band_title`）：班次名里已含时长就不重复追加
  （`Shift 1 · 12h`，不再是 `Shift 1 · 12h  12h`）；名字与真实时长不一致时（手写场景）
  以**真实 `hours`** 为准，显示成 `Shift 1  8h`。

### 2.2 周期数 > 1：底部班次条带「周期」选择器

**周期选择器**（用户口径："班次可以根据我选择的周期数不同，而能选择不同周期内的时段"）：

```
周期数 = 1   →  班次 [1. 00:00 – 12:00] [2. 12:00 – 18:00] [3. 18:00 – 00:00（第2天）]
周期数 = 3   →  周期 [1][2][3]   班次 [1. …] [2. …] [3. …]
```

- **点班次 `i`** → 跳「**你当前所在周期**的第 `i` 班」（`ui/app.py: _goto_shift`）；
- **点周期 `c`** → 跳「第 `c` 周期的**同一班**」（`_goto_cycle`）——"同一班换一周"最顺手；
- **高亮**：周期与班次各按 `Session.cycle_of(current_t)` / `Schedule.index_at(t)` 上色，
  所以**拖滑块跨周期时选择器自动跟随**；
- ⚠️ **不另存"选中周期"这个状态**（唯一真源＝`current_t` 落在哪个周期）：多一份状态就多一处
  会跟滑块不一致的地方（与"周期数两处共用一份状态"同一条理由）；
- 周期数改回 1 时这一段自动消失，`current_t` 被夹回新跨度内（`recompute(fit_spans)` 的老规矩）。

**「改时长」会连班次名里内嵌的旧时长一起改**（用户口径，`store/schedule.py: relabel_hours`）：
`Shift 1 · 12h` 在改成 8h 后变 `Shift 1 · 8h`（不含时长或写的不是旧时长的名字**一字不动**，
如 `第一个班`、`Shift 2 · 6h` 在 12h→8h 时）。同时把 `entry_events.per_shift` 里
**按班次名写的键**重映射成新名 —— 否则那条"按班次覆盖"会**静默失效**
（`EntryShiftOverride.matches` 是拿键跟新班次名比的）。

### 3.1 看板：紧凑芯片 + 「中枢整行 / 工作区·休息区两列」

旧版每个位置是 104×58 的大格子（名字/数值/心情条/红脸标签四个控件），一间 5 人宿舍占 290px 高，
**一屏装不下**（内容 695px > 可视 577px）——必须滚动才能看到宿舍，"看到所有干员"就成了空话。
现在每个位置是 **21px 高的芯片**（`ui/widgets.MoodChip`）：

```
▌制1  森蚺              16.2      ▌=心情色条（红→绿）；底色=该心情的浅色调；红脸整条变红
▌贸2  卡夫卡 E1         15.0      名字后的 E1＝精英化不足（只有非 E2 才显示，见 ②e）
```

排布（`ui/board.py`，示例排班实测 **338px 高 / 可视 577px**）：

| 区域 | 内容 | 说明 |
|---|---|---|
| **整行** | 控制中枢 | `FULL_WIDTH_TYPES`：占一整行、**芯片横排**（5 人才 1 行高） |
| **左列** | 制造站 / 贸易站 / 发电站 | `COLUMN_GROUPS[0]`　"工作区" |
| **右列** | 会客室·办公室·训练室·加工站（拼一行）/ 宿舍 | `COLUMN_GROUPS[1]`　"辅助与休息区"（`SMALL_TYPES` 里"通常各一间"的会拼行） |

### 3.2 「全员一览」：把整个周期的干员一次摆出来

看板只画**当前班次**，只出现在别的班次里的干员（示例排班有 10 名）在上面看不到；
而"这套排班能不能永动"恰恰要同时盯着所有人。所以底部另有一条全员一览：

- 覆盖 `Schedule.operator_names()` 的**全部**干员（示例 57 名），14 列 × 5 行铺满，不滚动不翻页；
- 顺序**固定**（班次出现顺序）——不按心情排序，否则拖动滑块时格子会跳来跳去；
  "谁危险"靠颜色与右上角的「最危险 3 人 / ⚠ 已红脸」文字体现；
- 每格带**位置标记**（`制1`/`贸3`/`宿2`/`中`/`办`…）：当前班次在哪；不在本班次显示 `休` 并置灰；
- **左键 = 对点**（右侧曲线切到该干员，并在看板上高亮他的位置）、**右键 = 设心情**。

### 3.3 其余

- **曲线**：班次交替底色 + 班次分界虚线 + 红脸区间红底；曲线是**事件节点直连的折线**
  （不做等距采样——等距采样会把拐点抹平）；鼠标悬停给十字准星与精确读数（时刻 / 心情 / **速率** / 所在设施）。

**横轴刻度的排版**：刻度**只写 `HH:MM`**（步长按最多 12 条 + 相邻间距不少于 46px 自动选），
跨天时**另起一行**在每天区间的下方居中标 `第1天`/`第2天`，并在天的分界处画一条实线。
> 为什么：刻度最后一条落在周期末尾，`fmt_clock(24)` 会给出 `00:00（第2天）`（约 90px 宽），
> 塞进约 43px 的刻度间距里必然和左右两条叠字——所以刻度一律走 `fmt_clock_short`（不带天数）。
- **滑块**：拖动只做插值刷新（不重算），节流约 30fps 且末位必落地；
  拖动中走"跟手快路径"（只改数值与色条），**停手 200ms 后补一次完整上色**（见 §4.2 的性能表）。
- **滚轮**：只在**指针位于看板上**时滚动看板；看板已经一屏放下时滚轮不做任何事。
  实现用 Tk 的 **bindtags**（给看板里的每个控件挂一个 `MoodBoard` tag），
  **不是** `bind_all` —— 后者会抢走整个窗口的滚轮（悬停在曲线/全员一览/干员下拉上滚一下，
  看板也跟着滚，这就是"滚轮有问题"的根源，见 §7.1）。
- **播放**：`▶ 播放` 按速度推进，单位是 **模拟秒/真实秒（s/s）**——`1x`＝实时、`3600x`＝1 小时/秒；
  推进量用**真实流逝时间**计算（不是名义 tick 间隔），所以标称与实际一致。
  工具栏的组合框旁只显示短提示（`＝实时` / `＝1 小时/秒`…），完整解释（含"1x 要放 24 小时"）写在状态栏。
- **切换班次不重建控件**：房间结构没变时只把芯片内容换一遍
  （旧写法每次都销毁重建 50 个芯片，实测一次 **419ms**，就是"切换布局卡顿"的来源；
  现在复用芯片后约 **56ms**，其中还包括真实重绘）。拖动中跨班还会把「全员一览」的位置标记
  推迟到停手后再补，避免拖动时噎一下。
- **时刻显示都带「初始时间点」**：`Schedule.start_clock`（时间轴里设）＝周期起点是几点，
  例如设成 `01:00` ⇒ 滑块读数 `01:00`、班次按钮 `1. 01:00 – 13:00`、曲线横轴 `01:00…`、
  逐次表组头 `第 1 周期 · 第 1 班（01:00–13:00）`。**只改标签**：轨迹与判定一字不变
  （`theme.fmt_clock(t, cycle, offset)` 统一渲染，`ui/app.py` 的 `clock_text()` 是唯一入口）。

## 4. 计算核心 `store/schedule.py`（**不依赖任何 GUI**）

排班是"多班轮换"：一个 24h 周期切成若干班（12h + 6h + 6h），每班**自己的布局**，
干员在班次切换时换房间；心情跨班连续（**不在班次边界重置**）。

### 4.1 为什么是「事件驱动精确积分」

在一段区间内（没有事件发生），所有干员的净速率都不变 ⇒ 心情是**时间的线性函数**，
可以一步解析地推到区间末尾。会让速率改变的事有四类，都能**精确求出时刻**：

| 事件 | 为什么它改变速率 |
|---|---|
| **班次边界** | 布局换了，房间与同设施他人都变了 |
| **心情触到 0（红脸）** | 红脸后该干员所有心情类技能失效（`04-特殊机制.md` 第 1 条） |
| **心情触到阈值** `{24, 20, 18, 12}` | 现有条件函数与变量产出者读的就是这些值（<18 / <20 / ==24 / 落差>12 / mood_below_12） |
| **同设施两人心情交叉** | 单体回复的受益者按"心情最低且未满"锁定、池分配按"未满成员"均分 ⇒ 排序变化会换人 |

外加一条**安全上限** `MAX_SEGMENT_HOURS = 0.25h` 兜底：将来若新增"读心情的条件"而忘了登记到
`EVENT_THRESHOLDS`，误差也被限制在一个小段内（而不是无声放大）。
另外，**只在"可能变了"时才重算速率**（进新班次 / 发生事件）；纯上限推进直接复用上一次的速率。

**好处**：曲线由事件节点直连即为**精确**折线，滑块处线性插值取值也精确，且不必按 0.05h 跑上万步。

实测（示例排班，47 名干员；节点数与耗时会随**数据与机器**漂移，以当时实测为准）：

| 周期数 | 重算耗时 | 轨迹节点 | 与 0.05h 细步长对照的最大偏差（**中间段**） |
|---|---|---|---|
| 1 | ~0.23s | 131 | ≈0（3e-26） |
| 2 | ~0.53s | 283 | ≈0（8e-26） |
| 3 | ~0.99s | 434 | ≈0（1.2e-25） |

> **精确性自证**：把 `max_segment` 缩到 0.05h（重算次数 ×5）后，同一排班的心情曲线在
> **每一个采样点**上都一致（偏差只有 Decimal 28 位有效数字处的舍入，量级 1e-25）
> —— 说明"事件切分"没有遗漏依赖心情的机制。
>
> ⚠️ **这条自证必须比"中间段"，不能只比 24h 末值**：曾经只比末值时它是"0.000000000000"，
> 而曲线中段**整整差了 1.0**（阈值吸附把积分值往回拽，见 `04-特殊机制.md` 第 35 条）——
> 末值恰好被"住满 24 再等"吸收了，所以只比末值等于没查。
> 回归断言：`tests/test_ui_schedule_blackbox.py::Test阈值吸附::test_步长不影响任何中间点`。

### 4.2 界面刷新性能（"跟手"是怎么做到的）

整屏有 50（看板）+ 57（全员一览）= **107 个芯片**，粗放地每步全量重绘会卡（实测单步 92ms）。
两级刷新 + 底色分桶之后：

| 路径 | 每次耗时 | 什么时候用 |
|---|---|---|
| **跟手快路径**（只改数值文字 + 色条；底色跨 2 点分桶才重绘） | **0.9 ms** | 拖动滑块中（节流 ~30fps） |
| **完整上色**（数值 + 色条 + 底色 + 红脸描边 + 最危险提示） | **11.7 ms** | 停手 200ms 后自动补一次；按钮/快捷键跳转 |
| 轨迹取值 `moods_at()` | 0.045 ms/次 | 每次刷新 |

其它几处刻意的取舍：

- 芯片只在 `_paint_key`（心情字符串 + dim）变化时才动控件，没变就整条跳过；
- 全员一览在拖动中**不重排、不改提示文字**（省一次 configure），且顺序固定不跳格；
- 只在"当前时刻所在班次的布局"变化时才重建看板控件（`_layout_sig` 比对）。

### 4.2 公开 API（可被测试/脚本直接用）

```python
from ui.schedule import load_schedule, simulate_schedule, Schedule, Shift, MoodSetEvent

sch = load_schedule(["a.json", "b.json", "c.json"])      # 多文件；或一个含多 plan 的文件
#  → Schedule.shifts（每班 label/hours/facilities）、cycle_hours（= 各班长之和，强校验）
traj = simulate_schedule(sch, cycles=1, initial_moods=None, entry_events=False)
traj.mood_at("巫恋", 12)          # 精确取值（分段线性插值）
traj.bounds("巫恋")               # (最低, 最低时刻, 最高, 最高时刻)
traj.red_face_spans("巫恋")       # 红脸区间
traj.min_mood_at_each_shift("巫恋")   # 每班最低点（"哪一班最危险"）
```

## 5. 口径与已知简化（写清楚，免得被当 bug）

1. **周期起点心情**：取"第一班布局里写的值"（场景格式支持 `{"name":"x","mood":10}`），
   没写就是满心情 24。界面上手动设的心情也是**周期起点**的值（对话框里已注明）。
2. **跨班不重置**：班次切换时心情接着上一班末尾继续（这才是排班能不能永动的关键）。
3. **未排班的干员**：某班次里没有他 ⇒ 视为"不在基建内"：净速率 0，心情不变。
4. **周期可重复**：周期数 2/3 表示把同一排班连跑几周，心情接着上一周期末尾继续；
   **每个周期里的每一班都会重新结算进驻事件**（同一个班次副本跨周期被复用，所以模拟器在
   每次"班次开始"前把 `Operator.entry_swapped` 归位——否则第 2 个周期起一次都不会换，
   这是修过的一个 bug：`rules.reset_entry_events`）。
5. **进驻事件（M15a 患难之交）**：默认**不结算**；勾选后在**每班开始时**结算一次（就地改心情，
   并在曲线面板标出）。理由同 CLI：它是"进驻那一刻"的事件，不是每小时速率。
   设置框＝**一个总开关 + 一张"每班一行"的表**（P5f 收过两次：先砍成三设置 + 折叠高级区，
   再合成这张表——真正逐班的东西本来就是"用不用 + 换谁 + 要不要等"这一整组，
   分成"全局值 + 例外"两层只会让人设的时候做三次映射）：

   ```
   ① 开启心情交换
   ② 每个班次单独设置：
        班次              用   换谁                    强制切换
        1. Shift 1 · 12h  [✓]  [前一位进驻（同宿舍）▾]  [ ]
        2. Shift 2 · 6h   [✓]  [塞雷娅 ▾]              [✓]
        3. Shift 3 · 6h   [ ]  [全基建最累的那位 ▾]     [ ]
                            [全选] [全不选]
   ```

   | 控件 | 取值 | 落到引擎 |
   |---|---|---|
   | **① 开启心情交换** | 勾 / 不勾 | `enabled`。**换心情的唯一开关**——它就在设置中心的「换心情」分区里，工具栏只留状态文字（`未开启` / `已开启 · 换塞雷娅 · 等她满`） |
   | **② 每行的「用」** | 勾 / 不勾 | `per_shift[key].enabled`：**不勾＝这一班不换心情** |
   | **② 每行的「换谁」** | 前一位进驻（同宿舍，默认）/ 全基建最累的那位（自动）/ 具体干员（下拉里是排班里的干员） | `swap_with` + `scope`——**每个选项自带范围**：前一位＝同宿舍，最累的 / 具体干员＝基建任意位置。⚠️ 不在排班里的人换不了（引擎会报"不在基建内"），所以下拉不含名册外的干员 |
   | **② 每行的「强制切换」** | 勾＝必须换成功：她没满心情就**等她回满再换**（`wait`）／不勾＝判定时她没满**就不换**（`full`） | `when` |

   **第 1 个勾着「用」的班次那一行充当全局默认**（写进 `swap_with`/`scope`/`when`），
   其余班次**只有和它不同**（含"这一班不用"）才写一条 `per_shift` 覆盖——所以三班设置相同时
   `per_shift` 为空、工具栏文案仍是那套紧凑的单设置写法（`已开启 · 换塞雷娅 · 等她满`）。

   **不设开关的固定口径**（写在框内说明里）：
   - 「对方心情是多少」**照换**：双方都是 24 也执行（数值不变）。
   - 「位置也一起互换」被收掉：界面**固定只换心情**、两人都留在自己的岗位上。
   - 引擎侧的 `when="immediate"`（连她的心情都不看）**仍保留在 JSON / API / CLI**，
     只是界面不再提供这一档（载入这种配置时那一行显示为"不勾强制切换"）。

   指定的对象不在允许范围内时该班次不换，并在图表标记里给出说明（`entry_swap_skipped`）。
   双方心情相同时**仍然执行**（标记会注明"数值不变"）。
   JSON 侧字段（含 `per_shift`、`when`）与引擎 API 见 `04-特殊机制.md` 第 29 条。
   > 实测的一个自洽例子（示例排班）：她红脸时「自律」失效 → 按宿舍基础 4/h 回满 →
   > **恰好走到 24 的那一刻**触发换心情（18:00 那次），而不是等她整天。

6. **同一份"班次副本"被跨班次/跨周期复用** ⇒ 三处状态必须跟着复位（都是修过的 bug，
   回归用例在 `tests/test_ui_schedule_blackbox.py::Test副本状态时效性`）：

   | 状态 | 什么时候复位 | 不复位会怎样 |
   |---|---|---|
   | `Operator.entry_swapped`（进驻事件幂等标记） | **每个班次开始**（`rules.reset_entry_events`） | 周期数 ≥ 2 时第 2 个周期起换心情一次都不触发 |
   | 副本里各干员的 `.mood` | **每次算速率之前**（`_sync_moods`） | 依赖心情的条件技能（宿舍单体回复选谁、池分配…）拿旧值判断，速率算错 |
   | 设施内的位置（`restore_back=false` 时会改） | **每个班次开始**（从计划重建那一班的副本） | `restore_back=false` + 多周期：第 2 个周期她不在宿舍，"进驻宿舍时"不成立、那一班静默不换 |

   前两条与界面无关（默认路径也会走到）；第三条只在 JSON/API 显式写 `restore_back: false` 时出现
   ——界面固定 `restore_back=True`。
   > 示例排班对"心情"不敏感（全员 24 → 全员 5，57 名干员的速率一个都不变），
   > 所以第 2 条在示例上看不出差别；换成带宿舍单体回复/池分配的真实阵容就会歪。

7. **闲置入宿（未满的闲置干员进宿舍）**：口径与规则见 `04-特殊机制.md` 第 30 条。界面侧四条要点：
   ① 表格**按时间排**（第 1 周期第 1 班 → … → 第 2 周期第 3 班），每个"周期 × 班次"一组、
   组头写明时刻区间、每组自带全选/全不选；只列出**真的有候选**的那些次；
   ② 「去哪／与谁换」下拉**只列那一刻真的可选的**：空位（`宿舍01`＝第 1 间宿舍，放进它最靠前的空位、不动任何人）与满心情的宿舍干员（与他互换）；设置粒度是 **（周期, 班次, 干员）**——
   因为心情跨班跨周期连续，每次的候选与可交换对象都不一样（实测第 2 周期第 1 班出现了
   第 1 周期同一班没有的候选）；
   ⚠️ 这里的"那一刻"是**轮到这一位候选的那一刻**：目标列表取自
   `Trajectory.idle_state_at`（引擎处理她时留的**逐位宿舍态**：住户名单 + 空位），
   取不到（没开闲置入宿 / 她不是引擎候选）才退回整份段世界 `world_at`、再退回排班快照。
   **不能**直接拿 `schedule.shifts[i].world` 快照当"她那一刻的世界"：候选是**依次**处理的，
   排前面的人会把宿舍里的人换出去，快照里那位看着还在宿舍 —— 用户报过
   "面板里列着 清流、那一刻宿舍里并没有 清流"（回归 `test_面板逐行候选按轮到她的那一刻算`）；
   ③ **改动实时生效**：勾选/改目标后（防抖 250ms）立刻把当前设置套进模拟重算，
   **表与主界面看板/曲线一起刷新**（改动会影响后面每一次的候选）；
   旧版对话框的"取消回滚"随对话框一起取消——设置中心里改完即接受（再改回去即可）；
   ④ 它**会改布局**（有人进宿舍、有人被换出），所以开启后别人的速率也可能变（宿舍回复按人数/氛围，
   被换出的人不再给同宿舍提供效果）——这是模型该有的行为，不是 bug。
   ⚠️ **"看不到谁被换出"已经修掉了**：界面显示"她在哪"一律读**引擎那份布局副本**
   （`Trajectory.world_at`，见 §5 第 21 条）—— 被换出的人在看板/全员一览/对点查询/表格位置列里
   都显示为"不在基建"，表格那行还会打 `⇄` 并在「说明」列写明`本班被闲置入宿换出（快照写 …）`。
8. **干员与心情（原「批量设置」）只收集结果、不新增数值逻辑**：`ui/batch.py` 把"当前布局的干员 +
   心情 + 练度"摊成一张表，干员列与**练度列**按班次（改过的班次留在面板的草稿里，
   切班次再切回来不丢）。练度也只是写回 `Operator.elite`，判定仍由 `mood_soc/rules.py` 的 `_unlocked` 做
   （见 `03-技能系统.md` §5.3）。面板本身**不含引擎逻辑**：它只把改动交给 `ui/app.py` 的
   `apply_batch` / `apply_entry_event` / `apply_idle_to_dorm` / `apply_shift_hours` 落地。
   **心情列＝"指定时刻那一刻的实际心情"**（老口径的"周期起点心情"就是时刻停在
   第 1 周期 0:00 的特例，见第 12 条）。**通知纪律**（这条是性能红线，改之前先看 §7.1 第 9 条）：
   ① **程序化刷新不算改动**——刷新前先把"刚写进去的值"登记进 `_shown`，再 `var.set`
   （顺序反了就会被自己的 `trace` 当成用户改动）；② **结果一样就不通知**——`_notify` 比对
   `repr((changes, moods, events))` 与上次发出的，相同直接返回。两条都是因为"一次通知＝
   宿主一整轮重算"（0.2~0.7s），漏一条就会变成"刷新→重算→刷新"的自激回路。
   **「跟随滑块」的口径**：勾上＝**一直跟着主界面滑块**（`app.follow_slider` 是唯一真源，
   切页/重建都不丢；跟随时周期/时刻/`◀▶`/班次下拉**只读**）；取消或手动指定时刻＝自己定。
   挂在 `<FocusOut>` 上的 `_on_view_change` **值没变就什么都不做**（否则"点一下输入框"
   就会把跟随取消掉）。
9. **单体回复的锁定**仍是引擎既有的**简化**（全局一名受益者，见 `04-特殊机制.md` 建模假设 5）——
   本工具只是在时间上把它推下去，没有改这条口径。
10. **`M15b` 加工类（棘刺「爆炸艺术」）与加工站配方心情消耗**不参与，理由见 `04-特殊机制.md` 第 32 条。
11. 数值：引擎全程 `Decimal`；`Decimal` 除法在 28 位有效数字处舍入，跨事件分割会留下
   `16.19999999999999999999999999` 这类尾巴——**不是算错**，界面上在**显示边界**统一舍入到两位小数
   （`ui/theme.py: fmt_mood`），这与本项目"只在输出边界做一次受控舍入"的约定一致。
12. **「指定周期内任意时刻的心情」＝心情指定事件（锚点）**：`(周期, 周期内时刻, 干员) → 值`，
   引擎（`ui.schedule.MoodSetEvent`）在那一刻把她的 SOC **直接置为**该值，之后按正常速率演化
    （轨迹上是**同刻跳变**，`mood_at(t)` 取到的正是设定值）。三条口径：

    | 问题 | 口径 |
    |---|---|
    | 周期起点（第 1 周期 0:00） | 写的是 `initial_moods`——**与老口径完全同一条路**，不产生锚点 |
    | 多周期 | 锚点**只对指定的那个周期生效**（`cycle` 1 基）；周期数被调小后超范围的锚点**不生效**，面板会在锚点一览里标 ⚠ |
    | 与进驻事件/闲置入宿同时刻 | **锚点最后生效**（显式设定优先于机制推算） |

    它是个**建模假设**：那一刻她被人为调到这个心情（吃了体力药 / 刚被换下来休息），
    不是游戏里真实存在的机制——所以"能不能永动"的结论里，锚点那一格等于假设条件。
    界面上：心情区一行「周期 + 时刻」（`◀/▶` 15 分钟、可「跟随滑块」、可「清空本时刻」），
    手改格子即在该时刻落一个锚点，锚点一览写在心情区下方，「恢复导入值」清掉全部锚点。
13. **「初始时间点」＝周期起点是几点**（`Schedule.start_clock`，0 ~ 24）：`01:00` 表示
    "1 点到第二天 1 点为一个周期"。**纯显示口径**——所有时刻标签按它渲染
    （`theme.fmt_clock(t, cycle, offset)`），**引擎数值、判定、积分一字不变**
    （模型本来就是相对时间：`t = 0` 就是周期起点）。
14. **「不在基建」的人（既不在工作设施、也不在宿舍）**：两个来源 ——
    ① **自动**：本班次没排到位置的人（含"整个排班都没排到"的板凳干员）；
    ② **显式**：排班 JSON 顶层 `"detached": ["某人", ...]`（或在面板里点「＋ 添加干员…」）。

    | 问题 | 口径 |
    |---|---|
    | 数值 | **这一刻**净速率 0（不消耗也不回复）⇒ 心情不变；轨迹里是**一条平线**（起点值） |
    | 但她在别的班有活？ | **那些班照常算**（"本班未排班" ≠ "整份排班都不在基建"）。面板 `—` 列会写 `其他班：2中 3宿` |
    | 参与技能计数吗 | **不参与**：她不在任何 `world.facilities` 里，「基建内每有 1 名 XX 干员」数不到她 |
    | 名单 ↔ 位置 | **不变式**：写进 `detached` 的人会被**自动从所有班次的位置上摘掉**（否则她一边在名单里、一边占着位置有消耗 —— 曾经的不一致，已修） |
    | 心情怎么设 | 与别人同一条路：周期起点写 `initial_moods`，其余时刻写锚点（面板那一段的心情列就是） |
    | 老文件 | 没有这个键 ⇒ 空名单，一切照旧（**向后兼容**）；导出时名单会写回场景顶层 |
14. **「不在基建」的干员（既不在工作设施、也不在宿舍）**：净速率 0、心情**一条平线**，
    不参与任何技能计数。两个来源：本班未排班（自动）、排班 JSON 顶层 `"detached": [...]`
    或面板「＋ 添加干员…」（显式）。
    ⚠️ **界面显示"她在哪"读的是引擎那份布局，不是排班快照**（见第 21 条）——
    因为**闲置入宿会把宿舍里的人换出去**，被换出的那位**当下就变成"不在基建"**：
    心情平线、速率 0。快照里她可能还写着"在宿舍/在贸易站"，所以这种行会打 `⇄` 并在
    「说明」列写清 `本班被闲置入宿换出（快照写 宿舍#1）`。
    判据不止一处：曲线上的绿色「宿」标记、右侧对点查询的 `⚠ 不在基建…`、以及表格的 `⇄`。
15. **`restore_back`（位置也一起互换）只有 JSON/API 能设**：界面固定 `True`；写 `false` 时
    "每班开始时从计划重建那一班副本"（见第 6 条），所以每班都从计划的位置出发、班内保持互换后的位置。
16. **滚轮与键盘：一次滚 3 行是底线**（`ui/scroll.py`）。61 行的表按 1 行/格要从头滚到尾
    60+ 次——"滚不动"就是这么来的。现在：滚轮 3 行、`Shift+滚轮` 整页、`Ctrl+滚轮` 10 行，
    `PgUp/PgDn/Home/End` 翻页与首尾。四条踩过的坑：

    | 坑 | 做法 |
    |---|---|
    | **不能 `bind_all`** | 会抢走整个窗口的滚轮（悬在曲线上滚一下看板也跟着滚）。用**本实例专属 bindtag**（`MoodVScroll<id>`）+ `bind_class`；⚠️ 两张表共用一个 tag 会让后注册的处理函数**同时接管**两张表 |
    | 滚不动时要**把事件让出去** | 内容装得下就 `return None`，否则是"滚了没反应"的错觉 |
    | 小窗口里"整页"要够大 | `_page_lines()` 下限取 `2 × 3 = 6` 行：算出来只有 3~4 行时 Shift 与普通滚轮没区别（实测过） |
    | **指针停在文字上就滚不动** | bindtags 链是「控件 → 控件类 → toplevel → all」，**不含父控件**：只挂 `canvas`/`inner` 挡不住"指针落在某个 `Label` 上"。有行 Frame 的表 `join(row)` 一次就够；**没有行 Frame 的表（表格改成共享 grid 之后）必须逐格 `join`**（见第 20 条、§7.1 第 12 条）——踩过：漏挂的表现是"停在文字上滚不动、停在行间空隙反而能动" |

17. **滚动要"丝滑"：三件事**（都实测过，见 `ui/scroll.py` 与 §7.1 第 12 条）：

    | 症状 | 原因 | 做法 |
    |---|---|---|
    | 滚一下顿一下 | 滚动时 `inner` 不停收到 `<Configure>`，每次都 `itemconfigure` + `scrollregion` | `VScroll.refresh()` 加**尺寸签名缓存**（内容高宽/可视高没变就直接返回）：实测 **0.73ms → 0.002ms** |
    | 滚动时一顿一顿 | 滚过一行会连着触发几十次 `<Enter>/<Leave>`，每次刷一行底色 | 滚动期间置 `VScroll.scrolling`（120ms 内位置不再变才复位），调用方据此**关掉悬停高亮**（`_bind_hover` 里的 `_scrolling()`） |
    | 手感"一格一格" | 一次只滚 1 行 | `UNITS_PER_NOTCH = 3` |

18. **表格高度：估计 + 自校正**（`ui/batch.py`）：
    `_table_height()` 只能**估**——它量的是"**已经建出来的**兄弟控件总高"，而搜索栏/表头/
    报错行那时还没建出来。所以 ① 表格**必须最后建**（放在等级区之前建，量到的已用高度就少了
    整个等级区，多房间时差 ~200px）；② `TABLE_CHROME` 按"搜索栏 + 表头两行"估一个；
    ③ 真正的保证是 `_fit_table_height()` 的**自校正**：面板 `<Configure>` 与构造末尾的
    `after_idle` 里量一次真实请求高度，**超了 `PAGE_H` 就把表格压回去**（每次最多压到
    `TABLE_H_FLOOR`），几帧内收敛。

    > 为什么要有自校正：22 间房（等级区 5 行）那个用例实测超了 **3px** —— 常量凑不准的东西
    > 就别凑，"量和补"更稳。`_fit_table_height()` 里**不能** `update_idletasks()`：那会重入
    > 正在派发的 `<Configure>`，构造期会把别的控件搅乱（实测连片 `invalid command name`）。
19. **搜索过滤只改"看得见"**：`_visible_names()` 让"全部 24 / 全部 0 / 统一设为 X"这类
    一键动作只作用于**过滤后仍显示**的行——"搜了某人、点全部 24"却把看不见的人一起改了，
    很反直觉。过滤只影响显示，**不动任何心情状态**（所以不需要重算）。
20. **列宽只有一个来源：所有单元格共享 `inner` 的 grid**（"不对齐"的根因）。
    grid 的列宽是**按容器**算的。老做法"每行一个独立 `Frame`、行内各自 grid"只能保证
    **行内**对齐、跨行照样差（实测空位行的 `—` 在 x=570、「不在基建」行在 x=561 → 肉眼就是歪的）。
    现在每一行的每个单元格都 `grid(row=行号, column=列)` 直接放在 `inner` 上：列宽彻底唯一
    （实测 6 列的 x 全是单值）。配套三条：

    | 细节 | 做法 |
    |---|---|
    | 像素固定列 | `TABLE_COLUMNS` 里写**像素**（房间 96 / 位次 40 / 练度 56 / 心情 72），不用 `Label(width=N)`（那是字符宽，粗体表头与常规体数据宽度不同 → 差几像素） |
    | 长文字不许撑列 | 干员列/说明列的 `Label` 一律给 `wraplength`（`OP_WRAP` / `DASH_WRAP`）；不给的话最长名字把列撑到 307px |
    | 行高固定 | `inner.rowconfigure(row_i, minsize=ROW_H)`（卡片 `CARD_H=22` + `grid_propagate` 锁高），三种行高一致滚动才顺 |

    ⚠️ 代价：**没有行 Frame 了**，所以 ① 滚轮要**逐格 `join`**（第 16 条）；
    ② 悬停/底色要刷"这一行的所有单元格"（`r["cells"]`）；③ `row` 是**行号**
    （`r["grid_row"]`），不再是 0。
21. **两层"世界"：排班快照 vs 模拟副本 —— 界面显示以引擎为准**（用户口径）。
    引擎跑模拟时会给**每个班次深拷贝一份布局**（`store/schedule.py: worlds`），
    进驻事件的"位置也互换"与**闲置入宿的换人都只改这份副本**，**绝不改排班快照**
    （`schedule.shifts[i].world`，那是"你导入的排班"，导出时原样写回）。
    于是同一个干员会有两份"她在哪"，换过人之后**必然不一致**：

    | 账 | 谁 | 谁读它 |
    |---|---|---|
    | **A 排班快照** | `schedule.shifts[i].world` | 只在"要编辑位置"的地方（面板选人/清空、`_sync_facilities` 的座位表） |
    | **B 模拟副本** | `Trajectory.world_at(t)`（`segments` 里那段实际用的副本） | **看板、全员一览的位置标记、对点查询的"所在设施"、面板的位置列与 `⇄` 标记** |

    ⚠️ 实测的两种不一致（都真的出现过）：
    `快照=贸易站#3（在上班）` vs `引擎=不在基建（心情平线 0）`；
    `快照=不在基建` vs `引擎=在宿舍（被重新放进去了）`。
    **不改快照**是刻意的：写回会让"导出"不再是你的原始排班，而且副本每次 `recompute` 都会重造。

    接线：`ui/app.py: _engine_world(t)`（看板/对点查询/位置标记）与 `world_at_abs(t)`
    （面板的 `world_at=` 口子）→ 都落到 `Trajectory.world_at(t)`；`t` 落在班次边界取**右侧**
    （与 `mood_at`/`rate_at` 的"同刻取跳变后"一致）。面板里"两份不一致"的行会打 `⇄`
    并在「说明」列写明原因，表头第二行同时给一句总说明。

### 6.1 「设置」中心：为什么切换不卡、窗口不跳

| 问题 | 做法 |
|---|---|
| 切页卡（「干员与心情」一页 400+ 控件，重建 ~150ms；用 `pack/pack_forget` 重新 pack 一次 ~100ms） | **页面缓存 + `place` + `tkraise`**：四个分区只建一次，切换只做"提到最上面"。实测切页本体 **<1ms**，加上 Tk 重绘约 **16ms**（一帧左右） |
| 每页高矮不一 → 切页时窗口一跳一跳 | **内容区固定尺寸**（`PAGE_H=740` × 窗口最小宽 980）：`host.pack_propagate(False)`，四个分区共用同一块地方，`open_page` 里**没有** `geometry("")`；窗口还有 `minsize(980,700)` 兜底 |
| **内容装不下 → 被悄悄裁掉** | 一条测试**同时量宽度和高度**（`test_四个分区都装得进固定内容区`）。⚠️ 只量高度会漏掉"房间等级区一行铺 17 间房要 2131px"这种溢出（右侧几间房根本改不了）——所以等级区是**网格**（每行 5 间），表格高度**自动吃剩余空间**。⚠️ **长说明文字必须给 `wraplength`**（`ui/batch.py: HINT_WRAP=700`）：一条长的 `tk.Label` 会把内容区从 816px 撑到 1247px，超宽被裁（踩过） |
| 隐藏页的控件还在，Tab 会跑进看不见的地方 | **焦点环**：`_focusables()` 只收集当前分区的控件，`<Tab>`/`<Shift-Tab>` 在分区内循环；切页时若焦点落在别处就收回窗口 |
| 时间轴一改，别的分区拿的是旧排班 | **`invalidate(*pages)` 标脏**：`ui/app.py` 在 `apply_shift_hours`（班次数量/时长变了）与 `on_cycles_changed`（逐次表按周期展开）里调用；标脏的分区下次进入时**重建**，**当前显示的那一页不标**（它就是改动来源） |
| 表比可视区高 → 只能用鼠标拖滚动条 | **滚轮接管**（`ui/scroll.py`）：表格本体、**表里每一个单元格**（共享 grid 后没有行 Frame 了）、**滚动条本体**都挂同一个 bindtag；只在指针位于那张表上时生效（不用 `bind_all`），且**滚不动时不 `break`**（不制造"滚了没反应"）。⚠️ tag 必须**每张表一个**：`bind_class` 是按 tag 全局生效的，两张表共用一个 tag 会让后注册的处理函数同时接管两张表。**速度**：一次 3 行（`UNITS_PER_NOTCH`）、`Shift+滚轮` 整页、`Ctrl+滚轮` 10 行，另有 `PgUp/PgDn/Home/End` —— 见 §5 第 16 条 |
| 滚起来"卡壳"、不丝滑 | **尺寸签名缓存**（`refresh()` 白花的 `itemconfigure`）＋ **滚动期间关掉悬停高亮**（`VScroll.scrolling`，120ms 复位）—— 见 §5 第 17 条 |
| 表格里的列"没对齐" | **列宽只有一个来源**：所有单元格共享 `inner` 的 grid + 像素固定列宽 + `wraplength` 夹住长文字 —— 见 §5 第 20 条 |
| 61 行的表找人要滚半天 | 「干员与心情」表格上方的**搜索框**（输入即过滤，匹配干员名或房间名，`Esc` 清空）；一键动作只作用于**过滤后仍显示**的行（见 §5 第 18 条） |

### 7.1 Tk 的坑（踩过一次，别再踩）

1. **不要在 `<Configure>`（几何）处理函数里销毁/重建控件**——Tk 正在做几何管理，
   在里面 `destroy()` 会让**进程直接崩**（实测 `0xC0000005`，不是 Python 异常）。
   全员一览重排列数时因此改为 `after_idle` 延迟重建（`ui/roster.py: _on_resize`），
   并且开局就按真实宽度算好列数，避免"建一次→布局落定→再重建一次"（那次重建 ~110ms）。
2. **`widget.after(...)` 的回调会因控件被销毁而报 `invalid command name`**：
   看板重建会销毁芯片，所以 `flash()` 的定时器挂到 `toplevel` 上，并在回调里判 `winfo_exists()`；
   主窗口 `destroy()` 会统一取消 `_refresh_job` / `_settle_job` / `_play_job` / `_autoload_job`。
3. **不要用 `bind_all("<MouseWheel>")` 做局部滚动**：它会抢走整窗滚轮，
   连 `Combobox` 下拉列表的滚动都会被带跑。用 **bindtags** 把事件限定在看板控件上。
4. **拖动时不要每步重建控件**：改数值/颜色即可，重建留给"布局真的变了"的时刻。
5. **定时器驱动的动画不要按"名义间隔"算推进量**：一次 tick 里还要做刷新，
   按 60ms 名义值算会让 1x 实际只有 0.78 倍速；要用 `time.perf_counter()` 的真实间隔。
6. **Canvas 里的 `create_window` item 不会自己跟着子控件长高**：它保持创建时的大小，
   `bbox("all")` 在几何落定前还会给出 `1×1`。症状是"滚动条拖不动、滚轮也没反应"——
   必须显式 `itemconfigure(win, height=子控件的 winfo_reqheight())` 并 `update_idletasks()`
   之后再读尺寸。两张表的统一做法在 `ui/scroll.py: VScroll.refresh()`（闲置入宿那张表踩过）。
7. **`bind_class(tag, …)` 是"按 tag 全局生效"**：两张表若共用一个 bindtag，
   后注册的处理函数会**同时接管两张表**。tag 要每实例一个（`ui/scroll.py` 用 `id(self)` 拼）。
8. **`event_generate("<MouseWheel>")` 在测试里不一定送到你写的那个控件**（滚轮事件与指针位置相关）：
   验证滚轮逻辑时可以直接调 `VScroll.on_wheel(事件对象)`，或者断言 bindtag 挂对了 —— 别只信 `event_generate`。
9. **`StringVar.trace_add("write", …)` 对"程序自己的 `var.set()`"一样触发** ⇒ 极易写出**自激回路**：
   面板刷新 → 写回输入框 → 被当成"用户改动" → 通知宿主 → 宿主重算 → 推送回来 → 又刷新 → ……
   实测症状是"设置干员与心情卡顿严重"：**空转 2 秒重算 6 次 / 2336ms**（单次 231ms），CPU 一直 ~75%。
   两条必守纪律（`ui/batch.py`）：
   - 程序化写入一律走 `_set_cell(name, text)`：**先登记 `_shown[name]`，再 `var.set`**
     （顺序反了，`trace` 回调读到的 `_shown` 还是旧值，就判成用户改的）；
   - 输入框的 `trace` 回调走 `_on_cell_write(name)`：**与 `_shown` 相等就直接 return**；
   - 再加一道"结果签名"去重：`_notify` 里比对 `repr((changes, moods, events))`，相同不通知。
   修完的空闲 CPU ≈ **1%**，改一格＝恰好 1 次重算。
10. **`Checkbutton` 的状态别放在"会被重建的 Frame"里**：设置中心每一页都会被**标脏重建**
    （改时长/周期数时），状态放面板内部就会"切个页回来勾选没了"——「跟随滑块」实测就是这样丢的。
    做法与「周期数」一致：**变量挂在 `app` 上**（`app.follow_slider` / `app.cycles_var`），
    面板只绑上去（`follow_var=` 传进来）；独立使用时（测试里）没有宿主就给个自己的变量。
11. **挂在 `<FocusOut>` 上的"提交"回调必须容忍"值没变"**：点一下输入框再点别处也会触发；
    此时若照样走一遍"提交"，就会产生看不见的副作用（本次就是"什么都没改却把「跟随滑块」取消了"）。
12. **bindtags 链不含"父控件"**：`控件 → 控件自身类 → 所属 toplevel → all → 你挂的 tag`。
    所以"把 tag 挂在容器的 Frame 上"**覆盖不到容器里的标签**——指针停在文字上时事件根本
    到不了处理函数。要有"行 Frame"就 `join(row)` 一次；**没有行 Frame（共享 grid）就逐格
    `join`**。踩过的两种症状：滚轮"停在文字上不动、停在行间空隙反而能动"。
13. **`_fit_table_height()` 这类"在 `<Configure>` 里跑"的函数里不要 `update_idletasks()`**：
    那会**重入**正在派发的几何处理，构造期把别的控件搅乱——实测整片
    `TclError: invalid command name ".!frame.!label2"`（19 个用例连带报错）。
    改为"用上一次量到的真实高度算差、每次 `<Configure>` 再修一次"，几帧内收敛。
14. **局部变量别和"控件属性名"撞车**：`ui/batch.py` 的 `_rebuild_rows()` 里既有滚动位置
    又有"位次"单元格，两者都叫 `pos` → 后者把前者覆盖成 `Label`，`_restore_scroll(Label)`
    抛 `TypeError`，**同一 `try` 之后的 `_sync_filter_note()` 就不执行了**。
    表现极具迷惑性："搜索框明明过滤了，计数提示还是空搜索的文案"。
    教训：`pos` / `row` / `label` / `info` 这类词在长函数里要带前缀（`scroll_pos` / `grid_row`）。
    做法：解析后先与当前值比对，**相同就直接 return**（`ui/batch.py: _on_view_change`）。
12. **面板的"构建"不该产生副作用**：`TimelinePanel` 构建时会 `_validate()` → `_notify()`，
    而 `on_change` 是"用户改了时长"的落地口子（`app.apply_shift_hours` → 重算 + **把当前时刻
    重置为 0:00**）⇒ "打开时间轴页"就把主界面时刻冲成 00:00（实测过）。构建时只报
    `on_validity`、不回调改动（`self._building` 开关），并在 `apply_shift_hours` 里
    **"时长没变就直接返回"** 兜一层。

⚠️ 新增"读心情的条件函数"时，**要把它的阈值登记进 `EVENT_THRESHOLDS`**
（否则该条件的变化不会被当成事件切分，误差靠 0.25h 上限兜底）。
