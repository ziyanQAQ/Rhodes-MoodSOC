## 4. 特殊情况处理（需求文档第 3 条，务必遵守）

1. **红脸（心情 ≤ 0）**：该干员**所有心情类技能失效**（`_active(op)` 返回 `mood > 0`），
   但仍可继续工作，只是不再影响速率。
2. **心情钳位**：任何时刻心情 ∈ [0, 24]，积分/查询/模拟均通过 `clamp` 保证。
3. **菲亚梅塔独占**：宿舍中只要她"持有技能且未红脸"，回复**恒等于 2.0**，
   **不接受**宿舍基础回复和其它任何来源（`rules._dorm_ledger` 顶部短路 return）。
4. **冰酿分配**：0.8 总额**平均分给"心情未满（<24）"的宿舍成员**；满心情者不分；
   宿舍无人未满时该项为 0（不会除以零）。
5. **消除类（槐琥 / 令）**：只消除目标干员 **"自身技能"（self_consume）的正负影响**；
   中枢减免、设施级技能**不受影响**；令额外限定 `trait="岁"`。
6. **中枢减免"取最高" vs 设施技能"求和"**：`cc_reduce` 按"不同干员取最高"（每名干员自身技能先求和，再跨干员取 max）；`facility_consume` 是"全体求和"。两者别搞混。
7. **消耗不为负**：`compute_consumption` 末尾 `max(0, total)`；"净回复"统一由 `compute_recovery` 表达。
8. **目标干员不在任何设施**：净速率视为 0（不消耗也不回复）。
9. **未知干员**：`compute_net_rate` / `remaining_*` / `evaluate` / `simulate` 抛 `KeyError`。
10. **显示取整**：`report._fmt_mood` 同时给出游戏内**向下取整**值 + 真实小数（如 `12（实际 12.700）`）。
11. **巫恋「低语」= 全体含自身**（用户拍板）：官方原文「…同时**全体**心情每小时消耗+0.25」，
    故归 `FACILITY_CONSUME`（`M05`，`include_self=true`），不再是 `ROOM_OTHERS_CONSUME`。
    `M06`/`ROOM_OTHERS_CONSUME` 保留但**当前无使用者**。
12. **玛恩纳扩散**：官方术语 `cc.c.skill` 的 15 条白名单中枢回复技能，在玛恩纳进驻中枢时
    额外作用于 room2；提供者红脸则扩散失效（`rules._spread_active` / `_reaches`）。
13. **room2 三条取最高**：官方术语 `cc.c.sui2_1`。`max_group=room2_recover` 的技能
    **同干员内求和、跨干员取最高**（由 `MoodLedger.total()` 完成）。
14. **设施分三类**：常规生产设施 1.0/h（制造/贸易/发电/办公/会客/中枢）、
    **挂件位 0/h（加工站、训练室）**、不进模型 0/h（宿舍只回复、活动室不视作入住在基建内）。
    按 `config.base_consumption(ftype)`。旧实现只排除宿舍、其余一律 1.0，
    把加工站与训练室算成 0.75/h（已修）。
15. **加工站 / 训练室是「挂件位」，不计算心情消耗**（用户拍板口径）：
    > 加工站、训练室的教练位的作用只是用来放挂件干员，即本身并没有什么技能，
    > 但**只要在基建内（不包含副手及活动室使用者）**，就可以为其他干员提供效果服务，
    > 所以不需要计算这两个的心情消耗。
    - 用法是**放挂件**：挂件本身没有与所在设施相关的心情技能，被放进来的唯一目的是
      「**人在基建内**」，好让**别人**的计数类技能数到它（`models.BaseLayout.base_operators`，
      **不含副手与活动室使用者**）。
    - 0 消耗 ⇒ 挂件永不红脸 ⇒ 它提供的"在场"效果**持续生效**，这正是挂件的意义。
    - 与 docx 第 4 段「工作时基础消耗 1 点/时」**不冲突**：那说的是常规生产设施的
      **上岗生产**消耗，挂件位不属于上岗生产。
    - ⚠️ **推论**：9 条「进驻训练室协助位时，心情每小时消耗 **+1**」的训练室技能**不生效**
      （`train_cost&profession[140/320/340/350/360/380]`、`train_spd_bd[000]`、
      `train_spd_doubleProf3[100]`、`train_spd_power_down[000]`）。已从 `moods_skills.txt` 撤出，
      `skills_registry.txt` 保留登记与原因。
16. **变量（中间货币）已纳入模型**（P3）：官方术语表 `cc.bd*` 共 26 种，其中
    **人间烟火 / 热情值 / 无声共鸣** 会影响心情，另有派生变量 **心情落差**（= 24 − 当前心情）。
    `mood_soc/variables.py` 的 `VariableLedger` + `resources/variable_producers.txt` 负责产出，
    技能用 `var_name`/`var_per`（每有 N 点 → 值 × floor(变量/N)）或 `var_min`（≥ N 才生效）消费。
    口径：变量是**基建级**值；产出者要①在布局里②已解锁③未红脸④条件成立（如夕「不以物喜」要求自身心情 < 12）。
    ⚠️ 变量与心情存在**单向快照依赖**（先用当前心情算变量，再用变量算速率）；
    `simulate` 每步重算故能跟上变化。
    ⚠️ 场景/导入文件还可以给一份**初始值**（`initial_global`）——它与产出值**相加**，
    语义是"进场时就有的量"（别的求解器把这类量当输入）。见 `04-特殊机制.md` 建模假设 11。
17. **变量产出者的持有者从 `operators.txt` 全量取**，不能从 `DEFAULT_OPERATORS`（仅心情技能）取——
    产出者里有不少是纯变量技能（祐天寺若麦「勤学苦练」、塑心「无声共鸣」），
    用后者会一个持有者都找不到（实测踩过这个坑）。
18. **「同种效果取最高」的粒度是「技能」不是「分句」**（P4a 修正）：
    上游原文写「…额外 +N 恢复效果（**叠加后的最终值**同种效果取最高）」
    → 同一技能的「基础 + 每有 N 额外」两个分句要**先求和**，再与其他技能取最高。
    `ledger.MoodLedger.total()` 的 `SAME_KIND_MAX` 现在按「**持有者 + skill_id**」先聚合分句、再取最高。
    旧实现按单个分句取 max，会丢掉基础分句（死前必做清单 Lv5 → 0.15 而非 0.25）。
19. **可数条件（`basis`）已纳入模型**（P4a）：12 条「每有 N 个什么」的子句从 `hold` 转 `apply`
    （柔和微光 每有 1 间发电站 / 死前必做清单 宿舍每级 / 倾谈者 每有 1 名未满干员 /
    独处·赋格融汇 每有 1 名其他干员 / 寻同路人·无瑕心 每个招募位 / 潮汐守望 每个深海猎人（含自身，见第 23 条） /
    救援队·保证体力 每个招募位；挑大梁的「每有黑钢国际」修饰的是**生产力**，心情 -0.15 无条件）。
    基准实现见 `variables.basis_count(world, basis, facility, op)`。
20. **β 替换链的单位是 `skill_id`，不是 `skill_id#clause`**（P4a 修 bug）：
    旧实现把每个分句当成链上一环，导致「基础 + 每有 N 额外」结构里额外分句把自己的基础分句
    "替换"掉（实测 6 例：响石 0.15 / 铎铃 万里传书 -0.1 / 刺玫 0.15 / 波卜 0.2 / 流明 0.1 / 隐德来希 0.1 全丢）。
    `SkillEquip.replaces` 现在存 **skill_id**，`rules._active_skill_ids` 按 `base_skill_id` 整条剔除。
    ⚠️ 改动 `replaces` 语义后务必跑全量测试。

    （资深料理人会无条件对所有人 +0.15；互为半身会无条件消除所有人）。

25. **`M07b`（自身回复·非宿舍）曾被完全忽略**：`_work_ledger` 只处理中枢的 `CC_RECOVER`，
    从不处理干员自己的 `DORM_SELF` 技能，所以潮汐守望的「反之」分支从未被求值。

26. **布局是一等公民**（多房间）：`Facility.operators` 是进驻者（占位/耗心情/算"处于工作状态"），
    `Facility.deputies` 是副手（不占位、不耗心情、被「不包含副手」类技能排除，29 条 buff 用到）；
    **活动室不纳入基建心情模型**——上游明确「活动室虽然有氛围提供，但是不能提供心情回复，
    **也不视作入住在基建内**」，故 `FacilityType.PRIVATE` 只为**解析输入**与
    **把活动室使用者排除出基建计数**而存在，本身不参与任何心情计算
    （其使用者默认被 `base_operators()` 排除，23 条 buff 用到）。
    `get_facility()` 只返回第一个同类型设施，多房间请用 `of_type()` / `count_of_type()`。
27. **`M09` 定向加成「如果目标是 X，则恢复效果额外 +0.45」已实现**（P5）：
    上游 6 条 `dorm_rec_single*` 写的是「…恢复 +0.55（同种效果取最高），**如果目标是 X，
    则恢复效果额外 +0.45**」。本地 CSV 当初挤成一行、加成丢失；现按上游原文**手工补 `clause#2`**
    （value=450，与 `#1` 同 `skill_id`），条件见 `generate_skills_data.CLAUSE_COND`：
    沏茶→锡兰、烤肉大师→嘉维尔、毒剂师之友→蓝毒（用 **`_cond_target_is`**，点名具体干员）；
    降生于冰寒→萨米、圣城趣事通→拉特兰、狩猎好帮手→怪物猎人小队/泡影国狩猎小队
    （用 **`_cond_target_in_faction`**，可传多个 = 并集）。
    两条配套铁律：
    - **「同种效果取最高」的单位是技能（含各分句），不是分句**（同 §4.18）。`_single_recovery`
      旧实现按单条分句取 `max` 会吃掉 +0.45；现改为记进 `MoodLedger` 后调用
      **`MoodLedger.same_kind_winner(bucket, group)`** 取获胜**技能实例**（0.55+0.45=1.00）。
      该方法与 `total()` 的 `SAME_KIND_MAX` 同源，规则只有一份。
    - **点名要过守卫**：`check_faction_refs()` 现在会扫 `CLAUSE_COND` 里的字符串字面量，
      阵营名与干员名对不上直接报错（干员名册取 `resources/operators.txt` **全量**，
      不能用 `DEFAULT_OPERATORS`——锡兰/嘉维尔/蓝毒都是只有生产/训练技能的干员）。
    ⚠️ 遗留简化：`_single_recovery` 的**目标锁定**是全局一名受益者（§8.5），
    所以「毒剂师之友」上游没写「除自身以外」、深靛本可自指，本模型仍把她排除在候选外。

29. **进驻事件（M15a）已实现**：**患难之交**（菲亚梅塔）。上游原文（`buffs["dorm_exchangeAp[000]"]`）：
    「进驻宿舍时，**如果自身为满心情**，则与当前宿舍**前一位进驻**的干员互换心情」。
    它不是"每小时 ±N 点"而是**进驻那一刻的状态跳变**，因此：
    - **不进速率流水账、不进时间积分**，而是走显式 API **`rules.apply_entry_events(...)`**
      （CLI：`main.py --entry-events`），事件本身记为 `Bucket.EVENT` 展示用。
    - ⚠️ **会就地修改** `world` 的干员心情；`evaluate` / `evaluate_base` **不**自动调用
      （它是布局初始化语义，不是速率语义）。重复调用幂等（换完她就不再满心情）。
    - 「前一位进驻」= `Facility.operators[idx-1]`——该列表**本来就是进驻顺序**，无需新结构。
      条件挂 `CLAUSE_COND` 的 `_cond_self_full_mood`；调度按 `template_id == "M15a"`
      （`rules._template_skills`，与 §4.25 的 M07b 同一约定）。详见 `documents/05-技能分类大纲.md` §5.8。
    - **换不换 / 在哪换 / 换谁 / 换完怎么放 / 要不要等她都可配**（P5e，用户需求扩展）：
      签名 `apply_entry_events(world, swap_with=None, enabled=None, scope=None, restore_back=None)`，
      场景 JSON 顶层 `entry_events`（宽松写法：`true`/`false`/`"某人"`/`"anywhere": true`）
      → 解析进 `models.EntryEventConfig`，挂在 `BaseLayout.entry_events` 上随布局一起走。

      | 字段 / 参数 | 默认 | 含义 |
      |---|---|---|
      | `scope` | `"dorm"` | `"anywhere"` = **基建任意位置**（任何设施上的干员都能换） |
      | `swap_with` | 省略 | 人名 = 指定；`"any"`/`"任意"`/`"最累"` = **自动挑全基建心情最低的那位**；省略（`anywhere` 时）同样走自动挑 |
      | `restore_back` | `True` | `True` = 把被换满的那位**换回原位**（两人都留在自己岗位，只换心情）；`False` = **位置也一起互换**（`_swap_positions`）。⚠️ 界面已收掉这个选项，固定按 `True` 走 |
      | `force` | 旧字段 | 兼容保留（`true`→`wait`、`false`→`full`） |
      | **`when`** | `"immediate"` | **她自己的心情门槛**：`immediate`（**不看她的心情，立刻换**，引擎默认）/ `wait`（等她回满再换）/ `full`（判定时没满就不换，游戏原文口径）。⚠️ 引擎默认仍是 `immediate`（向后兼容），**界面只写 `wait`/`full`**（见下面"界面＝一个总开关 + 一张表"） |
      | `enabled` | `None` | 三态；显式参数 > JSON > 默认结算 |
      | **`per_shift`** | `[]` | **按班次覆盖**（`models.EntryShiftOverride`）：3 班 12/6/6 就可以"第 1 班换给巫恋、第 2 班自动挑最累的、第 3 班不用"；列表＝按班次位置，字典＝按序号或**班次名**定位；**逐字段继承**（没写的沿用全局），写 `null`/`""` = 明确清空该字段 |

      **强制交换（默认口径，用户拍板）**：**「对方心情是多少」不构成任何限制**——
      只要换了就一定照换，**不再因为"双方心情相同"而跳过**：哪怕两边都是 24，事件照记、
      `restore_back=False` 时位置照换（标记里注明"数值不变"）。
      剩下唯一可配的**是"她自己的心情门槛"**，由 `when` 决定：

      | `when` | 她没满心情时 | 谁在用 |
      |---|---|---|
      | `"immediate"` | **不看她的心情，立刻换**（最强强制） | 仅 JSON / API / CLI（`main.py --entry-events`）；**界面不再提供这一档** |
      | `"wait"` | **等她回满心情再换**（带时间，只在排班模拟里生效） | 界面：勾了「③ 强制切换」 |
      | `"full"` | **判定时没满就不换**（游戏原文口径） | 界面：不勾「③ 强制切换」 |

      同一份布局快照只结算一次（`Operator.entry_swapped` 标记），故重复调用幂等、
      不会来回换；排班模拟里每个班次是一份**独立副本**，而那份副本会被**跨周期复用**，
      所以模拟器在每次"班次开始"前调用 `rules.reset_entry_events(world)` 把标记归位——
      语义上"**再次进驻 = 新的进驻瞬间，要重新判定**"（`main.py --entry-events` 那样只跑一次的
      调用不需要它，幂等保证不变）。⚠️ 曾经漏了这一步：周期数 ≥ 2 时第 2 个周期起
      换心情一次都不触发（多周期漏算的 bug，已修）。

      ⚠️ **同一族的两条"副本时效性"约定**（都写在 `ui.schedule.simulate_schedule` 里，
      回归用例见 `tests/test_ui_schedule_blackbox.py::Test副本状态时效性`）：
      ① 每次算速率之前必须 `_sync_moods(world, moods)` 把**真实心情**写进副本——否则
      依赖心情的条件技能（宿舍单体回复选谁、池分配、自身条件…）会拿旧值判断、速率算错
      （示例排班恰好对心情不敏感，看不出差别）；
      ② `restore_back=False`（位置也一起互换）时，**每个班次开始都要从计划重建那一班副本**——
      否则第 2 个周期她带着上一轮换过的位置、可能不在宿舍里，「进驻宿舍时」直接不成立、静默不换。

      优先级：**显式参数 > JSON > 默认**；按班次再"逐字段覆盖全局"（界面传的 `per_shift` > JSON 的）。
      指定的对象不在允许范围内时不换，但记一条 `Bucket.EVENT`（group=`entry_swap_skipped`）说明原因。
      `find_entry_target(world, holder, facility, swap_with, scope)` 可单独用来预览"会换谁"，
      `entry_target_kind(swap_with, scope)` 是**口径判定唯一来源**（行为与文案都从它取，
      曾经文案单独判断 `swap_with`，出现"实际自动挑、文案写成前一位进驻"），
      `resolve_entry_config(cfg, index, 班次名, overrides)` 合并出"这一班的有效配置"，
      `entry_event_holders(world)` 列出"谁会触发"（界面用它们做候选与提示）。
      ⚠️ 触发者仍须**进驻宿舍**（技能原文是「进驻宿舍时」）；"任意位置"放宽的是**目标**的范围。

      **界面＝一个总开关 + 一张"每班一行"的表**（`ui/dialogs.EntryEventDialog`，P5f 收过两次）：
      ① 开启心情交换 → `enabled`；② 表格每行 `用 / 换谁 / 强制切换` →
      `per_shift[key]` 的 `enabled` / `swap_with`+`scope` / `when`（换谁**自带范围**：
      前一位进驻＝同宿舍、最累的/具体干员＝基建任意位置）。
      **第 1 个勾着「用」的班次那一行充当全局默认**（写进 `swap_with`/`scope`/`when`），
      其余班次**只有和它不同**（含"这一班不用"）才写一条覆盖 ⇒ 三班设置相同时 `per_shift` 为空、
      行为与"没有这张表"逐位相同。
      为什么不做"全局值 + 例外"两层：真正逐班的东西本来就是这一整组，
      分两层会让人设置时在脑子里做三次映射（旧版 ①②③ + ④ + 折叠高级区就是那样）。
      「位置也一起互换」被收掉，界面**固定 `restore_back=True`**（只换心情、两人留原位；
      JSON/API 里写 `false` 仍有效，只是界面会按自己的口径覆盖它）。
30. **「闲置入宿」：把未满心情的闲置干员安排进宿舍**（P6，用户需求；与第 29 条同一层——
     它是**班次开始时的布局事件**，不改"每小时速率"公式）：

     | 步骤 | 规则 |
     |---|---|
     | 候选 | **不在宿舍** 且 **不消耗心情** 且 **心情 < 24**：挂件位（加工站/训练室）与本班**未排班**的人都算；正在上班的人不动、心情满的人不用动 |
     | 顺序 | 按**心情从低到高**（最需要恢复的先安排）；**每个人**都用"那一刻"的实时心情重判一遍 |
     | **①** | 任一间宿舍**还有未占满的位次** → **直接住进去**（**有空位就不换人**，哪怕别处有人满心情） |
     | **②** | 宿舍**全满** → 换「宿舍 **#4 → #3 → #2** 的**第 2~5 位**」里**实时心情已满**的那位 |
     | **③** | ② 找不到 → 只在**白板**（**不属于任何已记录阵营**的干员）里挑实时满心情的那位；**满 24 的菲亚梅塔也在此列**（见下表"例外"）；都没有 → 看 ④ |
     | **④** | ②③ 都挑不到 → **你点名了（`swap_with`）就与那位互换**（**主动换**，见下）；**没点名**则与宿舍里**心情最高**的**白板**互换（**不限 24**，例：最高只有 21 就跟 21 那位换）；**连白板都没有**才"这一位不动"，记 `idle_to_dorm_skipped` |
     | 指定宿舍 | `dorm=序号`（界面写作「宿舍01」）**优先于上面全部**：放进那间的空位、**不动任何人**；那间满了 / 不存在 → **跳过这一位**（不退回自动） |

     **同优先级内的顺序是「优先 4、最后 1」**（用户口径）：
     宿舍之间 `#4 → #3 → #2 → #1`（不足 4 间时自动前移：3 间 → #3 → #2 → #1）；
     同一宿舍内 **第 2 位 → 第 5 位 → 第 1 位**（位次 1 只在③兜底时轮到）。
     ⚠️ 宿舍序号取自**布局里未被排序的原始顺序**（第几间宿舍，与界面「宿舍NN」一致）——
     曾经拿"排序后的下标"当序号，于是"优先 #4"挑中的其实是布局里的第 1 间。

     **③ 的例外：满 24 的菲亚梅塔**（2026-09 用户裁决，`rules.TIER3_EXTRA_NAMES`）——
     她的价值全在「患难之交」（M15a）：**进驻宿舍那一刻**把心情换给上一位，**满 24 就够、
     不靠"待在宿舍里"**；她「自律」（M14）又会自己回满。所以满心情时把她当"备用容量"换出去
     **不亏**：③ 放行她（"白板"与"自回型"两道门**同时**为她让开），但仍要求**满 24**。
     ⚠️ 名字写死（当前 M15a 只有她一个持有者）；只放行她一个，**别的自回型/有阵营的人照旧不动**。

     **三条"谁可以被换出"的门**（不改"自动路径（②③）必须满 24"这个前提）：

     | 门 | 判据 | 为什么 |
     |---|---|---|
     | **白板**（②③④ 都适用，③ 的例外见上） | `_factionless(op)`：`OPERATOR_FACTIONS`（`data/factions.txt` + 人工补充表）里**没有她** | 白板没有阵营联动技能，换出去不会连带打断别人的阵营类加成；**有阵营的人优先留在宿舍** |
     | **自回型**（②③ 都适用，③ 的例外除外） | `_self_recovering_in_dorm(op)`：有 `M10` 宿舍自身回复技能（如菲亚梅塔「自律」+2/h 独占、缪尔赛思「天生丽质」+0.55） | 这类人在宿舍里**自己就能回满**，当作"备用容量"换出去等于白丢一份恢复能力，而且她换出去后心情成一条平线（看起来像"心情卡住"的 bug —— 实测踩过） |
     | **挂件**（②③④ 都适用；**点名不受限**） | `_is_pendant(world, name, memo)`：**把她从宿舍摘掉 → 全基建有人的净速率变差**（消耗上升 / 回复下降）；另含"位置挂件"（加工站 / 训练室入驻者、副手） | 用户口径：**"挂件指的就是有阵营效果，或者她在不在宿舍会影响其他干员的技能"**。这类人一走别人就要吃亏 —— 给别人群体/定向回复（如阿米娅「小提琴独奏」+0.15/h）、让别人"宿舍内每有 1 名干员"类条件/中间货币成立（热情值 · 人间烟火 · 无声共鸣）、给点名目标加成… |

     ⚠️ **挂件判据只看"变差"这一侧**：把她摘掉后有人的净速率**变大**才算挂件。
     反过来"她走了别人反而分得更多"（冰酿的池分摊少一个人分）**不算** —— 那是她占便宜，不是她有价值。
     ⚠️ 判据跑在**浅拷贝探针**上（`_world_without`），**原世界一个字节都不改**：调用点正遍历
     `dorm.operators`，就地增删太脆弱。同一个班次内按名字缓存（`memo`），换过人后清空。
     ⚠️ 实测成本：一次判据 ≈ 两遍全基建净速率（示例 47 人 ≈ 2.2ms），且**只在候选身上按需跑**。

     **④ 的两种动作**：

     1. **默认兜底（没点名时）**：与宿舍里**心情最高**的白板互换 —— **不限 24**
        （例：宿舍里最高只有 21，就跟 21 那位换；"心情从高到低"＝换出损失最小的先换，
        同心情按名字，宿舍顺序只用于同分）。仍然守白板 / 自回型 / 挂件三道门；
        这样的白板一个都没有 → 才"这一位不动"。
        为什么不再"直接不动"（2026-09 用户口径）：④ 的用处正是"让别人进来恢复"，
        只要挑的是**不亏的人**（白板、不靠宿舍自回、不是挂件），换出去就是净赚。
     2. **点名＝"主动换"（`swap_with`）**：②③ 都挑不到人时，**优先用你点名的那位**互换
        （比默认兜底更明确，所以排在它前面）。此时：
        - **不要求她满 24**（可以选宿舍里心情没满的人）—— 代价由点名的人自己承担；
        - 也不受上面那三道门限制（"只换白板 / 自回型不换出 / 不换挂件"只约束**自动**挑人）；
        - 仍要求她**此刻真的在某一间宿舍里**（不在宿舍 / 本班次已被换出 → 这一班不动）；
        - 且要过下面那道**心情闸**。
        ⚠️ **它只在 ④ 生效**：①②③ 能挑到人时，点名**不生效**（免得"我点名了"把自动规则整个顶掉）。
        界面上「换谁」下拉因此列的是**宿舍里的所有人**（标签带心情，如 `巫恋 23.4`）。

     **心情闸（用户口径）：目标的实时心情必须严格大于候选** ——
     "换的时候比较此干员与目标干员的心情，如果目标干员心情大于此干员才交换"。
     换人本质是"拿一个人的宿舍位子换给另一个人"：目标不比候选更满时，等于把**更需要恢复的那位
     挤出去**、床位给了不那么需要的候选，净亏 ⇒ **这一班不动**（记 `idle_to_dorm_skipped`，
     说明里写出两边心情）。要点：

     - 位置在"**挑完人、真正换之前**"统一判一次 ⇒ **②③ 天然满足**（它们要求目标实时满 24，
      而候选按定义 < 24），所以这条**实际只在 ④ 生效**（点名与默认兜底都算）；
     - **严格大于**：两边一模一样时换不换对基地总量没区别，不换更保守；
     - 对默认兜底还有一层含义：它挑的本来就是"宿舍里心情最高的白板"，连她都不比候选更满，
       **其余白板更不可能满足** ⇒ 直接判"不动"。
     - ⚠️ 这道闸**不是"一律更好"**：它保住了宿舍里心情更低的人，但也会让一位心情很高的闲置者
       进不去（示例排班里 幽灵鲨 20.1 就因此留在外面）。

     > ⚠️ 那三道门 + 心情闸的**代价**：宿舍能接纳的闲置者变少。示例排班（`MAA_SAMPLE`，
     > 4 间宿舍全满、20 位住客里没有白板满心情）在 2026-09 之前实测**一次都不换**；
     > 现在 ③ 放行满 24 的菲亚梅塔 ⇒ 12h 与 18h 各有一位闲置者（虎狼丸 / 地灵）与她互换进宿舍，
     > 而**其余有阵营的人与另一个自回型（缪尔赛思）照旧不动**。
     > ④ 的默认兜底在示例排班里也只在**白板**里挑，且要过心情闸：实测 t=18 共 4 条结算 ——
     > 承曦格雷伊 10.5 ↔ 可露希尔 20.1、跃跃 10.5 ↔ 清流 12.3 **换**；
     > 梅 19.5 ↔ 温蒂 12.3、幽灵鲨 20.1 ↔ 温蒂 12.3 **被心情闸拦下**（目标更不满）。
     > 结果：温蒂留在宿舍从 12.3 回满到 **24**，幽灵鲨留在外面（**20.1**，原来是与"刚被梅换进去的
     > 那位"换，现在连那条空转也一起没了）。
     > 示例里被行为判据判成挂件的只有三处：段1 宿舍#1 的**缪尔赛思**（+0.1/h 群体回复，且她本来
     > 就是自回型）、段1 宿舍#2 的**阿米娅**（+0.15/h 群体回复）、段2 宿舍#1 的**虎狼丸**
     > （她正是 t=12 被换进去的那位）—— 三处都不在"被挑出来换出"的候选位上。

     被换出的那位（实时满心情）**离开宿舍 → 既不工作也不在宿舍**（心情不变，反正已经满了）；
     进来的人**接替他被换出的那个位次**（不是排到末尾），这样"换的是第 2~5 位"才名副其实。

     ⚠️ **位次（`slot`）本身没有机制差异**：宿舍回复只看等级/氛围/人数，且 `Facility.operators`
     是紧凑列表（不表示"洞"）。但**位次决定"谁更容易被挑中"**（②只吃第 2~5 位），所以
     显式写 `slot` 时若与"最靠前的空位"不一致，会在说明里注明"按第 N 位放"。

     - 签名：`rules.apply_idle_to_dorm(world, enabled=None, idle=None, only=None, swap_with=None, scope=None)`。
       `idle`＝本班**未排班**的干员 `{名字: 心情}`（他们不在布局里，心情只能由调用方给；
       给了才会被当候选，引擎侧用 `scenario.build_operator` 按名字造出干员放进宿舍）；
       `only`＝只处理这些人；`swap_with`＝`{候选名: 指定对象}`；
       `scope`＝`(周期序号, 班次序号)`（1 基）——逐人设置按它取**最具体**的那一条。
       规则常量：`rules.DORM_PREFERRED_RANGE = (2, 3, 4)`、`rules.DORM_PREFERRED_SLOTS = (2, 3, 4, 5)`；
       三道门：`rules._factionless(op)`（白板）、`rules._self_recovering_in_dorm(op)`（自回型）、
       `rules._is_pendant(world, name, memo)`（挂件）；再加**心情闸**（目标心情严格大于候选，
       在 `apply_idle_to_dorm` 里统一判）。
     - 配置：JSON 顶层 `idle_to_dorm`（`models.IdleToDormConfig`）——
       `enabled` **默认 `true`（开）**：没写这个键 ⇒ **结算**（用户口径"闲置入宿默认是开启的"）；
       **显式写 `false` ⇒ 关**（显式配置永远优先）。三处默认值统一：
       `IdleToDormConfig.enabled=True`（`mood_soc/models.py`）、`Session.idle_to_dorm=True`
       （`store/session.py`）、`simulate_schedule(..., idle_to_dorm=True)`（`store/schedule.py`）、
       `apply_idle_to_dorm(world)` 的 `enabled=None` 也按开（`mood_soc/rules.py`）；
       命令行多了一个 `--no-idle-to-dorm`（`--idle-to-dorm` 变成"压过 JSON 里的 false"）。
       `per_operator` 逐人/逐次写 `参与 / 目标`（`false` = 不参与）；
       目标有**两类**：`swap_with`（与某位满心情的宿舍干员互换）或 `dorm`（1 基宿舍序号 = 放进那间空位）。
       数组写法还可带 `cycle`/`shift` **限定只在哪几次生效**：
       `[{"name": "虎狼丸", "shift": 3, "swap_with": "甲"}, {"name": "地灵", "shift": 2, "dorm": 2}]`
       （优先级：周期×班次 > 只写一个 > 全局）。
       **界面传的逐次设置 > JSON 的**（与进驻事件同一约定）。
     - ⚠️ **为什么要按 (周期, 班次) 细分**：心情跨班跨周期连续 ⇒
       "这一刻谁没满、谁在宿舍且满"**每次都不同**。实测示例排班（`cycles=3`）闲置入宿事件分别落在
       周期 1 的 12h/18h、周期 2 的 24h/42h、周期 3 的 66h，候选与可交换对象都不是同一批
       （第 2 周期的第 1 班里 地灵 已经掉到 7.5、而第 1 周期同一班根本没人需要入宿）。
     - **指定了对象就严格按指定**：那一班他不在宿舍 / 心情不是满的 → **跳过这一位**（不退回自动）。
       界面上的「换谁」下拉因此**只列当前在宿舍且心情满的人**，不给无效选项。
     - **实时性**（用户强调的重点）：触发时机是**每个班次开始时**，而且
       ① 先把**进驻事件（换心情）**结算完 → ② `_read_back_moods` 把换后的心情读回 →
       ③ 才判闲置入宿。所以判定看到的是"换完之后"的实时心情，不是进入班次时的旧值。
       同一次结算里逐个候选处理，**每换一个人，"还有没有空位 / 还有谁满心情"都按最新布局重算**。
       ⚠️ 候选里会**剔除已经不在宿舍里的人**（`world.facility_of` 校验）：跑过一整轮模拟的副本里
       可能残留"早先被换出去过"的陈旧成员对象，只看成员列表会挑到一个不在宿舍的人。
       CLI：`main.py` **默认就结算**（只在当前这一份布局上结算一次；多班轮换要逐班结算）；
       `--idle-to-dorm` = 压过 JSON 里显式写的 `false`，`--no-idle-to-dorm` = 强制关。
     - ⚠️ 它是**布局改动**，会连带影响别人的速率（宿舍回复按人数/氛围、被换出的人不再给同宿舍提供效果）
       ——这是模型该有的行为，不是 bug。事件记在 `Bucket.EVENT`（group=`idle_to_dorm`），
       界面曲线图用绿色「宿」标记标出。
     - ⚠️ **它改的是"模拟副本"，不是排班快照**：引擎每段用一份**布局副本**
        （`store/schedule.py: pristine` → 段首 `copy.deepcopy`），换人只改副本。
        所以"她在哪"有两份账，界面**显示以引擎为准**（`Trajectory.world_at(t)`）——
        被换出的人在看板/全员一览/对点查询/「干员与心情」位置列里都显示为**不在基建**，
        那行还会打 `⇄` 并写明`本班被闲置入宿换出（快照写 …）`。见 `10-图形界面.md` §5 第 21 条。
     - ⚠️ **每段（含每个周期）都从"未动过的计划副本"重建**（2026-09 修，两次）：
       ① 先是**段内快照**（P7）：只记引用的话，整轮跑完后副本只剩"最后一次跑这一班"的样子，
       `world_at(t)` 会在第 1/2 周期给出第 N 周期的排布（实测：第 1 周期宿舍 2 人 vs 第 2 周期 5 人）；
       ② 再是**段首重建**：副本被就地改（闲置入宿换人 / `restore_back=False` 的位置也互换），
       而 `worlds[idx]` 原本**跨班次、跨周期复用** ⇒ 第 1 周期把她换出去之后，**第 2/3 周期的
       同一班开局就没有她：既不重判心情、也没有任何事件**（用户报过"菲亚梅塔 20.4 却显示被闲置
       入宿换出"——那次换出其实是第 1 周期用 24 判的旧决定）。现在每段都重建：**位置**回排班原样、
       当班**按当时心情**重新判定；**心情仍跨周期连续**（在 `moods` 里，与副本无关）。
       代价 = 每段一次深拷贝（示例 ≈0.35ms，7 周期 21 段 ≈ 7ms）。
       回归：`test_跨周期位置复位_每周期都重新判定`（含"快照里有、引擎那份没有的人当班必须有
       换人事件解释"这条不变式）。API 的 `layout_at` 读的就是同一份段首快照。

35. **心情跨阈值时的「吸附」必须**就地**做，不能留到积分之后**（P7 修；曾把曲线整段压平）：
    事件驱动积分在"心情正好跨过 0/12/18/20/24 这些阈值"时把值**精确吸附**到阈值上，
    免得 `dt = (m−h)/r` 的除不尽留下 `16.19999999999999999999999999` 这种尾巴。
    - ⚠️ **吸附表是在积分「之后」应用的**，而那一刻 `nxt` 可能已经过去了一整个
      `MAX_SEGMENT_HOURS`（0.25h）——如果这个人只差末位舍入就跨过阈值（1e-26），
      积分早已把它推过阈值，再"吸附"回去等于**把它往回拽**，白扣掉 `|速率| × 0.25h` 的心情。
    - 实测（示例排班 `resources/arknights-infra-schedule-maa.json` 第 2 班宿舍段）：
      同宿舍 **8 名干员**（卡夫卡 / 娜斯提 / 水月 / 褐果 / 炎熔 / 伺夜 / 但书 / 空弦）在

      **把步长调到 0.05h 就全对** —— 步长不该影响结果，所以那是 bug 不是口径。
    - 修法（`store/schedule.py: _next_event`）：只差 `MIN_EVENT_GAP` 就跨过阈值的人
      **当场吸附**并把名单报给调用方（`snapped`）去**重算速率**；吸附表 `snaps` 只留
      "正好在**本段末尾**跨过"的人，并在**同一时刻**用 `setdefault` 合并（原先会互相顶掉）。
    - 回归：`tests/test_ui_schedule_blackbox.py::Test阈值吸附` —— 三条：解析值（宿舍回复段
      卡夫卡 13:12 = 21.0）、同宿舍 8 人阈值处不许有平台、**步长 0.25h 与 0.001h 的曲线必须一致**。
## 8. 关键"建模假设 / 近似"（不要当 bug 去"修复"）

文档未给出精确数值或机制时，代码做了显式简化并在注释中声明。改动前先确认是否要推翻这些假设：

1. **中枢全局减免线性折算**：文档只给"放满 5 人 = 0.25"一个锚点，代码按 `(人数/5)×0.25` 线性折算（`config.cc_reduction`）。若游戏真实规则是阶梯式，需改这里。
2. **条件槽空 → `partial`（保留效果骨架）**：模板化后不再"整条丢弃"。约 74 个子句的条件是
   MAA 占位符 / per-count 倍率 / 资源计数 / 截断文本，一律标 `partial=true`，并按
   `partial_mode` 处置：`apply`（子句 value 无条件成立 → 按骨架生效）/ `hold`（value 本身以缺失条件
   为前提 → 保留骨架但不生效，仍计入 `untranslated`）。判定：条件文本为空或含「额外」⇒ `apply`。
   实收：不生效子句 **37 → 31**（6 条本就正确的单体回复重新生效）；P3/P4a/P4b 又逐步降到 **3 条**
   （变量 + 可数基准 + 分支条件全部落地）。
   要彻底启用剩余子句，需实现 per-count 变量（人间烟火等）与 `COND_MARKERS` 扩充
   ——**这两项 P3/P4a 已完成，P5b 落地 M15a（患难之交），P5d 落地投资·α/β。
   至此 250 条 clause 里已无 `hold`（不生效）子句：不生效数 37 → 31 → 25 → 13 → 3 → 2 → **0**。**
3. **布局容量与房间数取自上游**：`config.FACILITY_MAX_COUNT`（`rooms[].maxCount`）与
   `FACILITY_SLOTS_BY_LEVEL`（`rooms[].phases[lv].maxStationedNum`）。`BaseLayout.validate()`
   只**报告**问题、不抛异常（历史场景可能刻意超容量）；`build_base_layout(validate=True)` 才抛。
4. **work_area 的 room1/room2 折算**：room2（"其他设施"）→ 全部 5 个工作设施；room1（"部分设施"，
   如玛恩纳"公事公办"）→ 发电/办公/会客。
5. **单体回复锁定规则简化**：文档的单体回复存在"进驻顺序/快照锁定"等复杂机制，代码简化为
   "锁定心情最低、未满、且非提供者的一名干员"（`rules._single_recovery`）。
6. **冰酿 0.8 分配语义**：按"心情未满成员平均分配"实现（`rules._dorm_ledger` 末尾的池分配段）。
7. **β 替换 α 的分组与粒度**：提升链按"同一干员 + 同一 skill_id 的 family"分组，
   组内按 (elite, level) 升序，`enhanced` 技能替换**前一个 skill_id**（整条，含全部分句）。
   family 取该技能**首个分句**的 family（同一技能的分句可能跨 family，如「挣脱」的 dorm_self / dorm_group）。

11. **变量初始值（`initial_global`）与"从布局推导"相加**（2026-09，配合导入 v4 蓝图）：
    本项目的变量默认是"数出布局里有哪些产出者"（`variables.collect_variables`），
    而别的工具（ArknightsInfraCalc-v3 的 `layout.scenario.initial_global`）把变量当**输入**给。
    两者语义不同但不能只留一个：放进 `BaseLayout.initial_variables`，与产出值**相加**。
    实测影响：`{"热情值": 40}` 会让丰川祥子「生活的重压」（需 热情值 ≥ 40，自身消耗 +0.05）
    在布局里没有任何热情值产出者时也生效。⚠️ 若某技能的真实口径是"只看产出"，
    将来要改成"以初始值为上限"之类的规则时，改的是这里。
12. **心情指定事件（锚点）是"人为调心情"，不是游戏机制**（2026-09，界面需求）：
    界面「干员与心情」允许指定"周期内某一刻某人心情是多少"（`ui.schedule.MoodSetEvent`），
    引擎在那一刻把她的 SOC **直接置为**该值、之后照常积分（同刻跳变）。
    它对应的是"那一刻她吃了体力药 / 刚被换下来休息"这类外部干预，
    游戏里并不存在"把心情设成 X"的机制——所以它**只是一个假设条件**：
    带锚点的"能不能永动"结论，前提就是"那一刻她确实有这么多心情"。
    ⚠️ 同一时刻若与进驻事件（第 29 条）/ 闲置入宿（第 30 条）重合，**锚点最后生效**
    （显式设定优先于机制推算）。多周期时**只对指定的那个周期生效**。
