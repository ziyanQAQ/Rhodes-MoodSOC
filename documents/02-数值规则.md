## 2. 数学建模：心情 ⇔ 电池

| 电池概念 | 心情概念 | 本项目的常量/变量 |
|---|---|---|
| 容量 C | 心情上限 | `MOOD_MAX = Decimal("24")` |
| 空电量 | 红脸（技能失效） | `MOOD_MIN = Decimal("0")` |
| 荷电状态 SOC | 当前心情 | `Operator.mood`（0~24，可含小数） |
| 放电电流 | 净心情消耗速率 | `net_rate = I`（点/小时，>0 下降） |
| 充电电流 | 净心情回复速率 | `-I`（I<0 上升） |

**核心公式（安时积分 / 库仑计数）：**

```
                t
SOC(t) = SOC(t0) - ∫ I(τ) dτ        其中  I(τ) = 消耗速率(τ) - 回复速率(τ)
                t0
```

**离散化**（`simulator.py`）：`SOC[k+1] = clamp( SOC[k] - I[k] * Δt , 0 , 24 )`

**解析解**（时段内速率恒定、其余干员心情无限，`rules.py` 用）：
`剩余心情 = clamp( SOC0 - I * T , 0 , 24 )`（对应 `remaining_mood_after(world, name, T)`）。

⚠️「还能维持/恢复多久」= `sustain_hours`，有**两个入口**（最易写错）：`remaining_work_hours(world, name)`
从**当前（初始）心情**起算 → `SOC0 / I`；`evaluate(world, name, T)` 的 `sustain_hours` 先推进 T 小时再按净速率
符号取时长（工作 → `剩余心情 / net`、宿舍 → `(24-剩余心情)/(-net)`；`I=0` 为 Infinity / JSON `null`），
CLI 输出的是后者。

关键约定：
- **`I = 消耗 - 回复`**；`I>0` 下降（工作中）、`I<0` 上升（休息/空闲）、`I=0` 不变；心情**始终钳位 [0, 24]**。
- `sustain_hours` 返回 `Decimal('Infinity')`（即 `mood_soc.INF`）＝永续（净速率 ≤ 0）。

**积分之外的两类「时刻事件」**（都是**同刻跳变**，不是速率）：进驻事件 M15a（换心情）与**心情指定事件**
（`ui.schedule.MoodSetEvent`）——在 `(周期, 周期内时刻)` 把某人的 SOC **直接置为**给定值（钳位 [0,24]），
其后照常积分（`t < T` 正常积分 / `t = T` 置为 V / `t > T` 从 V 继续）。它是**人为假设**，不是游戏机制；
与进驻事件重合时**锚点最后生效**，多周期时**只对指定周期生效**（界面口径见 `documents/10-图形界面.md` §5 第 12 条）。

**精度策略（全程 `decimal.Decimal`）**：
- 常量在 `config.py` 用 `Decimal("0.1")` 这类字符串字面量定义，导入时设全局上下文（28 位有效数字 + ROUND_HALF_UP）。
- ⚠️ **上下文是「线程局部」的**：新线程拿到的是 Python 默认上下文（`prec=28`、`ROUND_HALF_EVEN`）⇒ 末位差
  1e-26 经阈值吸附放大成**事件时刻不同**（实测：52 名干员的轨迹上主线程与工作线程不一致）。故引擎入口
  （`store.schedule.simulate_schedule`、`mood_soc.rules.evaluate` / `evaluate_base`）都先调
  `config.use_project_decimal_context()`；回归 `tests/test_equivalence.py::Test线程与精度`，详见 `07-设计史.md`。
- 外部输入一律经 `battery.to_decimal()`——**必须走字符串，禁止 `Decimal(float)`**。
- `INF = Decimal('Infinity')`（`battery.py` 定义，`mood_soc` 顶层导出）＝"无限"；Decimal 的 `==` / `<=`
  是精确判断，无需容差。
- 唯一受控舍入在输出边界：`output.py` 按 6 位小数舍入成 JSON 数字（整数退化为 int），`Infinity` 输出 `null`。

### 3.1 心情消耗 `compute_consumption(world, op, facility)` → 结果 ≥ 0

```

       常规生产设施 1.0（制造/贸易/发电/办公/会客/中枢）；加工站 0、训练室 0（「挂件位」，见下）；
       宿舍 0、活动室 0
     - X          设施基础减免（仅 制造站/贸易站：按进驻人数 (n-1)×0.05，上限 0.1）
     - 中枢减免    控制中枢全局减免：(cc人数/5)×0.25（满员=0.25）
     ± 自身技能    self_consume（泡泡 -0.25、火神 α-0.15/β-0.25 等，全表见 §5.4）

     （存在"消除类"干员时"自身技能"一项清零，见 `04-特殊机制.md`）
最后： max(0, 上面结果)   —— 消耗不为负，负值一律走"回复"侧表达
```

### 3.2 心情回复 `compute_recovery(world, op, facility)`

> 消耗与回复都由同一套**流水账**（`rules.consume_ledger` / `recovery_ledger`）产出，再交
> `ledger.MoodLedger` 按轴 F 合成；查某人速率为何是这个值：`rules.mood_ledger(world, "泡泡").explain()`。

**工作设施内**（非宿舍）：来自中枢内干员的 `cc_recover` 技能，按**三条规则**合成（轴 F）：
- **F1 求和**：不同来源默认相加。
- **F3 跨干员取最高**（`max_group=room2_recover`）：官方术语 `cc.c.sui2_1` 规定 公事公办 / 孤光共照 /
  巴别塔之帜 的 room2 恢复值**取最高**——同干员各 clause 先求和，再跨干员取 max。
- **M02c 扩散**：玛恩纳在中枢时，官方术语 `cc.c.skill` 的 **15 条**白名单中枢回复技能额外作用到
  room2（其他设施）内工作状态的干员；扩散提供者红脸则失效。

| 技能 | 效果 |
|---|---|
| 玛恩纳「公事公办」 | room1（发电/办公/会客）+0.1，**并把 15 条白名单中枢回复技能扩散到 room2** |
| 维什戴尔「巴别塔之帜」 | room2 +0.1（精英2）；与魔王同在中枢再 +0.1（同干员内相加后参与取最高） |
| 重岳「孤光共照」 | room2 +0.05（精英2） |
| 玛恩纳「独善其身」/ 冰酿「笑靥如春」等 15 条 | 中枢内 +0.05（被扩散时也作用于 room2） |

**中枢内**（`control_center`，即 `cc_recover` 里 `facility_types == (控制中枢,)` 的那些）：左膀右臂 /
S.W.E.E.P. / 笑靥如春等 15 条各 +0.05（求和）、德才兼备等 6 条按阵营人数 ×0.05、浮生得闲（与阿同中枢）
+0.25、魔王传承（与阿米娅同中枢）+0.05、**夕「不以物喜」+0.05**（上游原文是"心情每小时**恢复**+0.05"，
故走回复侧，见 `05-技能分类大纲.md` §5.12）。

**宿舍内**（`rules._dorm_ledger`）：

```
宿舍回复 = 基础回复（白字 + 绿字氛围）
         + 中枢干员对宿舍的回复（cc_recover 且 target=宿舍，如"领袖/战纹/巡心/羁绊相生"等）
         + 自身回复（dorm_self，同种取最高）
         + 群体回复（dorm_group，同种取最高；冰酿单独分配）
         + 单体回复（dorm_single，同种取最高，锁定"心情最低且未满且非提供者"的干员）
         + 定向回复（dorm_targeted，满足条件者叠加求和）
         ± 元修正（M17，dorm_meta）：**他人**把上面某条效果顶高（摩根→推进之王 +0.3，见 `04-特殊机制.md` 第 28 条）
         + 冰酿分配（0.8 总额 / 心情未满成员数）
```

- 基础回复 = `1.5 + 0.1×等级 + 0.0004×实际氛围`（`atmosphere=None` 时按该等级满氛围）。
- 宿舍等级表（`DORM_LEVEL_TABLE`）：

| 等级 | 氛围上限 | 满氛围基础回复 | 校验式 |
|---|---|---|---|
| 1 | 1000 | 2.0 | 1.5+0.1+0.4 |
| 2 | 2000 | 2.5 | 1.5+0.2+0.8 |
| 3 | 3000 | 3.0 | 1.5+0.3+1.2 |
| 4 | 4000 | 3.5 | 1.5+0.4+1.6 |
| 5 | 5000 | 4.0 | 1.5+0.5+2.0 |

- 叠加规则：**不同种类（自身/群体/单体/定向）之间相加，同一种类内部取最高**；例外是定向回复
  （dorm_targeted）在 `_dorm_ledger` 内**直接累加**而非取最高（`rules._targeted_recovery` 只是留给外部调用的取值包装）。

### 3.2.1 布局的规模与等级（上游硬约束）

布局**不是固定的**：制造站 / 贸易站 / 发电站数量可互换，但受上游约束（`building_data.json`，客户端 2.7.71）：

| 约束 | 上游字段 | 数值 | 项目里的落点 |
|---|---|---|---|
| 单类型房间数 | `rooms[].maxCount` | 制造 **5** / 贸易 **5** / 发电 **3** / 宿舍 **4** / 活动室 **6** / 会客·办公·训练·加工 **1** | `facility_max_count()`、`BaseLayout.validate()` |
| **建造位总量** | `layouts.v0.slots` 里 `category="OUTPUT"` 的槽位 | **9 个**（制造/贸易/发电**共用**） | `OUTPUT_SLOT_TOTAL = 9`、`validate()` 报"超出建造位总量 9：列出是哪几间" |
| 各等级容量 | `rooms[].phases[lv].maxStationedNum` | 制造/贸易 **1/2/3**、发电 1/1/1、宿舍 5/5/5/5/5、**控制中枢 1/2/3/4/5**、会客 2/2/2、训练 2/2/2、加工·办公 1/1/1 | `FACILITY_SLOTS_BY_LEVEL`（与上游逐项一致）、`facility_slots()`、`min_level_for_slots()` |
| 中枢等级 → 全基建减免 | `controlData.basicCostBuff = -5`（**每人 −0.05**，无逐等级字段） | 等级只决定**能站几个人**：Lv5 = 5 人 → **−0.25/时** | `cc_reduction(中枢人数)` |
| 宿舍等级 → 基础回复 | 同上（宿舍等级表见 3.2） | Lv1~5 = 2.0/2.5/3.0/3.5/**4.0** 点/时 | `dormitory_recovery(level)` |

**等级从哪来**：MAA 排班文件**不带等级**，导入时按"实际放了几个人"反推**最低可行等级**
（`maa.min_level_for_slots`）：制造站 3 人 → Lv3、控制中枢 5 人 → **Lv5**（不推断就会出现"Lv1 容量 1 却站
5 人"的矛盾布局）。宿舍保持默认 Lv5（等级决定基础回复，不能往下压）。导入后可逐间改：**点看板房间卡头**
（`LevelDialog`）或**批量设置的「房间等级」区**。

### 3.2.2 发电站数量 = **有效间数**（含「仅影响设施数量」的两条修正）

`power_count`（唯一消费方：流明「柔和微光」的 `+0.05/间` 分句）数的**不是**布局里有几间，而是上游措辞里的
「**设施数量**」——有两条技能的**唯一效果**就是把它改大（原文见 `data/facility_count.py`；
`mood_soc/facility_count.py` 求值）：

| 技能 | 条件 | 修正 |
|---|---|---|
| 森蚺「我寻思能行」（`control_pow_bot[000]`） | **森蚺进驻控制中枢** ∧ **Lancet-2 进驻在发电站**（**不看心情**：红脸也算） | 发电站 **+2** |
| 承曦格雷伊「晨曦」（`power_count[000]`） | **承曦格雷伊进驻发电站** ∧ **其他发电站内没有有效的作业平台**（`cc.tag.op`；**红脸的作业平台不算**"有效进驻"） | 发电站 **+1** |

⚠️ **两条不对称**（用户拍板 2026-09）：晨曦要"**有效的**作业平台"（总口径「红脸（心情 ≤ 0）⇒ 技能失效」，
故心情归零的平台不再阻断 ⇒ 照样 +1）；森蚺只看「Lancet-2 **进驻**在发电站」，红脸也照样 +2。
**别顺手把两条对齐**。

```
有效间数 = 实际间数 + Σ(条件成立的修正)          # 只改"数出来是几间"
```

⚠️ **不是"多了两间发电站"**：布局 / 容量 / 进驻位一个都不变（`BaseLayout` 不动），只有"数设施"读到 4 而不是 2。
典型算例（用户那份 252 排班，班次 1）：实际 2 间 + 森蚺 +2（Lancet-2 在发电站#2）⇒ **有效 4 间**；同班晨曦
**不成立**（她在发电站#1，而"其他发电站"#2 里正是作业平台 Lancet-2）。于是同宿舍的阿罗玛：
`4.00（宿舍 Lv5 基础）+ 0.15（柔和微光·β 基础）+ 0.05×4 = 0.20` = **4.35/h**；`--explain` 尾巴写明
`（实际 2 间 + 森蚺「我寻思能行」+2 = 4 间）`。

### 3.3 顶层查询（`rules.py`）

| 函数 | 作用 |
|---|---|
| `compute_net_rate(world, name)` | 净速率 = 消耗 - 回复（>0 下降 / <0 上升） |
| `remaining_mood_after(world, name, hours)` | 时段后剩余心情（钳位 [0,24]） |
| `remaining_work_hours(world, name)` | 还能工作多久（net≤0 → inf） |
| `time_to_mood(world, name, target_mood)` | 达到指定心情所需时间（工作=下降、宿舍=上升） |
| `evaluate(world, name, hours)` | single 模式汇总 → `MoodResult`（含中文状态） |
| `evaluate_base(world, hours)` | base 模式汇总 → `BaseResult`（所有干员 + 布局可维持时长） |
| `work_rest_ratio(x, y)` | 工休比指标 → `WorkRestRatio` |

`evaluate` 的中文状态判定顺序：不在任何设施→"未进驻"；宿舍→"宿舍休息"；mood ≤ 0→"红脸（技能失效）"；
net < 0→"休息中 / 空闲中（回复大于消耗）"；net == 0→"心情不变"；否则→"工作中"。

### 3.4 工休比 `work_rest_ratio(consumption=x, recovery=y)`

```
可连续工作    = 24 / x           （x>0，否则 Infinity）
从零回满      = 24 / y           （y>0，否则 Infinity）
最大工休比    = y / x
最大工作时长占比 = y / (x + y)
24h 内最长可工作时间 = 24·y / (x + y)
```

### 3.5 两种测算模式：single 与 base（核心入口）

| | single（`evaluate`） | base（`evaluate_base`） |
|---|---|---|
| 对象 | 一个目标干员 | 基建内所有干员 |
| 心情值 | 目标时段结束后的剩余心情 | 当前心情（或 `period>0` 时推进后） |
| sustain_hours | 其余干员心情无限：工作→到红脸、宿舍→恢复满 | 工作=布局可维持时长；宿舍=min(恢复满时间, 布局可维持时长) |

**base 模式口径**（`rules.evaluate_base`）：`layout_sustain_hours` = 所有干员"到红脸（mood≤0）剩余时长"的
**最小值**（mood/net，net>0；net≤0 为 Infinity；已红脸为 0），并标出 `bottleneck`（最先红脸者）。逐人
`sustain_hours`：net≥0 → 统一 = `layout_sustain_hours`；net<0 → `min(恢复满所需时间, layout_sustain_hours)`。
逐人 `mood_at_end` = clamp(mood - net×layout_sustain_hours, 0, 24)；`layout_sustain_hours` 为 Infinity 时二者
均为 None（JSON null）。解析解（速率恒定）；要"红脸后技能失效联动"用 `simulate`。

**JSON 输出**（`mood_soc/output.py`）：`mood_result_to_dict` / `base_result_to_dict` → dict，`dump_json`
写文件；`inf` 序列化为 `null`。CLI（`main.py --mode ...`）默认打印到 stdout，加 `--json-file` 才写 `results/`。

### 5. 技能系统（skills.py + skills_data.py）—— 技能数据自动生成

> ⚠️ **技能数值不要手写进 `skills.py`**：真实数据在 `data/moods_skills.txt` + `data/operators.txt`，跑
> `.venv/Scripts/python.exe scripts/generate_skills_data.py` 生成 `data/skills_data.py`（含 `SKILLS` /
> `DEFAULT_OPERATORS` / `SKILL_EQUIPS` / `TRAITS`）。`skills.py` 只保留框架（`Skill` / `SkillEquip` /
> `SkillKind` / 条件函数），末尾 re-export 数据。

#### 5.1 数据模型（三个关键对象）

`Skill` = 一个 skill_id 的一个 clause：

| 字段 | 含义 |
|---|---|
| `id` / `name` / `kind` / `value` / `facility_types` / `target_trait` / `condition` / `note` | 基本项；`value` 已是真实 Decimal（生成时由千分值 ÷1000 得到），符号语义见 §5.4 |
| `exclusive=True` / `pool=True` | 独占回复（菲亚梅塔）/ 池分配（冰酿） |
| `count_faction` | 非空 = **per-count 阵营计数**（详见 §5.2） |
| `var_name` / `var_per` / `var_min` | **变量**折算（`04-特殊机制.md` 第 16 条） |
| `self_only` | 消除类只作用于**自身**（若叶睦「互为半身」）；False = 同设施所有干员（槐琥/令） |
| `basis` | **计数基准**折算（`04-特殊机制.md` 第 19 条）：`power_count`（每有 1 间发电站）、`dorm_level`（当前宿舍每级）、`dorm_others`（每有 1 名其他干员）、`recruit_slot`（每个招募位） |
| `boost_provider` / `boost_group` | **元修正**（M17）点名槽：强化谁（持有者名）、强化哪一组贡献（如 `dorm_group`）；目标筛选仍走 `condition`（`04-特殊机制.md` 第 28 条） |
| `template_id` | 分类模板（`M01`~`M17` / `X01`~`X11`，见 §5.5） |
| `max_group` | 非空 = **同组取最高**（轴 F3，官方术语 `cc.c.sui2_1`） |
| `spread_whitelist=True` | 该技能是**扩散提供者**（玛恩纳公事公办） |
| `partial` / `partial_mode` | 模板确定但条件槽空（`apply` 按骨架生效 / `hold` 保留骨架不生效） |
| `untranslated=True` | **暂不生效**，等价 `partial_mode="hold"`（note 留原文待人工翻译）。⚠️ **当前 250 条 clause 已无实例**：最后 2 条（龙舌兰 投资·α/β）已按上游原文（心情 -0.25 常驻、只在贸易站）转为 `apply`，见 `04-特殊机制.md` 第 32 条 |

- **`SkillEquip`（干员↔技能的"解锁/提升"绑定）**：字段 `unlock_elite / unlock_level / enhanced / replaces`；
  同一 skill_id 在不同干员身上解锁等级可能不同，故解锁信息**不属于 Skill 本身**。
- **`Operator.elite / level`**：精英化等级（0/1/2）与干员等级（1/30）；缺省 **elite=2、level=30**（满练口径，
  见 §5.3 第 5 条）。技能是否生效 = `op.elite >= equip.unlock_elite 且 op.level >= equip.unlock_level`。

#### 5.2 阵营联动（"因其他阵营/干员存在而改变心情"）

三类联动技能，均已在数据中生效（阵营表 `skills.OPERATOR_FACTIONS` **由上游自动生成**）：

| 类 | 机制 | 例 |
|---|---|---|
| **阵营计数类**（per-count，`count_faction`） | 总回复 = `value × 目标设施内该阵营干员数` | 陈"德才兼备"（中枢内每个龙门近卫局 +0.05）、电弧"无言的慈爱"（宿舍内每个精英干员 +0.1）、异格者/彩虹小队/谢拉格/乌萨斯/鲤氏等 |
| **与具体干员共事**（`condition`） | `_cond_with_cc_operator(name)`（同中枢）、`_cond_with_facility_operator(name)`（同设施） | 德克萨斯"恩怨"与拉普兰德同贸易站 +0.3、老鲤"浮生得闲"与阿同中枢、魔王"魔王传承"与阿米娅同中枢 |
| **与阵营共事**（`condition`） | `_cond_with_cc_faction(faction)`（同中枢、排除自身） | 摆渡人"英雄的骄傲"与萨尔贡干员同中枢 +0.02 |

> 阵营表 `OPERATOR_FACTIONS` / `FACTION_MEMBERS` **自动生成**：上游 `gamedata_const.json → termDescriptionDict`
> 的 `cc.g.*` / `cc.tag.*`，共 28 组 231 条；`cc.g.sp`（异格）上游不列名单，放 `data/factions_supplement.txt`。
> 生成：`python scripts/generate_factions.py --agd <ArknightsGameData>`；**禁止手工维护阵营表**（历史手工表把
> 米诺斯误标为萨尔贡、岁只收 3/7）。`generate_skills_data.py` 的 `check_faction_refs()` 校验技能引用的阵营名，
> 对不上直接报错。

#### 5.3 精英化判断（本项目的核心扩展）

| # | 规则 | 说明 |
|---|---|---|
| 1 | **解锁** | `enhanced=False` 的技能是独立技能，达到 `unlock_elite/unlock_level` 才生效（如巫恋"低语"精英2解锁） |
| 2 | **β 替换 α** | `enhanced=True` 的技能是"精英化提升"版，其 `replaces` 指向被替换的低版本技能 id；同一干员同一 family 内解锁后**替换**低版本、**不叠加**（如火神"工匠精神" α-0.15 → 精英2 β-0.25） |
| 3 | **规则引擎** | `rules._active_skill_ids(op)` 一次算好"已解锁 + 未被替换 + 非待译"的集合，`_skills_of(op, kind)` 全基于它；改判断逻辑只动 `rules.py` |
| 4 | **判定式** | `rules._unlocked(op, sid)` = `op.elite >= equip.unlock_elite 且 op.level >= equip.unlock_level`（`equip` 取自 `SKILL_EQUIPS[(干员名, skill_id#clause)]`）。上游门槛分布（291 条绑定）：`unlock_elite` 0→166 / 1→33 / 2→92；`unlock_level` 只有 **30** 一档、共 4 条（杜林 ×2、THRM-EX、Lancet-2） |
| 5 | **缺省＝满练** | `Operator.elite` 缺省 **2**、`level` 缺省 **`DEFAULT_OPERATOR_LEVEL = 30`**（`scenario.build_operator`）；要算没练满的写 `{"name": "卡夫卡", "elite": 1}`（GUI 侧＝「批量设置」的练度列）。⚠️ 缺省等级从 1 提到 30 是**有意的口径变化**：那 4 条要 30 级的技能（如杜林"陪练"）因此在缺省场景下生效（陪练速率 −4.2000 → −4.2500） |
| 6 | **看出"没满练"** | 非 E2 的干员在看板 / 全员一览的芯片上带 `E1` 角标，对点查询多一行 `练度 E1（等级 30）· 已解锁 N 条心情技能；⚠ 因未满练少 …`，文字由 `rules.mood_skill_summary(op) -> (已解锁数, [(技能名, 需要精英, 需要等级)])` 生成（只统计 `SKILLS` 里的心情技能；只读接口，不参与速率计算） |

#### 5.4 `SkillKind`（11 种）与 value 符号语义（极易错，请牢记）

| SkillKind | value 语义 | 叠加方式 | 现有哪些技能（节选） |
|---|---|---|---|
| `SELF_CONSUME` | 自身消耗增减：负=减耗，正=加耗 | 该干员自身求和 | 泡泡-0.25 / 火神α-0.15·β-0.25 / 阿罗玛+0.25 / 斥罪+0.5 / 夕"不以己悲"+0.5 |
| `FACILITY_CONSUME` | 同设施全体消耗增减（含自身） | 全体求和 | 黍-0.1 / **巫恋"低语"+0.25**（含自身） |
| `ROOM_OTHERS_CONSUME` | 同设施**其他**干员消耗增减（不含自身） | 全体求和（跳过自身） | **当前无使用者**（低语已改判，见 `04-特殊机制.md` 第 11 条） |
| `CC_REDUCE` | 中枢全局消耗减免（正=减免量） | 跨干员取最高 | 预留（真实数据中相关技能已归为 CC_RECOVER） |
| `CC_RECOVER` | 中枢提供的回复速率（恒正） | **F1 求和 + F3 同组取最高（`max_group`）+ 扩散** | 玛恩纳公事公办 / 维什戴尔巴别塔之帜 / 重岳孤光共照 / 冰酿笑靥如春 / 左膀右臂等 15 条 / 德才兼备等阵营计数 / **夕"不以物喜"** |
| `DORM_SELF` | 宿舍自身回复（恒正） | 同种取最高 | 菲亚梅塔+2.0（独占） |
| `DORM_GROUP` | 宿舍群体回复（恒正） | 同种取最高 | 刺玫+0.15 / 冰酿0.8（池分配） |
| `DORM_SINGLE` | 宿舍单体回复（恒正，锁定目标） | 同种取最高 | 使徒/慈悲/疗养等（大量真实技能） |
| `DORM_TARGETED` | 宿舍定向回复（恒正，满足条件） | 求和 | 刺玫低心情+0.1（mood<18）/ 净化呼吸（mood<20） |
| `ELIMINATE_SELF` | 消除他人自身消耗（value 恒 0） | — | 槐琥 / 令（限岁） |
| `DORM_META` | **元修正**：强化**他人**在宿舍的恢复效果（value = 增量，正） | 并入**被强化技能**的小计（轴 F2） | 摩根「头号陪练」→ 推进之王 +0.3（见 `04-特殊机制.md` 第 28 条） |

`condition` 是 `Callable(SkillContext)->bool`，`SkillContext` 含 `world / owner / target / facility`；条件函数用
鸭子类型读 ctx，故 `skills.py` 不 import `rules.py`（避免循环依赖）。**新增/修正一条技能 = 改 `data/*.txt`
→ 重跑生成脚本**；特殊机制无法用数据表达的才在 `rules.py` 加解释逻辑。

#### 5.5 分类模板（六轴）—— 新增技能的"填表"入口

`mood_soc/skill_templates.py` 定义**六轴**：A 建模地位（`A1` 速率 / `A2` 事件 / `A3` 心情当条件 / `A4` 非心情）、
B 作用域、C 作用对象、D 效果、E 数值形态、F 叠加规则。**模板 = 真实数据里用到的 (B,C,D,E,F) 组合**，
ID 为 `M01`~`M17`（心情类）与 `X01`~`X11`（非心情，登记不建模）。

- **铁律**：模板挂在 **clause** 上（一个 buff 的多个子句可属不同族），故 `moods_skills.txt` 是 clause 级、
  每行带 `template_id` + `params`；`skills_registry.txt` 是 buff 级覆盖台账（上游全部 755 条，一行一条）。
- **「规则修饰」并入 F 轴**（同种取最高 / 特殊比较规则 / 归零 / 恒定 / 除以 / 优先生效）：只改"怎么合"、
  不改"改什么"，不是独立技能族。
- **零遗漏保证**：`scripts/classify_skills.py --check` 断言「模板全部命中 + 台账行数 == buff 总数 +
  无 `tier=??`」，不满足即退出码 1；新 buff 没归宿会**硬报错**而不是被静默忽略。
- 详细模板字典、判定关键词、待办缺口见 `documents/05-技能分类大纲.md`。
- 引导死锁：`scripts/*.py` **不能** `import mood_soc.skill_templates`（包 `__init__` 会连锁到 `skills_data`，
  而它是生成物），故用 `importlib` 按文件加载（见脚本内 `_load_templates_module`）。
