> 结论先行：**数据层已经可拓展（六轴模板就绪），运行时不可拓展**——所以重构范围是**运行时**

## 一、诊断结论

| 维度 | 状态 | 证据 |
|---|---|---|
| 数学层（安时积分） | ✅ 可拓展 | `battery.py` 与游戏规则无关，纯钳位积分 |
| 数据层（技能库） | ✅ 可拓展 | 六轴模板已就位：250 clause 全挂 `template_id`，755 buff 全登记 |
| **运行时派发** | ❌ **不可拓展** | `template_id` 在数据里，**`rules.py` 从不读它**；派发靠 `SkillKind` 的 if/else |
| **布局模型** | ❌ **不可拓展** | `get_facility()` 只返回第一个同类型设施；无容量 / 副手 / 工作状态 / 活动室 |
| **记录系统** | ❌ **不存在** | 只有一个 `net_rate` 数字 + `note` 原文；无法回答"这个速率由谁贡献、按什么规则合成" |
| 特殊机制 | ⚠️ 半成品 | 阵营表曾手工且**错误**（已修）；26 种变量（热情值等）无载体 |

> 病灶的**现行测绘**（逐条 `file:line`）见 `09-架构总览.md` §7；下面几小节是**当年的诊断口径**，保留用于对照。

### 1.1 运行时派发：模板与代码双轨

- 数据侧 `Skill.template_id ∈ {M01…M17, X01…X11}`（六轴分类，已完整）；代码侧 `SkillKind ∈ {self_consume, facility_consume, …, eliminate_self}`（8 种在用）。
- **两者互不知情**：`rules.py` 里 `SkillKind.` 出现 15 次，`template_id` 出现 **0 次**。
- 后果：新增机制 = 改 `SkillKind` 枚举 + 在 `compute_consumption`/`_work_recovery`/`_dorm_recovery` **三处**加分支 + 生成器 `FAMILY_KIND` 加映射 + 同步两份文档 —— 这就是"不可拓展"的定义。

### 1.2 聚合规则散落成硬编码

| 规则（轴 F） | 当前实现位置 | 问题 |
|---|---|---|
| F1 求和 | 各函数内 `total +=` | 与环境耦合 |
| F2 同种取最高 | `_dorm_recovery` 内 `max(...)` ×3 | 写死；无法表达"哪几种算同种" |
| F3 跨干员取最高 | `_work_recovery` 内 `grouped[group] = max(...)` | 后加的特例 |
| F6 池分配 | `_icebrew_recovery` 独立函数 | 冰酿专属，不通用 |
| F7 归零优先 | `_dorm_recovery` 顶部 `exclusive` 短路 | 菲亚梅塔专属，不通用 |

→ 没有统一的 `Accumulator`，每加一条叠加规则就多一处 `max/min/短路`（`rules.py` 里 `max(` 9 次、`min(` 4 次）。

### 1.3 布局模型：只支持"每种设施一个"

`get_facility()` 只返回第一个同类型设施。实测：布局放 2 个制造站 + 2 个宿舍时，`facility_of()`（遍历全部）**能**逐干员算对，但任何"按设施类型聚合"的技能无处落地。上游需求规模（755 buff 实测）：

| 需求 | 上游条数 | 现状 |
|---|---|---|
| 「处于工作状态」 | 15 | 无概念：默认所有进驻者都在工作 |
| 「不包含副手」 | 29 | 无概念 |
| 「活动室使用者」 | 23 | `FacilityType` 里**没有 PRIVATE**（上游 `rooms` 有） |
| 「每有 N 间发电站」 | 2 clause | 无"按类型计数"能力 |
| 「所有宿舍 / 所有制造站」 | 5 / 7 | 靠逐设施迭代侥幸可用，非通用能力 |
| 设施等级折算（宿舍每级、办公室等级） | 4 clause | `Facility.level` 有，但技能读不到 |

### 1.4 一个已确认的错误：加工站 / 训练室被当成普通工作设施

实测 `加工站 路人X 消耗=0.75`、`训练室 路人X 消耗=0.75`：`compute_consumption` 只排除宿舍，其余一律 `BASE_CONSUMPTION = 1.0`。但**加工站的心情是按次消耗（配方心情消耗）**，不搓材料就是 0/h；训练室的协助位另有规则。同时这 9 条训练室 + 35 条加工站心情技能**根本没进技能库**（登记在台账里，`modeled=no`）。

### 1.5 特殊机制

| 机制 | 状态 |
|---|---|
| 阵营/标签 | ⚠️ 曾是手工表，**已修**：`cc.g.*`/`cc.tag.*` 28 组自动生成 |
| 变量（热情值/人间烟火/感知信息/无声共鸣/因果业报/木天蓼/魔物料理/乌萨斯特饮/外势实地/巫术结晶…） | ❌ 26 种全部无载体 → 依赖它们的 43 条 buff + 31 条 `partial/hold` 子句无法生效 |
| 心情落差 | ❌ 无载体（`A3` 档 6 条的唯一来源） |
| 事件类（消除/独占/互换/触发恢复/元修正） | ⚠️ 消除与独占已实现；`M15a/M15b/M17` 未实现 |
| 跨设施聚合（room1/room2/room3） | ✅ `config` 已按官方术语定义 |

### 2.1 五个核心抽象

| # | 抽象 | 落地形态 |
|---|---|---|
| 1 | **布局是一等公民** | `Facility`（`level` / `operators` / `deputies` / `slots` / `enabled` / `atmosphere`）+ `BaseLayout`：`of_type()` / `count_of_type()` / `all_dormitories()` / `operators_in()` / `working_operators()`（「处于工作状态」15 条）/ `base_operators()`（「不包含副手及活动室使用者」29 条）；新增 `FacilityType.PRIVATE`（活动室），`get_facility()` 保留但 deprecated |

## 三、已完成（P1 布局 + P2 记录层 + P3 变量）

### P3 —— 变量账本（`variables.py` + `variable_producers.txt`）

- 官方术语表 26 种变量里 **3 种影响心情**（人间烟火 / 热情值 / 无声共鸣），另有派生变量 **心情落差**（= 24 − 当前心情）。
- `VariableLedger`：变量值 + 产出者来源（可解释）；`basis_count()` 支持 4 种计数基准（`flat` / `dorm_operator` / `recruit_slot` / `sui_non_dorm`）。
- 消费端：`Skill.var_name` + `var_per`（每有 N 点 → 值 × floor(变量/N)）/ `var_min`（≥ N 才生效）。
- **不生效子句 31 → 25**，6 条变量消费子句从 `hold` 转 `apply`：孤光共照#2、跋山涉水#2、万里传书#2、无词颂歌#2、生活的重压、演技的怪物。
- 实测：热情值 40（若叶睦+祐天寺若麦+八幡海铃）→ 丰川祥子「生活的重压」+0.05 生效；人间烟火 50（夕+令+岁×4）→ 重岳「孤光共照」从 0.05 升到 0.15。

### P1 —— 布局模型（`models.py` / `config.py` / `scenario.py`）

- `FacilityType.PRIVATE`（活动室）补齐；上游 `rooms` 有 12 种 roomType（含 PRIVATE/ELEVATOR/CORRIDOR）。
- 容量与房间数**取自上游**：`FACILITY_MAX_COUNT`（`rooms[].maxCount`）、`FACILITY_SLOTS_BY_LEVEL`（`rooms[].phases[lv].maxStationedNum`）。实测：中枢 [1,2,3,4,5]、制造站 [1,2,3]×5 间、发电站 [1,1,1]×3 间、宿舍 [5]×4 间、活动室 0×6 间。
- 多房间查询 `of_type()` / `count_of_type()` / `all_dormitories()` / `facilities_in()`；对象查询 `working_operators()`（「处于工作状态」15 条）、`base_operators()`（「基建内（**不包含副手及活动室使用者**）」29 条）。
- `Facility.deputies`（副手）+ `slots`/`enabled`/`name`；`BaseLayout.validate()` 自检容量与房间数。
- **修掉一个真错误**：`compute_consumption` 只排除宿舍、其余一律 1.0，把**加工站算成 0.75/h**。现在按 `config.base_consumption(ftype)`：加工站 0（按次消耗）、活动室 0、宿舍 0。

### P2 —— 记录层（`ledger.py` + `rules.py` 重写）

- `Contribution`：一条来源 = 谁（owner）+ 哪条技能（skill/template）+ 作用于谁（target）+ 值 + 叠加规则。
- `MoodLedger.total()`：轴 F 统一落地 —— `SUM` / `SAME_KIND_MAX`（同 group 取最高）/ `CROSS_OWNER_MAX` / `POOL` / 归零 / 独占。
- `rules.py` 重写为**唯一计算路径**：先记 Contribution，再由 ledger 合成。重构前散落的 `max()`（9 处）、菲亚梅塔短路、冰酿专属函数、消除布尔判断，全部变成数据 + 一个 Stacking 分支。
- `mood_ledger(world, name).explain()` + CLI `--explain`：中文逐条解释，并标出「同种取最高，被更高者覆盖」「跨干员取最高，被更高者覆盖」。
- **流水账当场抓出 2 条数据错误**（数字上被 `max()` 掩盖）：① 刺玫「芬芳疗养·β」漏标 `enhanced=1` → α 与 β 同时生效；② 反过来查了 39 名多阶段槽位干员的 `replaces` 链 —— **完整**（含赫拉格的三阶段链）。为此新增 `classify_skills.py → audit_enhanced()`：对照上游**槽位结构**校验提升链（同槽位多个 `buffData` = 提升链；除最低阶段外都应 `enhanced=1`）。

### P4a —— 可数条件 + 两处语义/实现修正（已完成）

12 条「每有 N 个什么」的子句全部启用（`basis` 参数 + `variables.basis_count`，新增 5 个基准）。
过程中查出并修掉两个**真问题**：

1. **「同种效果取最高」的粒度错了**。上游写「（叠加后的**最终值**同种效果取最高）」
   → 同一技能的多个分句要先求和。旧实现按单个分句取 max：
   死前必做清单 Lv5 得 0.15（正确 0.25）、倾谈者/寻同路人/无瑕心/柔和微光/独处 同类偏低。
   修法：`MoodLedger.total()` 的 `SAME_KIND_MAX` 改为「按 (持有者, skill_id) 先聚合分句，再取最高」。
2. **β 替换链把「同一技能的分句」当成链上环节**，导致额外分句"替换"掉自己的基础分句——
   实测 **6 例**基础值全部丢失：响石 0.15、铎铃「万里传书」-0.1、刺玫 0.15、波卜 0.2、
   流明 0.1、隐德来希 0.1。修法：替换链单位改为 **skill_id**（`SkillEquip.replaces` 存不带 `#clause` 的 id，
   `_active_skill_ids` 按 `base_skill_id` 整条剔除）。
   > 这两条都是**已存在**的 bug，不是 P4a 引入的；是"把更多子句打开"之后才显形。

**效果**：不生效子句 **25 → 13**（累计 37 → 13）。

**同时修掉 5 个结构/实现缺口**（都是"打开更多数据"之后才显形的）：

1. **3 处贡献循环从不求值 `skill.condition`**：`DORM_GROUP` / `DORM_SELF` / 消除类。

### P7 —— 求解器适配面 + "真名 / 组合"体检（已完成）

> 目标（用户口径）：`ArknightsInfraCalc-v3`（Rust）算"**高效率的基建布局**"，本项目**匹配那套布局**并生成它的**完整心情变化周期**；界面只负责让人看，**交付面是 `api/`**。接入说明见 `08-程序接口.md`。

**一、适配面：三个新 op（协议 1 → 2）**

| op | 解决什么 |
|---|---|
| `load_json` | v3 **内存里**的求解结果直接喂进来（4 种格式自动识别，含 `{"result": …}` 信封），不必再落临时文件 |
| `layout_at` | 「某时刻 → **整座基地的布局 + 全员心情**」：每间房 / 位次 / 在位干员 / 不在基建名单 |
| `closure` | 「这套布局**能不能长期跑**」：连跑 N 个周期，周期末心情逐人不再变化即进入固定点 |

按文件（`load_file`）与内联（`load_json`）**共用同一条装配路**（`store.schedule.load_schedule_from_imports`），同一份 JSON 两条入口必须逐位相同。

**默认口径**（用户裁决）：换干员**默认关**（且**不继承**文件里的 `Fiammetta.enable`）、闲置入宿**默认开**、周期**取文件里的各班时长**。⚠️ "闲置入宿默认开"**当时**只作用于 `load_json`（界面与 `load_file` 维持"关"）—— 这条已被 **P8 第九节**推翻，现在是**全项目统一默认开**。

**二、顺手修掉的两个真问题**

1. **多周期下"她在哪"会错位**（分两步修完）：① **段内快照** —— 布局副本跨周期复用（`worlds[idx]` 只建一次），而闲置入宿**就地改这份副本** ⇒ `world_at(t)` 在第 1/2 周期给出第 N 周期的排布（实测：第 1 周期宿舍 2 人 vs 第 2 周期 5 人），于是开着闲置入宿时**每段留一份深拷贝快照**。② **段首重建**（2026-09，用户报"菲亚梅塔心情 20.4 却被换出"）：快照只解决"读"、没解决"算" —— 副本本身仍被跨周期复用，"第 1 周期把她换出去"于是继承到后面所有周期（那一班开局就没有她、**既不重判心情也没有事件**）。现在改成 `pristine` + 每段 `copy.deepcopy` 重建：位置回排班原样、当班按当时心情重新判定，**心情仍跨周期连续**（在 `moods` 里），代价 ≈ 每段 0.35ms。回归 `test_跨周期位置复位_每周期都重新判定`，口径见 `03-特殊机制.md` 第 30 条。
2. **文档里的 `load_file --args @文件` 是错的**（args 被当成整个文件内容，而 `load_file` 要 `{"path": …}`）：`08-程序接口.md` 里 5 处示例全部改正并逐条跑通。

**三、技能核对从三层加到四层（L4）**

L2 用**合成干员 + 手工注入 `skill_id`**，留两个盲区：① 没走"真名 → `DEFAULT_OPERATORS` → 技能槽 → 进流水账"这条路（名字没认出来、精英化门槛把技能全挡掉，都能让一位干员**一条技能都不生效**）；② 只核"条件满足时数值对不对"，**没核**"条件不满足时**不该**生效"—— 组合技能最容易错的就是后一半。于是 L4 分三块：**真名挂载 178/178**、**真名结算 178/178**、**组合双向对照 48/48**（覆盖 9 类）。

⚠️ **L4-c 的坑**："把搭档**搬走**"会同时改掉**控制中枢「N 人，每人 −0.05」的全局减免**，差值不再只反映那条组合条件 —— 实测德才兼备的差值从 −0.10 变成 −0.20，**看起来像"引擎多算了一倍"，其实是中枢少了一个人**。正确手法是**改名 / 摘阵营、人留在原房间**（保持在场人数）；只有「独自一人」「宿舍他人在场」这类**条件本身就是人数**的才真去增删人。

**四、阈值吸附把曲线压平**（用户从卡夫卡的曲线里看出来的）

- **症状**：示例排班第 2 班宿舍段 `[12.95h, 13.2h]` 同宿舍 **8 名干员**一起被压在阈值 **20** 上（速率 ≈ 0）；她在宿舍以 4/h 回复，13:12 该是 **21.0**、实际 **20.0**（**整段低 1.0**），14.2h 就住满 24 ⇒ **24h 末值看不出来**，只在**曲线中段**可见。
- **定性**：`MAX_SEGMENT_HOURS` 从 0.25h 调到 0.05h / 0.01h / 0.001h，曲线**全部回到解析值** ⇒ 是积分器 bug，不是机制口径。
- **根因**（`store/schedule.py: _next_event`）：阈值吸附表在**积分之后**应用，而那一刻 `nxt` 可能已在 `MAX_SEGMENT_HOURS` 之外 —— 只差 1e-26 就跨阈值的人**已经被积分推过去了**，再吸附等于**把它往回拽**，白扣 `|速率| × 0.25h`。让它更早暴露的是同一函数里 `snaps = {name: h}` 的**覆盖赋值**（同一步里多人跨阈值时只有最后一个赢家留下）。
- **修法**：只差 `MIN_EVENT_GAP` 就跨阈值的人**当场吸附**（并把这批人报给调用方重算速率），吸附表只留"正好在**本段末尾**跨过"的人；同刻用 `setdefault` 合并。
- **回归** `tests/test_ui_schedule_blackbox.py::Test阈值吸附` 三条：解析值（宿舍回复段 13:12 = 21.0）、同宿舍 8 人阈值处不许有平台、**步长 0.25h 与 0.001h 的曲线逐点一致**（最后这条把"算得对"定义成**与积分步长无关**）。口径见 `03-特殊机制.md` 第 35 条；**24h 末值不变**（20.1），只少了 1 个由 1e-26 尾巴带出的多余节点（**132 → 131**）。

- **只读对照（2500 条判定）**：改成"贡献溯源"（看有没有 `owner==她` 的正向条目）后 **一致 2497/2500（99.9%）**，**漏判 2 条**：**乌尔比安 / 幽灵鲨** —— 摘掉她们后 **歌蕾蒂娅**变差（「潮汐守望」的条件按**全宿舍 / 宿舍外**的深海猎人**计数**）。**结论：不直接换**。⚠️ 第一版对照被**合成世界的重名**骗过（随机住客与既有干员同名 ⇒ `facility_of` 命中工作设施那份），造随机世界前先把同名摘干净。
- **落地**：`rules._pendant_probe_names` = 她同设施的人 ∪ `rules._dependent_holders`（持"`condition` 非空 或 模板 ∈ 聚合/池分配/定向/元修正"技能者）；真值在 **571 条正例**里始终落在这条保守带内。**实测**：探针 45.4 → **10.5 人**、判据耗时占比 **27% → 13.6%**、7 周期 **1893 → 1552 ms（1.22×）**、等价性 **2000 条判定 0 不一致**；回归 `test_equivalence.Test挂件判据探针范围`（60 个同种子随机世界），全量 **467 → 470**。

**六、P6a / P6b：增量重算**（已完成，口径见 `§9.5`、`AGENTS.md` 坑 23 ⑤）

- 同一个班次**每周期都重复** ⇒ 最早受影响段取决于改的是什么：7→6 只截断（~100%）、6→7 第 18 段（86%）、改末周期锚点/逐次设置第 20 段（95%）、改**某班布局/房间等级/练度**第 2 段（**只省 10%**）、改初始心情/总开关/`detached` 第 0 段（0%）。另实测：后面几个周期**不是逐位重复**前面的（相邻周期起点差 4~34 人）⇒"收敛后直接抄"**不可用**。
- **P6a**：`simulate_schedule(..., continue_from=(上一份轨迹, 它算完的周期数))`，前缀的 `times/series/marks/seg_worlds/idle_states` 预填进累加器、段循环从 `已算完周期数 × 班数` 起跑；能不能增量由 `Session._inputs_fingerprint()`（除周期数外的全部输入）判定，`ui/app.py` 把 `_fingerprint` 一起传给 `Session.adopt`。实测 7→6 **6.5 ms**（原 1300 ms，200×）、6→7 **217 ms**（约 6×）、7→1 **3.8 ms**；回归 `Test周期数增量重算`，全量 **470 → 473**。
- **P6b（通用化）**：`continue_from` 从"周期数"改成"**段数**"（`simulate_schedule(..., continue_from=(上一份轨迹, k))`，`k` 段 = 前 `k` 个班次段），切点按**逐段输入指纹**算：
`Session._segment_signatures()` 给每段记一条 `(全局设置摘要, 那一班的布局摘要, 那一段命中的闲置入宿逐次设置, 落在那一段的心情锚点)`，取**第一个不同**的下标；⚠️ 段边界必须落在新时间轴的段起点上，否则抛错、退回整条重算。
  ⚠️ **2026-10 后记**：那第三项**已随逐人「参不参与」整条撤销**（`per_operator` / `IdleToDormEntry` / `entry_for` 全删）⇒ 现在的指纹是 **3 元组** `(全局设置, 那一班的布局, 落在这一段的心情锚点)`；「改逐次设置只算那一段」那条实测与回归也随之删除（**对象消失**，不是失效）。

**七、P7：一批人的净速率共享「变量快照」**（已完成，2026-09，口径见 `§9.5`）

- **先量再做**：7 周期全量的 cProfile（未优化前 4.22 s / 1175 万次调用）里 `mood_soc/variables.py: collect_variables` 被调 **44,240 次**、累计 0.65 s（≈15%）—— `rates_in_world`（以及 `_all_rates` / `evaluate_base` / 挂件探针世界）都"循环调用 `compute_net_rate(world, 每人)`"，而**每人各收一遍基建级变量快照**；可那份快照是**世界级**的（人间烟火 / 热情值 / 无声共鸣…）。
- **做法**：新增 `mood_soc.net_rates(world, names=None)`（收一次快照喂给这批人），`mood_ledger` / `compute_net_rate` / `remaining_mood_after` 各加**可选** `variables=`；调用点 `store.schedule.rates_in_world` / `rules._all_rates` / `rules._is_pendant_uncached` 的探针循环 / `rules.evaluate` / `rules.evaluate_base` / `simulator.simulate`。
- **同机交替 A/B**：1 周期 **147 → 119 ms（1.23×）**、3 周期 **602 → 459 ms（1.31×）**、7 周期 **1525 → 1159 ms（1.32×）**；累计（含 P1~P6）7 周期 3.41 s → **1.14 s**。回归 `test_equivalence.Test变量快照共享`，全量 **476 → 478**（加打包路径与 `--smoke` 用例后 **481**）。
- **负结果（留档）**：试过把 `_active(op)` + `_skills_of(op, kind)` 合成"带红脸态"的缓存（12 处调用点），交替 A/B 只有 **1.01×**（profiler 那 112 万次调用大半是**采样开销**）——**已回退，别再试**。

**八、闲置入宿第二版：取消班次门槛 + 长班内部换班执行点**（2026-09）

- ① **取消"至少 3 个班次"门槛**（1/2/3 班都执行）；② 新增**内部换班执行点**：班时长 > 12h 时，班内每个**严格小于班末**的 12h 整数倍都是执行点（12h→`[0]`、18h→`[0,12]`、24h→`[0,12]`、25h→`[0,12,24]`）。
- **引擎侧**：`rules.apply_idle_to_dorm` 去掉 `shift_count` 与 `MIN_SHIFTS_FOR_IDLE`；`store/schedule.py` 新增 `INTERNAL_SWAP_HOURS = 12` / `execution_offsets(hours)` / `execution_points(schedule, cycles)`，段循环改成"一个执行点一段"（段元组多带 `(周期序号, 班内偏移)`），每个 `offset > 0` 的执行点记 `Mark(t0, "internal", …)`。**不变式**：不增加班次数、不改 `shift_index`；同班共用一份逐人配置（`scope` 照旧 `(周期, 班次)`）；`world_at/mood_at` 落在执行点上取**换班后**（`_segment` 的 `bisect_right`）；"等待回满再换"**不跨执行点**（`t >= seg_end` 那一瞬不执行）。
- **界面与代价**：逐次表**一个执行点一组**（标题带 `（12h 内部换班）`），`_collect` 加"用户改过的那一行优先"防覆盖；>12h 的长班每次重算多出若干次"重建 + 速率重算 + 闲置入宿"（示例排班 12/6/6 没有 >12h 的班 ⇒ **数值一字不变**）。验证：`scripts/verify_idle.py` **95 条全绿（当时口径；该脚本 2026-10 整段重写并扩容，条数以跑脚本为准）**；24h 单班三条增量重算**逐位等于全量**。

**怎么量**（照抄，改完对比这三个数）：

```python
import time
from data.paths import MAA_SAMPLE
from store.session import Session

for cycles in (1, 3, 7):
    s = Session()
    s.load_paths([MAA_SAMPLE])
    s.set_cycles(cycles)
    best = 9e9
    for _ in range(3):                       # 取 3 次最小值，去掉调度噪声
        t0 = time.perf_counter()
        s.recompute()
```

- [ ] 新技能所在的设施是**挂件位**（加工站 / 训练室）？→ 是的话**不该建模**：只放挂件、不计算心情消耗，见 `03-特殊机制.md` 第 15 条。
- [ ] 新技能属于**尚未建模的设施**？→ ①在 `generate_skills_data.FACILITY_BY_PREFIX` 加 `"<skill_id 前缀>": "<FacilityType>"`；②在 `classify_skills.MODELED_ROOMS` 加上该 roomType（否则台账继续标"设施未建模"）；③确认 `config.base_consumption` 有该设施的口径**并且有出处**（docx 段落 / 上游字段），不要按"增量语义"猜。
- [ ] 动了界面「异步重算 / 线程 / 关窗口」？（`ui/app.py: recompute_async` / `_poll_recalc` / `destroy`）→ 四条：①结果只由主线程 `adopt`；②工作线程里**一次都不碰 `self`**（跨线程要用的东西启动前取成局部量）；③**GC 只关不恢复**（`_gc_off_for_worker()` / `_gc_worker_done()`，恢复走 `_gc_on_when_idle()`）；④新挂的 `after` / `after_idle` 要在 `destroy()` 里撤掉 —— `Tk.destroy()` 期间 Tk **仍会派发 `<Configure>`**，所以是"上闩 + 撤"。跑 `tests/test_ui_app_smoke.Test重算中关窗口` 与 `TestGC只在主线程跑`；详见 `07-图形界面.md` §7.1 第 16~20 条。
