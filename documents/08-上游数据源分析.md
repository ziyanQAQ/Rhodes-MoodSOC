## 0. 结论速览

1. **心情技能的权威数据源只有一个文件**：`zh_CN/gamedata/excel/building_data.json`。
   其 `buffs`（755 条定义）与 `chars[charId].buffChar[].buffData[]`（429 名干员 ↔ buffId + 解锁 cond）
   就是现在 `resources/*.txt` 的上游。**不需要**碰 `skill_table.json` / `buff_table.json`（那是战斗数据）。
2. **本地资源已经与该上游一致**：本地 209 个 skill_id 全部能在 `buffs` 里找到（0 缺失）；
   本地 `operators.txt` 覆盖仓库全部 429 名干员、全部 755 个 buffId（0 缺失）。
3. **本地表漏掉 50 条含“心情”的 buff**，全部属于三类：
   训练室 9 条（真·每小时心情消耗，但训练室目前不在建模范围内）、
   加工站 35 条（是「配方心情消耗」，不是每小时速率，属另一种机制）、
   6 条「把心情当条件用」（效果不是心情）。→ 见 §3 待判定清单。
4. **额外白捡的三件宝**（都在 `gamedata_const.json`)：
   阵营/标签花名册 `cc.g.*`/`cc.tag.*`（可替代手工维护的 `OPERATOR_FACTIONS`）；
   设施集合定义 `cc.c.room1/room2/room3`（印证现有折算假设）；
   术语 `cc.c.skill` + `cc.c.sui2_1`（**玛恩纳“部分技能扩散”白名单** 与 **“取最高”特殊比较规则**）。

关键点：**这是一个纯数据 dump，没有可执行的公式实现**（`[uc]lua` 只含 hotfix 片段），
所以“心情消耗/回复怎么算”仍要以本项目 `resources/心情消耗回复和工休时间.docx` 为准，
仓库只负责提供**技能文本、数值、解锁条件、阵营名册、设施集合、术语定义**。

## 2. building_data.json 的 schema（只列心情相关）

```jsonc
{
  "controlData":  { "basicCostBuff": -5 },        // 中枢：每名进驻干员全基建心情消耗 -5%(即 -0.05)
  "dormData":     { "phases": [ { "manpowerRecover": 160, "decorationLimit": 1000 }, …, 200/5000 ] },
  "manufactStationBuff": 0.1,                     // 制造站每多 1 人的基础效率（非心情）
  "comfortManpowerRecoverFactor": 25,            // 宿舍氛围→回复系数（=0.0004 的来源之一）
  "manufactManpowerCostByNum": [0, 0, -5, -10],   // 制造站按人数的心情消耗修正

  "buffs": {                                       // 755 条 buff 定义（去重后的“技能效果”）
    "control_mp_lonely[000]": {
      "buffId":      "control_mp_lonely[000]",
      "buffName":    "公事公办",
      "buffIcon":    "control",        "skillIcon": "bskill_ctrl_cost_mlynar",
      "buffCategory":"FUNCTION",       // FUNCTION(421) / RECOVERY(86) / OUTPUT(248)
      "roomType":    "CONTROL",        // CONTROL/POWER/MANUFACTURE/TRADING/WORKSHOP/
                                       //   TRAINING/DORMITORY/HIRE/MEETING
      "description": "进驻控制中枢时，<$cc.c.room1>部分设施</>…",  // ★ 唯一文本来源
      "targets": [], "sortId": …
    }, …
  },

  "chars": {                                       // 429 名干员 ↔ buff
    "char_4064_mlynar": {
      "charId": "char_4064_mlynar",
      "buffChar": [                                // 一个元素 = 一个基建技能槽
        { "buffData": [ { "buffId": "control_mp_cost[008]",
                         "cond": { "phase": "PHASE_0", "level": 1 } } ] },
        { "buffData": [ { "buffId": "control_mp_lonely[000]",
                         "cond": { "phase": "PHASE_2", "level": 1 } } ] }
      ]
    }, …
  }
}
```

要点与坑：

- **`cond.phase`**：`PHASE_0/1/2` = 精英 0/1/2；**`cond.level`** = 该技能可用所需的最低等级（多为 1，三星满级技能为 30）。
  它同时是「解锁」和「提升」的门槛；仓库**不区分**二者。
- **β 替换 α 需要自己推断**：仓库把 α、β 当成两个独立 buff（如 火神 `manu_prod_spd&limit&cost[000]` PHASE_0 / `[001]` PHASE_2），
  没有 `replaces` 字段。本项目 `operators.txt` 的 `enhanced` 列就是这一步推断的结果——**保留它，别指望从仓库直接读**。
- **buffId 里的 `[ ]`**：仓库是 `control_mp_cost[008]`，本项目 CSV 里是 `control_mp_cost_008`（`[`→`_`、`]`→删）。
  规则已核对：**209/209 一一对应，无歧义**。
- **描述里的富文本标记**：`<@cc.kw>12</>`（关键字）、`<$cc.c.room1>部分设施</>`（术语引用）、`<@cc.vup>+0.1</>`（增益）。
  去掉标记的正则：`re.sub(r'</?(?:@cc\.\w+|\$cc\.\w+)>', '', s)`。
