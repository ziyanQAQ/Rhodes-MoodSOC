# 施工总览

## 1. 文档定位

本目录描述从设计契约到可运行实现的施工顺序。明确标注为已实现的部分以源码和黑盒验证为准，其他接口仍是规划。行为规则不得在本目录重新定义：

- 分层与依赖：[`../架构设计.md`](../架构设计.md)
- 功能归属与用例：[`../功能模块.md`](../功能模块.md)
- 入宿完整规则：[`../入宿逻辑.md`](../入宿逻辑.md)
- 程序 API、Worker 与 DTO：[`../协议格式.md`](../协议格式.md)
- 游戏数据事实：干员、技能、设施文档，以及上游 `Kengxxiao/ArknightsGameData/zh_CN/gamedata/excel/`

## 2. 施工顺序

```text
data → domain → application → infrastructure → presentation
                         ↘ test/黑盒验收贯穿各阶段
```

依赖顺序不是目录强制顺序，而是允许的知识和调用方向。`infrastructure` 是适配器层，依赖 application 定义的端口；它不能成为 domain 的依赖。presentation 只能通过 application 用例读写业务状态。

| 阶段 | 文档 | 入口条件 | 出口条件 |
|---|---|---|---|
| 0 | 本文 | 规则真源和协议真源已确认 | 文件树、版本策略和验收顺序明确 |
| 1 | [`01-data层施工.md`](01-data层施工.md) | 已确认上游数据版本 | 已完成来源保真目录校验/生成/冻结和文件 Reader；技能语义仍待建模 |
| 2 | [`02-domain层施工.md`](02-domain层施工.md) | data 的只读目录接口稳定 | 规则可脱离 UI 计算，领域不变量可测试 |
| 3 | [`03-application层施工.md`](03-application层施工.md) | domain 命令和快照稳定 | 用例、版本、查询投影和错误映射稳定 |
| 4 | [`04-infrastructure层施工.md`](04-infrastructure层施工.md) | application 端口明确 | Worker、程序 API、目录和存储适配器可替换 |
| 5 | [`05-presentation层施工.md`](05-presentation层施工.md) | 协议与查询 DTO 稳定 | UI 设置、回放和曲线均不含业务规则 |
| 6 | [`06-test与验收.md`](06-test与验收.md) | 任一实现阶段准备开始 | 黑盒契约、回归、文档和发布门禁齐备 |

## 3. 统一施工规约

### 3.1 变更前流程

1. 阅读当前源码、文档和测试；若尚无源码，只能把设计文档作为契约。
2. 对用户提交具体方案：文件、接口、行为、影响、验证和待裁决项。
3. 获得明确同意后才修改。
4. 若发现范围、规则或外部副作用变化，暂停并重新请求裁决。

### 3.2 Module 与 seam 规约

- 每个 Module 只暴露完成职责所需的最小 Interface；不要把内部实体、数组或可变对象泄漏给调用者。
- Seam 放在会发生变化的地方：目录来源、规则策略、结果存储、Worker/HTTP 传输和 UI 框架均可替换。
- Adapter 只做格式、生命周期和外部错误转换，不复制领域公式。
- Interface 同时是调用契约和黑盒测试面，必须写明不变量、顺序、错误模式、配置和性能限制。
- 稳定关联只能使用 ID；显示名、数组位置和运行时对象身份不是持久化关联。

### 3.3 数据与版本规约

- 未知的技能原文、数值、精英化/等级、阵营成员、设施集合、全局常量或机制术语，先查上游仓库，不能猜测或照抄二手资料。
- 原始数据、规范化数据和运行时对象分离；运行时不得修改目录记录。
- 模拟输入冻结后才执行；结果发布后不可变。
- 内部计算使用十进制定点语义；跨层协议使用十进制字符串。

## 4. 推荐文件树

```text
src/
  data/          # 目录装配与版本化静态数据
  domain/        # 实体、值对象、规则和不变量
  application/   # 用例、端口、DTO、结果投影
  infrastructure/# Worker/API/文件/缓存等 Adapter
  presentation/ # Controller、View model、UI 组件
test/
  contracts/     # 跨 Adapter 的黑盒协议测试
  domain/        # 通过领域 Interface 的行为测试
  application/   # 用例和查询黑盒测试
  adapters/      # Worker/API/导入映射测试
  ui/            # 设置与回放交互测试
```

实现前可以调整路径，但必须说明原因并同步本文和 AGENTS.md；目录结构不能改变依赖方向。

## 5. 阶段交付门禁

每个阶段依次执行：先在 `test/` 写黑盒契约测试 → 运行并确认失败原因 → 实现 → 运行测试 → 更新受影响文档 → 检查 Git 差异。纯文档阶段没有可执行逻辑，不创建伪测试；改用 Markdown 结构、本地引用、协议示例、规则与术语一致性检查。

阶段完成后必须提醒用户裁决：是否更新受影响 `documents/`、`AGENTS.md`、未来根 `README.md`，以及是否初始化/暂存/提交 Git；提交前确认仓库边界和具体文件。
