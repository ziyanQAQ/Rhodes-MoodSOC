# 11 · 程序接口（`api/`）

> 本文属于 `documents/`（**文档**目录）。代码在 `api/`，状态在 `store/session.py`，
> 计算在 `mood_soc/`，数据在 `data/`。
>
> **一句话**：`api/` 把图形界面能做的事**全部**暴露成「JSON 进 / JSON 出」，
> 供外部程序（主要是 Rust 侧求解器）调用；**不依赖 tkinter**，无图形环境照样跑。

---

## 1. 为什么要它 / 边界在哪

以前"图形界面能做的一切"只存在于 `ui/app.py`（tkinter 窗口的实例方法）里：
想批量算 20 套布局，只能手点 20 次；想从别的语言调用，根本没有入口。

现在分三层，**同一个 `Session`**：

```
        ui/app.py（tkinter 视图）        api/ops.py（36 个 op）
                 │                              │
                 └──────── store/session.py ────┘   ← 状态与重算的唯一住处
                                   │
                    mood_soc/（纯计算） + data/（数据）
```

`ui` 与 `api` **互不 import**（有测试盯着：`tests/test_layers.py`），
两边都只经 `store.Session` 与 `mood_soc` 的公开 API 做事 ——
所以"界面算出来 8.4、API 算出来 9.1"这种分叉在结构上就不可能出现，
`tests/test_api_ops.py::Test数值同源` 还会逐位比对。

## 2. 两种用法

### 2.1 常驻进程（**推荐**）

```bash
python -m api.server            # stdin/stdout 都是 NDJSON；stderr 是日志
python -m api.server --quiet
```

**为什么推荐**：`data/skills_data.py`（755 条 buff / 250 条 clause 的对象图）
import 一次约 **0.3~0.5 s**；一次性调用每次都要付这笔钱，常驻只付一次。
之后每次 `moods` 的耗时就是"重算一轮"的量级（周期 1 约 0.2 s、周期 3 约 0.7 s）。

```jsonc
// stdin（一行一条）
{"id": 1, "op": "capabilities"}
{"id": 2, "op": "load_schedule", "args": {"facilities": [ ... ]}}
{"id": 3, "op": "set_timeline", "args": {"cycles": 2}}
{"id": 4, "op": "moods", "args": {"at": [0, 8, "24:00"], "include_trajectory": true}}
{"id": 5, "op": "quit"}
```

```jsonc
// stdout（一行一条，与请求同序）
{"op":"capabilities","ok":true,"protocol":3,"id":1,"data":{...}}
{"op":"load_schedule","ok":true,"protocol":3,"id":2,"data":{...}}
...
{"op":"quit","ok":true,"protocol":3,"id":5,"data":{"bye":true}}
```

**会话是有状态的**：一次进程 = 一个 `Session`，调用顺序有意义：

```
capabilities → load_json / load_schedule / load_file → set_*（改设置）→ moods / layout_at / closure
```

`load_*` 会**重置**会话（起点心情、锚点、设置全部从新排班重新读）。

### 2.2 一次性调用

```bash
python -m api.cli --op capabilities

# 内联布局 → 所有干员心情（此刻 + 8h + 周期末 + 曲线 + 红脸 + 瓶颈）
python -m api.cli --op load_schedule \
  --args '{"facilities":[{"type":"制造站","level":3,"operators":["泡泡","黍","路人甲"]}]}' \
  --then '{"op":"moods","args":{"at":[0,8,"24:00"],"include_trajectory":true}}'

python -m api.cli --op load_file --args '{"path":"my_layout.json"}' --then '{"op":"moods"}'
cat req.json | python -m api.cli --op moods --args @-        # args 从管道读
python -m api.cli --script steps.json                        # 一串步骤，共享会话
python -m api.cli --op moods --all                           # 打印每一步的完整响应
```

`--args` 三种写法：内联 JSON / `@文件` / `@-`（stdin）。
成功 = 最后一步的结果打到 **stdout**；失败 = 协议错误对象打到 **stderr** 且退出码 1
（这样 `moods=$(python -m api.cli ...)` 不会把错误当数据）。

## 3. 线协议（**稳定面**）

| 请求字段 | 必填 | 说明 |
|---|---|---|
| `op` | ✓ | 操作名，见 §4 |
| `args` | | 该操作的参数对象（缺省 `{}`） |
| `id` | | 原样回显，便于调用方配对（任意 JSON 值） |

| 响应字段 | 说明 |
|---|---|
| `id` / `op` | 与请求相同（`id` 缺省则不回填） |
| `ok` | `true` 成功 / `false` 失败 |
| `protocol` | 协议版本号，**每个响应都带**（长连接里随时能发现版本漂移） |
| `data` | 成功时的结果 |
| `error` | 失败时的 `{"type","message"}` |

**错误类型**：参数类问题（`ValueError` / `KeyError` / `TypeError`）→ `"bad_request"`；
其余异常用类名。**任何 op 出错都不会杀掉常驻进程**，下一条请求照常处理
（坏 JSON 也一样，回一条 `op: null` 的错误响应）。

**先握手**：

```jsonc
{"id": 1, "op": "capabilities"}
// → data = {"protocol": 3, "operations": [36 个 op 名], "stateful": true, "loaded": false,
//           "docs": "documents/11-程序接口.md"}
```

`protocol` 与预期不一致就**别继续**——否则双方会悄悄按不同语义算。
协议改动（增删 op、改字段语义）时 `api/__init__.PY` 的 `PROTOCOL_VERSION` 加一。

**时刻的两种写法**（所有带时刻的 op 通用）：

- **绝对小时**：`0` / `8.5` / `"36"` —— 从周期起点算起，跨周期递增；
- **钟点字符串**：`"08:30"` / `"1:05"` / `"24:00"` —— **周期内**时刻
  （`"24:00"` = 周期末），与界面上的时刻标签同义。
  ⚠️ `start_clock`（初始时间点）只影响**显示**，不影响这里的换算。

| `operator_names` | 全部可选干员名 | `extra`（额外补充的名字） |
| `operator_detail` | 某人：房间 / 练度 / 解锁技能数 / 此刻心情与速率 / 红脸区间 | `name`✓、`shift_index`、`at` |

| `entry_candidates` | 谁可能触发进驻事件、可以和谁换 | — |

### 载入（4）

| op | 作用 | 关键参数 |
|---|---|---|
| `load_schedule` | **内联布局** → 单班排班（最常用） | `facilities`✓、`hours`、`label`、`entry_events`、`idle_to_dorm`、`initial_global` |
| **`load_json`** | **内联 JSON**（任意受支持格式，含 v3 求解输出）→ 排班；**不落临时文件** | `data`✓、`hours`、`cycle_hours`、`cycles`、`apply_file_settings`、`entry_events`、`idle_to_dorm` |
| `load_file` | 按**一个文件**载入（4 种格式自动识别） | `path`✓ |
| `load_files` | 按**多文件**载入（12h / 6h / 6h 三个文件那种） | `paths`✓ |

`facilities` 的元素与本工具场景 JSON 完全同构：
`{"type": "制造站", "level": 3, "name": "制造站#1", "operators": [...], "deputies": [...], "enabled": true}`，
干员可以是名字字符串，也可以是 `{"name","mood","elite","level","skill_ids","factions"}` 对象。
顶层还可带 `entry_events` / `idle_to_dorm` / `initial_global` / `detached`（与场景 JSON 同义）。

**`load_json` 的默认口径**（与界面 / `load_file` 不同，按"外部求解器调用"的需求收窄）：

| 项 | 默认 | 说明 |
|---|---|---|
| 文件里的开关（如 v3 的 `Fiammetta.enable`） | **不继承** | `apply_file_settings: false`；换干员必须手动配置 |
| 闲置入宿 | **开** | 本项目默认四级优先级；传 `idle_to_dorm: false` 关掉 |
| 换心情（进驻事件） | **关** | 传 `entry_events: true` 才结算 |
| 周期 | 取文件里的班次时长之和 | 如 `12/6/6` → 24h；`cycles` 默认 1（＝正好一个完整周期） |

它与 `load_file` 走**同一条装配路径**（`store.schedule.load_schedule_from_imports`），
所以同一份 JSON 走文件或走内存，数值**逐位相同**（`tests/test_api_ops.py::Test求解器适配` 盯着）。

### 不在基建：一次完整调用

```bash
# 把"这一刻没上班、也不在宿舍"的人列出来，并给其中一个设心情 12
python -m api.cli --op load_file --args '{"path":"resources/arknights-infra-schedule-maa.json"}' \
  --then '{"op":"bench_names","args":{"shift_index":1}}' \
  --then '{"op":"set_detached","args":{"add":["某人"],"moods":{"某人":12}}}' \
  --then '{"op":"moods","args":{"at":[0,12]}}'
```

```jsonc
// bench_names → data
{"detached": ["歌蕾蒂娅", "寒芒克洛丝"],      // 名单点名的 ∪ 整个排班都没排到位置的
 "explicit": ["歌蕾蒂娅"],                    // 名单里**显式**写的（会写进 JSON 顶层 detached）
 "stationed": ["泡泡", "黍"],                 // 在某个班次房间里的
 "shift_index": 1,
 "not_in_shift": ["歌蕾蒂娅", "寒芒克洛丝"]}  // 第 1 班没排到位置的人（界面那一段的来源）
```

⚠️ `add` 默认 `remove_from_slots: true` —— 加进名单时会把她**从所有班次的位置上摘掉**
（"名单里的人 ↔ 不在任何房间里"是一条不变式）。要保留位置就传 `remove_from_slots: false`。

## 5. `moods` 的返回（核心输出）

```jsonc
{
  "operators": ["泡泡", "黍", "路人甲", "板凳甲"],
  "cycle_hours": 24, "cycles": 2, "total_hours": 48,
  "moods": {                       // 键 = 绝对小时；值是"那一刻的全员心情"
    "0":  {"泡泡": 24, "黍": 24, "路人甲": 24, "板凳甲": 12},
    "8":  {"泡泡": 23.6, ...},
    "24": {"泡泡": 19.2, ...}
  },
  "trajectory": {                  // include_trajectory=true 才有
    "times": [0, 0.25, 0.5, ...],  // 节点即"事件时刻"（见 10-图形界面.md §4.1）
    "operators": {"泡泡": [24, 23.99, ...], "板凳甲": [12, 12, 12, ...]}
  },
  "red_face": {                    // 有红脸段才出现
    "泡泡": [[21.0, 24.0]]
  },
  "layout_sustain_hours": 21,      // 第一个人红脸的时刻（null = 整段没人红脸）
  "bottleneck": "泡泡"
}
```

数值口径：**6 位小数**舍入、`inf → null`（与 CLI / 文件输出同一套，见 `store/serialize.py`）。
轨迹节点是"速率会变的时刻"（班次边界 / 红脸 / 心情阈值 / 两人交叉），节点之间**严格线性**，
所以调用方按线性插值取值与引擎结果一致（`moods` 就是这么算的）。

**「不在基建」的人**（`set_detached` / 场景顶层 `detached`）也会出现在
`operators` / `moods` / `trajectory` 里，数列是**一条平线**（等于起点心情，速率为 0）。
他们**不参与任何技能计数**（不在房间列表里）——见 `bench_names` op 与
`moods` 的参数说明。

## 6. `layout_at` / `closure` 的返回

### 6.1 `layout_at`：时间节点 → 整座基地

```jsonc
{"at": 8, "cycle": 1, "in_cycle": 8, "shift_index": 1, "shift_label": "1. alpha/beta · 12h",
 "rooms": [                       // 房间顺序 = 布局顺序（未排序），索引 1 基、位次 1 基
   {"index": 1, "type": "贸易站", "name": "贸易站#1", "level": 3, "capacity": 3,
    "enabled": true,
    "operators": [{"slot": 1, "name": "但书", "mood": 22.4, "rate": 0.85,
                   "elite": 2, "level": 30}],
    "deputies": []}               // 副手（不占位、不消耗心情）
 ],
 "detached": [{"name": "歌蕾蒂娅", "mood": 24, "rate": 0}],   // 不在基建：心情一条平线
 "moods": {"但书": 22.4, "歌蕾蒂娅": 24, ...}}
```

⚠️ **读的是引擎那份布局副本**（`Trajectory.world_at`）——换心情 / 闲置入宿换过人之
后的**真实**排布，**不是**你导入的那份快照。两者在换过人之后必然不一样
（`AGENTS.md` 第 20 条那个坑）。落在班次边界取**右侧**。

### 6.2 `closure`：这套布局能不能长期跑

```jsonc
{"cycles": 3, "cycle_hours": 24,
 "cycle_start_moods": {"1": {"泡泡": 24, ...}},          // 第 1 周期起点
 "cycle_end_moods": {"1": {...}, "2": {...}, "3": {...}}, // 每个周期末（＝下一轮开局）
 "converged": true, "converged_from_cycle": 2,            // 第 2 与第 3 周期末逐人相同
 "delta_last_vs_first": {"泡泡": 0, ...},                 // 周期末 − 周期初（<0 = 越跑越累）
 "layout_sustain_hours": 21.5, "bottleneck": "泡泡",      // null = 整段没人红脸
 "red_face": {"泡泡": [[21.5, 24.0]]},
 "verdict": "稳定但有人红脸：第 2 周期起周期末不再变化，但 泡泡 在 21.5h 就红了脸"}
```

口径：`cycles` 是**心情跨周期连续**（`simulate_schedule` 的同一语义），所以"周期末"就是
下一轮的开局心情；相邻两周期的周期末逐人相同（容差 1e-9）即认定进入固定点。
⚠️ 这个 op **会改会话的 `cycles` 并重算**（与 `moods` 的 `cycles` 参数同一口径）。

## 7. Rust 侧怎么接（样例）

最小可用（常驻，一次握手 + 一次调用）：

```rust
use std::io::{BufRead, BufReader, Write};
use std::process::{Command, Stdio};

fn main() -> std::io::Result<()> {
    let mut child = Command::new("python")
        .args(["-m", "api.server", "--quiet"])
        .current_dir("E:/code_h/python/Rhodes-MoodSOC")   // 建议用环境变量传
        .stdin(Stdio::piped()).stdout(Stdio::piped()).stderr(Stdio::inherit())
        .spawn()?;
    let mut stdin = child.stdin.take().unwrap();
    let mut out = BufReader::new(child.stdout.take().unwrap());

    let send = |stdin: &mut _, line: &str| { writeln!(stdin, "{line}").unwrap(); stdin.flush().unwrap() };
    let read = |out: &mut BufReader<_>| {
        let mut s = String::new();
        out.read_line(&mut s).unwrap();
        s
    };

    send(&mut stdin, r#"{"id":1,"op":"capabilities"}"#);
    let caps: serde_json::Value = serde_json::from_str(&read(&mut out)).unwrap();
    assert_eq!(caps["data"]["protocol"], 3);              // 版本不一致就别继续

    // v3 求解结果**原样**塞进来（不落临时文件）
    let req = r#"{"id":2,"op":"load_json","args":{"data":{ ... }}}"#;
    send(&mut stdin, req);
    let _: serde_json::Value = serde_json::from_str(&read(&mut out)).unwrap();

    send(&mut stdin, r#"{"id":3,"op":"moods","args":{"at":[0,8,24]}}"#);
    let moods: serde_json::Value = serde_json::from_str(&read(&mut out)).unwrap();
    println!("{}", serde_json::to_string_pretty(&moods["data"]).unwrap());

    send(&mut stdin, r#"{"id":4,"op":"layout_at","args":{"at":8}}"#);
    let _: serde_json::Value = serde_json::from_str(&read(&mut out)).unwrap();

    send(&mut stdin, r#"{"op":"quit"}"#);
    let _ = child.wait()?;
    Ok(())
}
```

三条实践经验：

1. **路径别硬编码**：用环境变量（如 `RHODES_MOODSOC_ROOT`）传仓库根，
   `current_dir` 指过去即可（本包一律用绝对/相对包名 import，不依赖 cwd）。
2. **每行 flush**：服务端已做（`stdout.flush()` 每行），Rust 侧 `read_line` 不会卡。
3. **别把 stderr 丢掉**：`--quiet` 时它基本安静，但出错信息（哪个 op 为什么失败）
   只在 stderr 上，`Stdio::inherit()` 或自己收着都行。

不想管进程生命周期时，用一次性 CLI 更省事：

```rust
let out = Command::new("python")
    .args(["-m", "api.cli", "--op", "load_file", "--args", r#"{"path":"layout.json"}"#,
           "--then", r#"{"op":"moods","args":{"at":[8]}}"#, "--quiet"])
    .output()?;                        // stdout = 结果 JSON；stderr = 错误
```

## 8. 加一个新 op 的步骤

1. 在 `api/ops.py` 写 `def op_xxx(session, args) -> dict`：
   **只做"取参 → 改 Session → 返回结果"**，不自己存状态、不算心情；
   参数用 JSON 原生类型，进来就 `to_decimal()`；数值出参一律过 `_num()`；
2. 加进 `OPERATIONS` 表（表就是契约，`capabilities` 会报给调用方）；
3. 在 `tests/test_api_ops.py` 里加一条黑盒断言（走 `handle(...)`，别直接调 Session）；
4. 若改变了已有 op 的语义 / 删了 op → `api/__init__.py` 的 `PROTOCOL_VERSION` +1；
5. 更新本文 §4 的表格。

**不许**在 `api/` 里 import `ui` / `tkinter`（`tests/test_layers.py` 会报错）。
