# 07 · 设计史与重构决策

> 本文属于 `documents/`（**文档**目录）。数据在 `resources/`，代码在 `mood_soc/`。
> 文中的 `§X.Y` 沿用原 `AGENTS.md` 的稳定编号，映射表见 `documents/README.md`。

---

> 文档目的：回答「当前心情机制**是否具备可拓展性**」，并给出重构设计。
> 结论先行：**数据层已经可拓展（六轴模板就绪），运行时不可拓展**——所以重构范围是**运行时**
> （布局模型 / 效果派发 / 记录层），**不是**重写数学层（`battery.py`）与数据管道。

## 一、诊断结论

| 维度 | 状态 | 证据 |
|---|---|---|
| 数学层（安时积分） | ✅ 可拓展 | `battery.py` 与游戏规则无关，纯钳位积分 |
| 数据层（技能库） | ✅ 可拓展 | 六轴模板已就位：242 clause 全挂 `template_id`，755 buff 全登记 |
| **运行时派发** | ❌ **不可拓展** | `template_id` 在数据里，**`rules.py` 从不读它**；派发靠 `SkillKind` 的 if/else |
| **布局模型** | ❌ **不可拓展** | `get_facility()` 只返回第一个同类型设施；无容量 / 副手 / 工作状态 / 活动室 |
| **记录系统** | ❌ **不存在** | 只有一个 `net_rate` 数字 + `note` 原文；无法回答"这个速率由谁贡献、按什么规则合成" |
| 特殊机制 | ⚠️ 半成品 | 阵营表曾手工且**错误**（已修）；26 种变量（热情值等）无载体 |

### 1.1 运行时派发：模板与代码双轨

- 数据侧：`Skill.template_id ∈ {M01…M17, X01…X11}`（六轴分类，已完整）。
- 代码侧：`SkillKind ∈ {self_consume, facility_consume, …, eliminate_self}`（8 种在用）。
- **两者互不知情**：`rules.py` 里 `SkillKind.` 出现 15 次，`template_id` 出现 **0 次**。
- 后果：新增一个机制 = 改 `SkillKind` 枚举 + 在 `compute_consumption`/`_work_recovery`/`_dorm_recovery`
  **三处**加分支 + 在生成器 `FAMILY_KIND` 加映射 + 同步两份文档。这就是"不可拓展"的定义。

### 1.2 聚合规则散落成硬编码

| 规则（轴 F） | 当前实现位置 | 问题 |
|---|---|---|
| F1 求和 | 各函数内 `total +=` | 与环境耦合 |
| F2 同种取最高 | `_dorm_recovery` 内 `max(...)` ×3 | 写死；无法表达"哪几种算同种" |
| F3 跨干员取最高 | `_work_recovery` 内 `grouped[group] = max(...)` | 后加的特例 |
| F6 池分配 | `_icebrew_recovery` 独立函数 | 冰酿专属，不通用 |
| F7 归零优先 | `_dorm_recovery` 顶部 `exclusive` 短路 | 菲亚梅塔专属，不通用 |

→ 没有统一的 `Accumulator`，每加一条叠加规则就多一处 `max/min/短路`（`rules.py` 里 `max(` 9 次、`min(` 4 次）。

### 1.3 布局模型：只支持"每种设施一个"

```python
def get_facility(self, ftype):   # 只返回第一个
```

实测：布局放 2 个制造站 + 2 个宿舍时，`facility_of()`（遍历全部）**能**逐干员算对，
但任何"按设施类型聚合"的技能无处落地。上游需求规模（755 buff 实测）：

| 需求 | 上游条数 | 现状 |
|---|---|---|
| 「处于工作状态」 | 15 | 无概念：默认所有进驻者都在工作 |
| 「不包含副手」 | 29 | 无概念 |
| 「活动室使用者」 | 23 | `FacilityType` 里**没有 PRIVATE**（上游 `rooms` 有） |
| 「每有 N 间发电站」 | 2 clause | 无"按类型计数"能力 |
| 「所有宿舍 / 所有制造站」 | 5 / 7 | 靠逐设施迭代侥幸可用，非通用能力 |
| 设施等级折算（宿舍每级、办公室等级） | 4 clause | `Facility.level` 有，但技能读不到 |

### 1.4 一个已确认的错误：加工站 / 训练室被当成普通工作设施

```
加工站 路人X  消耗=0.75   训练室 路人X  消耗=0.75     ← 实测
```
`compute_consumption` 只排除宿舍，其余一律 `BASE_CONSUMPTION = 1.0`。
但**加工站的心情是按次消耗（配方心情消耗）**，不搓材料就是 0/h；训练室的协助位另有规则。
同时这 9 条训练室 + 34 条加工站心情技能**根本没进技能库**（登记在台账里，`modeled=no`）。

### 2.1 五个核心抽象

**(1) `layout.py` —— 布局是一等公民**

```python
@dataclass
class Facility:
    ftype: FacilityType
    name: str                     # "制造站#2"（同类型可多个）
    level: int = 1
    operators: list[Operator] = []      # 进驻（占位）
    deputies: list[Operator] = []       # 副手（不占位，被"不包含副手"排除）
    slots: int = 0                      # 容量（0=不校验）
    atmosphere: Decimal | None = None   # 仅宿舍
    enabled: bool = True                # 停电/未建造

class BaseLayout:
    def of_type(self, ftype) -> list[Facility]      # 多房间
    def count_of_type(self, ftype) -> int           # 每有 N 间
    def all_dormitories(self) -> list[Facility]     # 所有宿舍
    def operators_in(self, ftypes) -> list[Operator]
    def working_operators(self, ftypes) -> list[Operator]   # "处于工作状态"
    def base_operators(self, include_deputies=False, include_activity_room=False)  # 基建内每有 1 名
```
新增 `FacilityType.PRIVATE`（活动室）。`get_facility()` 保留但标 deprecated（兼容旧调用与场景）。

**(2) `effects.py` —— 模板驱动的效果管道**

```python
class Bucket(Enum): CONSUME, RECOVER, EVENT

@dataclass(frozen=True)
class Effect:
    template: str          # "M08"
    bucket: Bucket
    stacking: Stacking     # 轴 F
    scope: Domain          # 轴 B
    targets: Target        # 轴 C
    def contribute(self, ctx: EffectContext) -> Iterable[Contribution]: ...

EFFECTS: dict[str, Effect]      # template_id -> handler
```
`rules.py` 退化为编排：
```python
def compute_recovery(world, op, facility):
    acc = Accumulator()
    for skill, owner in active_skills_reaching(world, op, facility):
        for c in EFFECTS[skill.template_id].contribute(ctx):
            acc.add(c)
    return acc.total(Bucket.RECOVER)
```
**新增机制 = 数据（模板行）+ 一个 handler**，不再改三处函数。

**(3) `Accumulator` —— 轴 F 统一落地**

```python
class Accumulator:
    def add(self, c: Contribution) -> None
    def total(self, bucket) -> Decimal
```
按 `stacking` 分组合并：`SUM` / `SAME_KIND_MAX`（同 template 取最高）/
`CROSS_OWNER_MAX`（同 `max_group` 内先按 owner 求和再取最高）/ `POOL`（平分给 recipients）/
`ZERO_PRIORITY`（归零优先）。
→ `_icebrew_recovery`、菲亚梅塔短路、`max_group` 特例**全部消失**，变成数据。

**(4) `ledger.py` —— 心情记录系统（本轮 #3 的核心诉求）**

```python
@dataclass(frozen=True)
class Contribution:
    bucket: Bucket
    template: str          # "M08"
    skill_id: str          # "control_dorm_rec_000#1"
    skill_name: str        # "领袖"
    owner: str             # "焰影苇草"
    target: str            # "刺玫"
    value: Decimal
    scope: str             # "所有宿舍（同种取最高）"
    stacking: Stacking
    detail: str            # 人类可读

@dataclass
class MoodLedger:
    operator: str
    consume: list[Contribution]
    recover: list[Contribution]
    def explain(self) -> str        # 中文逐条解释 + 合计 + 净速率
```
`MoodResult` 增加 `ledger` 字段；CLI 增加 `--explain`。
→ 直接回答"**为什么这个干员的净速率是 0.7**"，也让测试可以断言"贡献构成"而不只是数字。

**(5) `variables.py` —— 变量账本**

```python
@dataclass
class VariableLedger:
    values: dict[str, Decimal]      # "热情值" -> 20
    sources: dict[str, list[str]]   # 谁产的
```
技能声明 `produces` / `consumes`；阈值条件读它（`热情值 >= 40`、`每有 8 点热情值`）。
→ 解锁 43 条变量相关 buff + 剩余 31 条 `partial/hold` 中的大部分。

  **判定依据此前只能靠猜，现在有上游结构可依。**

### P4a —— 可数条件 + 两处语义/实现修正（已完成）

12 条「每有 N 个什么」的子句全部启用（`basis` 参数 + `variables.basis_count`，新增 5 个基准）。
过程中查出并修掉两个**真问题**：

1. **「同种效果取最高」的粒度错了**。上游写「（叠加后的**最终值**同种效果取最高）」
   → 同一技能的多个分句要先求和。旧实现按单个分句取 max：
   死前必做清单 Lv5 得 0.15（正确 0.25）、倾谈者/寻同路人/无瑕心/柔和微光/独处 同类偏低。
   修法：`MoodLedger.total()` 的 `SAME_KIND_MAX` 改为「按 (持有者, skill_id) 先聚合分句，再取最高」。
2. **β 替换链把「同一技能的分句」当成链上环节**，导致额外分句"替换"掉自己的基础分句——

#### P6 修订：表格从"每行一个 Frame"改成"所有单元格共享一个 grid"

「干员与心情」的表格原来是**每行一个独立 `Frame`**，行里各列各自 `grid`。当时以为"行内
等宽 = 对齐"，实测是错的：**grid 的列宽是按容器算的**，所以列宽只在行内成立、跨行照样差
（空位行的 `—` 落在 x=570、「不在基建」行落在 x=561 —— 肉眼就是"没对齐"）。

改法（三件事，缺一件都不齐）：

| # | 改什么 | 为什么 |
|---|---|---|
| 1 | 所有单元格直接 `grid(row=行号, column=列)` 到**共享的 `inner`** | 列宽只有一个来源 |
| 2 | `TABLE_COLUMNS` 的非拉伸列写**像素**（96/40/56/72），不用 `Label(width=N)` | 那是**字符宽**，粗体表头与常规体数据宽度不同 → 差几像素 |
| 3 | 干员列/说明列一律给 `wraplength` | 不给就被最长名字撑到 307px，列宽逐行不同 |

代价与随之而来的三个坑（都写进 `10-图形界面.md`）：**没有行 Frame 了** ⇒
① 滚轮要**逐格 `join`**（bindtags 链不含父控件，漏挂的表现是"停在文字上滚不动"）；
② 悬停/底色要刷 `r["cells"]` 整行；③ `row=` 用的是 `r["grid_row"]`（`row=0` 是表头那一行，
写字面量 `0` 会把控件叠到表头上）。

**每阶段的硬约束**：黑盒测试必须全绿；新增机制必须走"模板 + handler"，不得再往 `rules.py` 塞分支（沿用 P1~P5 的规矩）。

> 本项目**匹配那套布局**并生成它的**完整心情变化周期**；界面只负责让人看，
> **交付面是 `api/`**。接入说明见 `12-v3接入.md`。

**一、适配面：三个新 op（协议 1 → 2）**

| op | 解决什么 |
|---|---|
| `load_json` | v3 **内存里**的求解结果直接喂进来（4 种格式自动识别，含 `{"result": …}` 信封），不必再落临时文件 |
| `layout_at` | 「某时刻 → **整座基地的布局 + 全员心情**」：每间房 / 位次 / 在位干员 / 不在基建名单 |
| `closure` | 「这套布局**能不能长期跑**」：连跑 N 个周期，周期末心情逐人不再变化即进入固定点 |

按文件（`load_file`）与内联（`load_json`）**共用同一条装配路**
（`store.schedule.load_schedule_from_imports`），同一份 JSON 两条入口必须逐位相同。

**默认口径**（用户裁决）：换干员**默认关**（且**不继承**文件里的 `Fiammetta.enable`）、
闲置入宿**默认开**（本项目四级优先级）、周期**取文件里的各班时长**。
"闲置入宿默认开"**当时**只作用于 `load_json` 入口（界面与 `load_file` 维持原默认"关"）；
⚠️ 这条已被 **P8 第九节**推翻 —— 现在是**全项目统一默认开**。

**二、顺手修掉的两个真问题**

1. **多周期下"她在哪"会错位**（分两步修完）：
   ① **段内快照**（P7 当时）：布局副本跨周期复用（`worlds[idx]` 只建一次），而闲置入宿
   **就地改这份副本** ⇒ `world_at(t)` 在第 1/2 周期给出第 N 周期的排布
   （实测：第 1 周期宿舍 2 人 vs 第 2 周期 5 人）。于是开着闲置入宿时**每段留一份深拷贝快照**。
   ② **段首重建**（2026-09，用户报"菲亚梅塔心情 20.4 却被换出"）：快照只解决了"读"，没解决"算"——
   副本本身仍被跨周期复用，"第 1 周期把她换出去"于是继承到后面所有周期：那一班开局就没有她、
   **既不重判心情、也没有任何事件**（现场：默认样例 + 换心情 1班龙舌兰/2班巫恋/3班不换 +
   周期数 3，t=42/66 的"班次 3 开局"她凭空不在宿舍）。现在改成 `pristine` + **每段
   `copy.deepcopy` 重建**：位置回排班原样、当班按当时心情重新判定，**心情仍跨周期连续**
   （在 `moods` 里）。代价 ≈ 每段 0.35ms。回归 `test_跨周期位置复位_每周期都重新判定`。
   见 `04-特殊机制.md` 第 30 条。
2. **文档里的 `load_file --args @文件` 是错的**（args 被当成整个文件内容，而 `load_file` 要
   `{"path": …}`）：`11-程序接口.md` / `12-v3接入.md` 里 5 处示例全部改正并逐条跑通。

**三、技能核对从三层加到四层（L4）**

L2 用的是**合成干员 + 手工注入 `skill_id`**，留下两个盲区：

- 它证明"这条技能**定义**对不对"，**没走**"真名 → `DEFAULT_OPERATORS` → 技能槽 → 进流水账"
  这条路（名字没认出来、精英化门槛把技能全挡掉，都能让一位干员在基建里**一条技能都不生效**）；
- 它只核"条件满足时数值对不对"，**没核**"条件不满足时**不该**生效"——而组合技能
  （共事 / 定向 / 阵营 / 变量 / 元修正）最容易错的就是后一半：条件漏判在"满足条件"的场景里
  **数值完全正确**。

于是 L4 分三块：**真名挂载 178/178**、**真名结算 178/178**、**组合双向对照 48/48**（覆盖 9 类）。

⚠️ **L4-c 踩到的坑（记下来，别再犯）**："把搭档**搬走**"会同时改掉**控制中枢的
「中枢 N 人，每人 −0.05」全局减免**，差值就不再只反映那条组合条件——实测德才兼备的差值
从 −0.10 变成 −0.20，**看起来像"引擎多算了一倍"，其实是中枢少了一个人**。
正确手法是**改名 / 摘阵营、人留在原房间**（保持在场人数），
只有「独自一人」「宿舍他人在场」这两类**条件本身就是人数**时才真去增删人。

**四、阈值吸附把曲线压平（用户从卡夫卡的曲线里看出来的）**

用户跑全量测试时注意到卡夫卡的心情曲线有"一小段变化为 0、又没到 24"。查下来是**真 bug**：

- **症状**：示例排班（UI 默认加载的那份）第 2 班宿舍段，`[12.95h, 13.2h]` 同宿舍 **8 名干员**
  一起被压在阈值 **20** 上（速率 ≈ 0）。她在宿舍以 4/h 回复，13:12 该是 **21.0**，实际 **20.0**
  —— **整段低了 1.0**，到 13.9h 才追平；而 14.2h 就住满 24 了，所以 **24h 末值看不出来**，
  只在**曲线中段**可见。
- **定性**：把 `MAX_SEGMENT_HOURS` 从 0.25h 调到 0.05h / 0.01h / 0.001h，曲线**全部回到解析值**。
  **步长不该影响结果** ⇒ 是积分器 bug，不是机制口径。
- **根因**（`store/schedule.py: _next_event`）：阈值吸附表是在**积分之后**应用的，而那一刻 `nxt`
  可能已在一个 `MAX_SEGMENT_HOURS` 之外——只差 1e-26 就跨阈值的人**已经被积分推过去了**，
  再吸附回去等于**把它往回拽**，白扣 `|速率| × 0.25h`。让它更早暴露的是同一函数里
  `snaps = {name: h}` 的**覆盖赋值**：同一步里多人跨阈值时只有最后一个赢家留下，其余人丢吸附、
  这才停在阈值前 1e-26。
- **修法**：只差 `MIN_EVENT_GAP` 就跨阈值的人**当场吸附**（并把这批人报给调用方去重算速率），
  吸附表只留"正好在**本段末尾**跨过"的人；**同一时刻**跨阈值的用 `setdefault` 合并。
- **回归**：`tests/test_ui_schedule_blackbox.py::Test阈值吸附` 三条 —— 解析值（宿舍回复段
  13:12 = 21.0）、同宿舍 8 人阈值处不许有平台、**步长 0.25h 与 0.001h 的曲线必须逐点一致**
  （最后这条才是真正拦住这类 bug 的：它把"算得对"定义成**与积分步长无关**）。
- 口径与现场见 `04-特殊机制.md` 第 35 条。**24h 末值不变**（20.1）；轨迹里少了 1 个由那个
  1e-26 尾巴带出来的多余节点（**132 → 131**），其余节点时序不变 —— 只改节点上的数值。

**四、P5 后台重算：编辑不再冻住界面**（已完成，同批用户口径）

- 旧：任何编辑都在**主线程**同步重算（0.16~1.53s），窗口连重绘都停住；用户感受就是"卡"。
- 新：`ui/app.py: recompute_async()` —— 工作线程跑 `Session.compute_trajectory(inputs)`，主线程

  `Session.recompute()` 拆成三段：`recompute_inputs()`（**冻结**一份可跨线程用的参数包：
  「不在基建」名单先同步进 Schedule、可变的 `initial_moods`/`mood_events`/`entry_per_shift`
  各拷一份；`schedule` 本身是"换新对象"的，直接传引用）→ `compute_trajectory()`（纯计算）

- **连续编辑只落地最后一版**：请求带**代数**，过期的结果直接丢；期间改了就按最新设置再算一代。
- **两个坑（都是实测踩出来的）**：
  ① **落地刷新会盖掉用户正在敲的值**：面板防抖（心情 500ms / 闲置入宿 250ms）还没提交时，
  重算可能先算完并刷新面板 —— 面板按轨迹重写格子，用户输入的那次编辑**整个丢失**

  ② ⚠️ **`decimal` 上下文是线程局部的**：`config.py` 那两行只设到**导入它的线程**，
  工作线程拿到 Python 默认上下文（`prec=28`、但舍入是 `ROUND_HALF_EVEN`）⇒ 末位差 1e-26

  会打印 `RuntimeError: main thread is not in main loop`）。
- 面板侧：闲置入宿的表格内容依赖**新轨迹**，所以设置中心注册

**六、P6a：改「周期数」只算尾部**（已完成，用户口径"先做周期维度"）

- **为什么先量再做**：同一个班次在**每个周期都会重复出现**，所以"编辑 → 最早受影响段"完全取决于改的是什么：

  | 编辑类型 | 最早受影响段 | 7 周期下能省 |
  |---|---|---|
  | 改周期数 7→6 | —— | ~100%（只截断） |
  | 改周期数 6→7 | 第 18 段 | 86% |
  | 改「第 7 周期第 3 班」的锚点 / 逐次设置 | 第 20 段 | 95% |
  | 改**某班布局 / 房间等级 / 练度** | 第 2 段 | **只 10%** |
  | 改初始心情 / 总开关 / `detached` | 第 0 段 | 0% |

  另外实测：多周期跑下来后面几个周期**不是逐位重复**前面的（相邻周期起点差 4~34 人）⇒
  "收敛后直接抄"这条捷径**不可用**（除非容忍数值变化）。
- **做法**：`store.schedule.simulate_schedule(..., continue_from=(上一份轨迹, 它算完的周期数))` ——
  把前缀的 `times/series/marks/seg_worlds/idle_states` 预填进累加器，段循环从 `已算完周期数 × 班数` 起跑；
  周期数变少就传"已算完 = 新周期数" ⇒ 只截断。**能不能增量**由 `Session._inputs_fingerprint()`
  （除周期数外的全部输入）判定：任何别的设置变了就整条重算（用指纹而不是"在每个 setter 里清缓存"，
  少漏一处就是少一个"拿旧轨迹当种子"的静默出错）。`ui/app.py` 的异步重算把 `_fingerprint`
  一起传给 `Session.adopt`。
- **两个坑**（写的时候踩到、都已由回归钉住）：
  ① 种子必须取"**段边界上第一个节点**"的值＝**段首事件之前**的心情 —— 段首的进驻事件在续算时会再跑一遍，
  用 `mood_at(t0)` 会拿到跳变**后**的值 ⇒ 事件被算两遍；
  ② 续算时**不要再加一遍班次标记**（前缀里已经带着；只有全量时才在开头加），红脸标记一律按合并后的曲线重算。
- **实测收益**：7→6 **6.5 ms**（原 1300 ms，200×）、6→7 **217 ms**（约 6×）、7→1 **3.8 ms**；
  "1→7" 与全量持平（18/21 段，不是常见路径）。
- 回归：`Test周期数增量重算`（加/减周期与全量**逐位相同** + 改别的设置后必须整条重算）。全量 **470 → 473**。
- ⚠️ **当时只做"周期维度"**：`continue_from` 收的是**周期数**，所以它只覆盖"改周期数"这一类编辑。
  通用化（收**段数**、切点按逐段指纹算）见下面的 **P6b**。

**七、P6b：通用「从第 k 段续算」**（已完成，用户口径"引擎本体也一起优化"）

- **做法**：`continue_from` 的语义从"已算完的**周期数**"改成"已算完的**段数**"
  （`simulate_schedule(..., continue_from=(上一份轨迹, k))`，`k` 段 = 前 `k` 个班次段），
  P6a 就是它的特例（周期数 × 班数）。切点不再按编辑类型硬判，而是**逐段输入指纹**算出来：
  `Session._segment_signatures()` 给每一段记一条
  `(全局设置摘要, 那一班的布局摘要, 那一段命中的闲置入宿逐次设置, 落在那一段的心情锚点)`，
  与上一份轨迹的指纹逐条比对，取**第一个不同**的下标当切点；比不出来（整份都相同）就是 0 段可省 ⇒ 整条重算。
- **⚠️ 段边界必须落在新时间轴的段起点上**：`continue_from` 只接受"上一个轨迹里正好有该时刻节点"的切点，
  否则抛错、退回整条重算（时间轴改了就属于这种）。
- **三个坑**（都已由回归钉住）：
  ① 种子取"**段边界上第一个节点**"＝**段首事件之前**的心情（`mood_at(t0)` 会拿到跳变**后**的值 ⇒ 进驻事件算两遍）；
  ② **班次标记一律按 `schedule` 重新生成**：它是 `schedule` 的纯函数，而前缀里那份是**旧时间轴**的
     （周期数改小后还多出几段）—— 照搬会出现"第 5 班的标记还在、第 6 班的没了"，与全量对不上；
  ③ 判"输入变了"要用**内容摘要**（`Session._world_digest()`）——`set_training` 是**就地改干员对象**的，
     拿 `id(schedule)` 当判据会漏掉"对象没换、值变了"。
- **实测收益**（示例排班 7 周期 21 段，全量 ≈1.5 s）：
  周期 7→6 **7.6 ms**（只截断）、6→7 **247 ms**（切点 18）、改第 7 周期第 1 班锚点 **264 ms**、
  改第 7 周期第 3 班逐次设置 **96 ms**（切点 20，省 94%）。
- 回归：`Test增量重算`（6 个用例：加/减周期、改某班布局、改末周期锚点、改末周期逐次设置、
  改全局设置必须整条重算；每个都**逐位等于全量**并**钉住切点段号**）。全量 **473 → 476**。
- ⚠️ **仍然救不了"改班次布局"**：布局按班次存、那个班每周期都会出现 ⇒ 切点＝它在**第 1 周期**的出现处，
  7 周期下只省 ~3%（实测 1250 ms）。"改布局也快"要动**引擎本体**（见下）。

**八、还没做的**

- **引擎本体**：`mood_ledger` 每次速率重算都全量重建账本，且 `collect_variables(world)` 在
