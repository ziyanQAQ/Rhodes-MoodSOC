# 心情计算与技能结算规范

## 1. 文档定位

本文是心情数值、设施贡献、技能子句和进驻事件的唯一计算真源。它只描述本项目如何把**已核实的数据目录**和模拟状态转换为心情账本与轨迹；闲置入宿的候选、锁定、位次和执行点规则仍以 [`入宿逻辑.md`](入宿逻辑.md) 为真源，协议字段仍以 [`协议格式.md`](协议格式.md) 为真源。

本文中的事实分为三类：

1. **项目契约**：由本仓库协议或规则文档明确规定，例如心情范围、十进制定点、事件顺序和账本字段。
2. **上游事实**：必须在 [Kengxxiao/ArknightsGameData](https://github.com/Kengxxiao/ArknightsGameData) 的 `zh_CN/gamedata/excel/` 中查证的技能原文、数值、设施属性、解锁条件和成员关系。
3. **待核实**：当前没有足够的一手来源或尚未登记上游版本；不得进入已启用目录或实现默认值。

## 2. 计算边界

### 2.1 输入

一次计算段接收：

- 当前执行点的实时 `MoodState`；
- 执行点之后的最终 `SimulationLayout`；
- 本次模拟冻结的 `CatalogSnapshot`；
- 规则版本、班次上下文和十进制时长；
- 已按顺序结算的事件结果。

布局变化和心情变化是两个独立维度：布局在每个执行点按 [`入宿逻辑.md`](入宿逻辑.md) 重建，心情从到达该执行点的实时值连续继承。

### 2.2 输出

计算输出必须包含：

- 每名干员的 `consume`、`recover`、`net` 账本；
- 下一节点的心情值，钳位在项目协议规定的 `[0,24]`；
- 产生心情变化的事件及其 `before/after` 节点；
- 可追溯到设施、技能子句、条件和规则版本的贡献明细；
- 无法计算时的稳定错误或警告，不得静默使用猜测值。

## 3. 十进制数值语义

### 3.1 表示

- 协议、事件和结果 DTO 中的数值使用十进制字符串；不得使用二进制浮点字符串作为真值。
- domain 内部使用明确精度的定点/十进制实现；精度、舍入模式和溢出行为必须作为规则版本的一部分登记。
- 心情上限和边界按照协议定义为 `[0,24]`；边界钳位发生在每次积分结果和显式心情事件之后。

### 3.2 积分公式

本项目账本约定：

```text
net = consume - recover
mood_after = clamp(mood_before - net * elapsedHours, 0, 24)
```

其中 `consume` 和 `recover` 为同一时间单位下的非负贡献；正 `net` 表示心情下降，负 `net` 表示心情恢复。若上游机制使用非线性、分段或离散事件，必须以独立模板/策略表达，不得偷偷改写通用积分器。

**待核实项**：具体游戏单位、基础消耗/恢复值、显示精度、内部取整时点和上游特殊曲线。没有上游依据前，只能使用测试专用的符号值，不能添加生产目录数值。

## 4. 贡献账本

### 4.1 贡献来源

贡献按以下来源分组，顺序固定且可解释：

1. 设施基础消耗或宿舍恢复；
2. 设施计数和房间上下文；
3. 满足条件的技能子句；
4. 规则版本允许的全局修正；
5. 进入/离开/换心情等离散事件（不混入持续速率）。

设施字段和作用域见 [`设施信息.md`](设施信息.md)，技能目录结构见 [`技能分类.md`](技能分类.md)。本节定义的是账本顺序，不替代上游数据中的具体效果。

### 4.2 账本项

每个贡献项至少记录：

```text
sourceKind: facility | skill-clause | global-rule | event
sourceId: stable ID
targetOperatorId: stable ID
direction: consume | recover | event | modifier
amount: decimal string, when applicable
conditionResult: true | false | not-applicable
ruleVersion / catalogVersion
```

条件不成立的子句不进入有效账本，但在解释模式下可以记录为 `skipped`，并必须说明条件未满足的原因。显示名不能替代 `sourceId`。

## 5. 技能子句结算

### 5.1 数据驱动

技能通过 `operatorId → skillId → clauseId → templateId` 关联。模板负责解释参数，策略负责组合语义；通用流程禁止出现干员名称分支。每个子句必须声明作用域、目标、方向、条件、组合方式和来源。

### 5.2 条件求值

条件只读取冻结快照和当前计算上下文，包括设施类型/等级、房间成员、阵营、练度、心情区间和已结算事件。条件求值必须是纯函数；不得读取 UI 状态、时间墙钟或可变外部缓存。

条件顺序：

```text
解析子句 → 校验引用 → 求值条件 → 生成候选贡献 → 应用组合语义 → 写入账本
```

### 5.3 组合语义

组合方式必须由模板/规则目录声明：求和、取最高、替换、扩散、元修正或互斥。调用方不得自行 `max`、重复累加或按数组顺序猜测优先级。跨技能比较前按 `skillId` 聚合其子句，不能把子句误当成独立技能。

红脸、特殊状态和技能失效条件如果属于游戏事实，必须登记对应上游字段或规则来源；当前没有来源的阈值和失效范围保持待核实。

## 6. 事件与持续速率

进驻事件和持续速率严格分离。执行点按照 [`入宿逻辑.md`](入宿逻辑.md) 的顺序：

```text
重建原始布局 → 继承实时心情
→ 结算已启用进驻/换心情事件
→ 读回事件后的心情
→ 执行闲置入宿
→ 应用同刻手动心情指定
→ 按最终布局与心情重算净速率
→ 积分到下一节点
```

事件产生同刻 `before/after` 节点；事件后的心情参与该段速率，但同刻手动指定发生在闲置入宿之后，不能反向影响本次候选排序。位置变化引起的生产暖机不属于本文的心情计算，不能混入心情速率。

## 7. 领域 Interface 草案

以下是待实现的 deep Module Interface，不代表当前已有源码：

```ts
interface MoodCalculator {
  rate(context: RateContext): RateBreakdown;
  integrate(state: MoodState, rate: RateBreakdown, hours: Decimal): MoodState;
}

interface SkillClauseEvaluator {
  evaluate(clause: SkillClause, context: ClauseContext): ClauseResult;
}

interface EventApplier {
  apply(event: MoodEvent, state: MoodState): AppliedEvent;
}
```

Interface 必须返回不可变结果和结构化错误；不得暴露可变目录对象、JSON DTO 或 UI 类型。黑盒测试穿过这些 seam，验证账本、积分、事件顺序和确定性。

## 8. 待核实清单

在 data 层登记并查证以下项目后，才能从 `待核实` 转为启用：

- 心情上限、红脸阈值及红脸对技能的具体影响；
- 各设施等级的基础消耗、宿舍恢复和容量/作用域；
- 技能原文、数值、精英化与等级解锁条件；
- 阵营成员集合、设施集合和计数口径；
- 事件型技能的触发时点、目标和重复规则；
- 小数精度、取整位置和边界行为。

每项记录上游仓库版本或本地归档的输入 SHA-256、具体文件路径、字段路径、读取日期、解析解释和未覆盖范围。无 `.git` 的本地归档不得伪造 commit；找不到依据时保留错误/待核实状态，不得凭印象补齐。

## 10. 黑盒验收

实现阶段先在 `test/domain` 写黑盒测试，再实现：

1. 十进制积分不受二进制浮点误差影响；
2. 心情和事件边界正确钳位；
3. consume/recover/net 账本可追溯且符号一致；
4. 条件不成立的子句不贡献数值；
5. 组合语义按模板执行而非由调用方猜测；
6. 事件顺序与 `入宿逻辑.md` 一致；
7. 相同输入、目录版本和规则版本产生相同结果；
8. 未知技能、缺失数值和待核实条件不会静默运行。
