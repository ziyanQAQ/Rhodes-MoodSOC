## 0. 一句话概括

> **正本在 `AGENTS.md` §0**（项目根）：本文只留**架构相关**的那部分，不重复它的定位段
> （为谁服务 / 默认口径 / 交付面），只讲"这话落在代码的哪一层"（见 §1 / §6 / §9）。

这是一个 **纯 Python 标准库** 的建模工具，把《明日方舟》基建中的干员 **心情** 抽象为一块
**电池**，用 **BMS-SOC 安时积分法（库仑计数）** 建模，回答两个问题：

> - **single**：输入「干员 + 基建布局 + 目标时段」→ 该干员剩余心情 + 其余干员心情无限时还能工作多久；
> - **base**：输入「基建布局」→ 每个干员的心情 + 该布局"没有一个干员红脸"可维持的最长时长。

### 1.1 数据为什么分成 `data/` 与 `resources/` 两条线

**一句话**：`data/` 放"**要 import 的表**"，`resources/` 放"**要读文件的东西**"。

| | `data/` | `resources/`（仓库根） |
|---|---|---|
| 形态 | `.py`（能 import）与 `.txt`（CSV 表，生成器的输入） | 样例 `.json` / 说明 `.md` / 报告 `.md` / 需求 `.docx` |
| 典型内容 | 技能库 `moods_skills.txt`、台账 `skills_registry.txt`、阵营表、生成物 `skills_data.py` / `operator_names.py` | MAA 排班样例、4 种导入格式的样例、`输出JSON结构说明.md`、`skill_verify_report.md` |
| 谁写 | 生成器（`scripts/generate_*.py`） | 人工放样例；`verify_skills.py --report` 写核对报告 |
| 为什么不合并 | 表是**代码的延伸**（import 即用、可被静态检查）；样例/文档/报告是**项目级资产**，只按路径读 | |

三条规矩：

1. **路径只有一处**：`data/paths.py`。全项目（含 `scripts/`、`tests/`）一律 `from data.paths import X`，
   不再各自拼 `Path(__file__).parent.parent / "resources"`；`tests/test_layers.py` 扫源码，手拼路径就报错。
2. **生成器只写 `data/`**（`skills_data.py` / `operator_names.py` / `factions.txt`）；
   `resources/skill_verify_report.md` 是唯一例外 —— 报告是**给人看的产物**。
3. **领域基元下沉 `data/domain.py`**（`FacilityType` / 容量表 / 心情上下限）：为**断开循环导入**（见 §1.3）。

> 样例与报告**不放 `data/` 里**（曾短暂放过 `data/resources/`，已改回）：`data/` 是 Python 包，测试与打包
> 会整体遍历它，样例还要能被 `.gitignore` / 发布策略单独对待。

### 1.2 为什么需要一个 `store/`（数据管理层）

`mood_soc` 只回答"给定一个布局，谁的心情怎么变"；而"**多班轮换能不能永动**"（周期切成 12h+6h+6h、
每班布局不同、心情跨班连续）与四种排班/蓝图 JSON 的解析、结果序列化都属于**状态与 IO**，于是有了
`store/`（各文件职责见上面那棵树）：`schedule.py` 跑整周期轨迹（**「不在基建」的人（`detached`）是一条
平线**）· `session.py` 管"**当前在算的是哪一套**"（**唯一的重算入口**）· `sources.py` 认出这份 JSON 是
哪种格式、怎么变成班次（含顶层 `detached` 名单）· `layout.py` 把场景 dict 变成 `BaseLayout`（含
`build_detached` 宽松解析）· `serialize.py` 出 JSON（`inf → null`、6 位小数）。

**关键收益**：`Session` 同时被 `ui/` 与 `api/` 使用 ⇒ 界面能调的与程序接口能调的是**同一份语义、
同一条重算路径**（以前状态散在 `ui/app.py` 的实例属性里，两份迟早分叉）。

### 1.3 依赖方向（严格单向，有测试盯着）

```
main.py / tests / scripts
   ↓
ui/（视图）        api/（程序接口）        ← 两者互不 import
   ↓                    ↓
        store/（状态与 IO）
   ↓
mood_soc/（纯计算）
   ↓
data/（数据与领域基元）      ← 只允许依赖 Python 标准库
```

三条硬规矩（`tests/test_layers.py` 静态扫描源码）：

1. `data/` 与 `mood_soc/` **不许** import `store` / `ui` / `api`；
2. `store/` **不许** import `ui` / `api`；`ui/` 与 `api/` **互不** import；
3. `api/` / `store/` / `data/` 的**代码**里不许出现 `tkinter`（程序接口要能在无图形环境跑）。

> **唯一的例外**：`mood_soc/__init__.py` 里 `build_base_layout` 从 `store.layout` 取（历史公开 API
> `from mood_soc import build_base_layout` 不破）—— 只是**顶层 re-export**，不构成模块级环：
> `store.layout` 只依赖 `mood_soc.battery/config/models`。

**为什么必须这样**：`data/conditions.py` / `data/skill_model.py` 要用 `FacilityType` / `MOOD_MAX`，
而 `mood_soc/config.py` 在计算包里 —— 数据包一旦 import 它就会连锁
`rules → skills → data.skills_data → data.conditions`，形成双向环（实测报错：
`cannot import name '_cond_alone_in_facility' from partially initialized module`）；
下沉 `data/domain.py` 后链条单向，环消失（见 `06-设计史.md` P6）。

改代码时的经验法则：

| 要改什么 | 只动 |
|---|---|
| 数值 / 阈值 / 公式 | `mood_soc/config.py` |
| 设施 / 容量 / 心情上下限 | `data/domain.py` |
| 加技能 | `data/moods_skills.txt` 等表 → 重跑生成器（见 §6 管道） |
| 计算逻辑 / 数学积分 | `mood_soc/rules.py` / `mood_soc/battery.py` |
| 输入格式 / 输出文案 | `store/sources.py`、`store/layout.py` / `mood_soc/report.py` |
| 可调项 / 会话语义 | `store/session.py`（界面与 API 同时生效） |
| 加程序接口能力 | `api/ops.py` 加一个 op（见 `08-程序接口.md` §8） |
| 图形界面 | 只动 `ui/`（见 `07-图形界面.md`） |

### 1.4 包名对照（老名字 → 新名字）

P6 重构改过几个模块的**位置**（少数连名字一起改），新代码请用新名字；
老名字仍然 import 得到（兼容转发壳），但**别往里加逻辑**：

| 老 | 新 | 为什么 |

## 6. 数据流（一次完整测算怎么走）

```
用户输入（dict/JSON）→ store.layout.build_base_layout(data)   # 解析层 → Operator/Facility/BaseLayout
  场景来源：main.py 内置 DEMO_SCENARIO 或 load_scenario(文件)
  ├─ single：rules.evaluate(world, name, hours) → MoodResult        # base：rules.evaluate_base(...) → BaseResult
  └─ mood_soc.battery.ampere_hour_integration   # 数学层：钳位积分
       └─ store.serialize.mood_result_to_dict() → dump_json()   # 输出层：JSON dict → results/
（--trace，single 时）simulator.simulate(...)：每步 rules.compute_net_rate 重算 → 积分推进
```

技能数据管道（与测算主流程分离）：`Kengxxiao/ArknightsGameData` 的 `building_data.json`（上游，非本仓库）
→ `scripts/classify_skills.py --agd <仓库>`（挂模板 + 生成 755 行覆盖台账 + 零遗漏校验）→
`data/moods_skills.txt`（clause 级，+`template_id`/`params`）/ `data/skills_registry.txt`（buff 级台账）→
`scripts/generate_skills_data.py` → `data/skills_data.py`（`SKILLS` / `DEFAULT_OPERATORS` / `SKILL_EQUIPS` /
`TRAITS` / `OPERATOR_FACTIONS` / `SPREAD_SKILL_IDS` / `VARIABLE_PRODUCERS`）→ `mood_soc/skills.py`
re-export → `rules.py` 使用。

> ⚠️ **生成物只 import 数据包**（`data/skill_model.py` / `data/conditions.py` / `data/domain.py` 的
> `Skill`/`SkillEquip`/`SkillKind`、条件函数与 `FacilityType`），**绝不 import `mood_soc`** —— 那会连锁
> `rules`/`models`，让"生成器无法重新生成自己"。细节见 `data/__init__.py`、`05-数据来源.md` 与
> `scripts/generate_skills_data.py` 的 `_load_templates_module()`。

程序接口的数据流（Rust ↔ Python）：`api.server` ←NDJSON（一行一请求 / 一行一响应）→ `api.ops.<op>` →
`store.Session` → `store.schedule`（轨迹）/ `mood_soc`（速率）；完整数据流图、重算时序与界面写路径见
`09-架构总览.md` 末尾的四张图。

**解析解 vs 数值解**：

| | 谁 | 口径 |
|---|---|---|
| **解析解** | `remaining_mood_after` / `remaining_work_hours` / `evaluate` / `evaluate_base` | 假设速率恒定（single 的"其余干员心情无限"、base 的"到第一个红脸前无人红脸"）：快、结果确定 |
| **数值解** | `simulator.simulate` | 逐步推进、每步**重算所有干员**速率 ⇒ 能表现"中途红脸 → 技能失效 → 速率改变"的联动；**深拷贝** world，返回 `[(时间, 心情), ...]` 轨迹 |

### 9.5 顶层 API 详情（签名 / 返回 / 说明）

> 从根 `README.md` 搬来的**完整表**（README 只留最常用的几个 + 指针，细节归这里）。
> 全部 `from mood_soc import ...`。

| 函数 / 常量 | 签名 | 返回 | 说明 |
|---|---|---|---|
| `build_base_layout` | `(data, validate=False)` | `BaseLayout` | 场景 dict → 布局；`validate=True` 做容量/房间数自检并抛 `ValueError` |
| `evaluate` | `(world, name, period_hours=0)` | `MoodResult` | single 模式：目标干员时段后的状态 |
| `evaluate_base` | `(world, period_hours=0)` | `BaseResult` | base 模式：全体干员 + 布局可维持时长 |
| `compute_net_rate` | `(world, name, variables=None)` | `Decimal` | 某干员净速率（消耗 − 回复，>0 下降）；`variables` 是共享的变量快照（见 `net_rates`） |
| `net_rates` | `(world, names=None)` | `dict[str, Decimal]` | **一次算一批人**（共享一份变量快照，缺省全基建）—— 7 周期重算快 1.32× |
| `remaining_mood_after` | `(world, name, hours, variables=None)` | `Decimal` | 时段后剩余心情（钳位 [0,24]） |
| `remaining_work_hours` | `(world, name)` | `Decimal` | 从当前心情起算还能工作多久（net≤0 为 Infinity） |
| `time_to_mood` | `(world, name, target_mood)` | `Decimal` | 达到指定心情所需时间（工作=下降、宿舍=上升） |
| `work_rest_ratio` | `(consumption, recovery)` | `WorkRestRatio` | 工休比指标（字段见 9.6） |
| `simulate` | `(world, name, duration, step=0.05)` | `list[(时间,心情)]` | 时间步进模拟轨迹（深拷贝 world，处理红脸联动） |
| `mood_ledger` | `(world, name, variables=None)` | `MoodLedger` | **心情流水账**（唯一计算路径）：逐条来源 + 轴 F 叠加规则，`.explain()` 可读 |
| `consume_ledger` / `recovery_ledger` | `(world, op, facility, variables=None)` | `MoodLedger` | 消耗侧 / 回复侧流水账 |
| `apply_idle_to_dorm` | `(world, *, enabled=None, idle=None, only=None, swap_with=None, scope=None, trace=None)` | `list[Contribution]` | **自动入宿**（三层解耦：锁定入宿 > 自动入宿 > 导入布局）：候选＝该班**原始布局**里没出现在任何设施 + 心情 < 24 + 非黑名单（心情取**执行点实时值**），按 (心情↑, 名字↑)；两相＝**竖向反序填空床**（2026-10 口径反转，旧的是竖向正序） → 全满则取**心情最低**的候选，换出"锁定区外、心情 **≥ 她**、心情**最大**"的住户（并列取竖向反序最靠前）；**没有班次数参数**（单班也执行）；`trace` 是出参、`swap_with` **已作废**；⚠️ **就地改布局**，**三层唯一的裁决点是 `rules._seat_verdict`**。口径见 `03-特殊机制.md` 第 30 条 |
| `ManualLedger` / `mark_manual` / `read_manual` / `clear_manual` / `set_seat` / `remove_occupant` / `facility_occupancy` | `models.py` | 台账与占位原语 | **手动编辑逻辑**的数据面：`{slots, names}` 挂在设施上（随班次走、进 JSON、随 `deepcopy` 进每个执行点）；`set_seat` 是"空洞"的唯一写入口（位次不左移）；写入点**只有** `store/session.py`，读取点**只有** `rules._seat_verdict` 与自动入宿内部 |
| `execution_offsets` / `execution_points` | `(shift_hours)` / `(schedule, cycles=1)` | `list[Decimal]` / `list[(起, 止, 班次下标, 周期序号, 班内偏移)]` | **换班执行点**（`store/schedule.py`）：班初 + 长班（>12h）班内每个严格小于班末的 12h 整数倍（`INTERNAL_SWAP_HOURS = 12`）；段循环、增量指纹、逐次表都读它 |
| `apply_entry_events` | `(world, swap_with=None, enabled=None, scope=None, restore_back=None, when=None, detached_moods=None)` | `list[Contribution]` | **进驻事件**（M15a 换心情）；触发者＝**本班任一设施 ∨ 本班未排班 ∨ 显式「不在基建」名单**（`detached_moods`＝本班不在场那些人的实时心情表，**就地读写**；不传＝不当她在场）；`when`（`immediate`/`wait`/`full`）只管"她没满时等不等"——**三档都要求她满 24**；找不到对象**一律**记一条 `entry_swap_skipped`；⚠️ **就地改** `world` |
| `entry_event_holders` | `(world)` | `list[(干员, 房间)]` | 谁会触发进驻事件（界面提示用） |

### 9.6 结果数据模型字段

**MoodResult**（single）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `operator_name` | str | 目标干员名 |
| `facility_label` | str | 所在设施中文名 |
| `initial_mood` | Decimal | 初始心情 |
| `net_rate` | Decimal | 净速率（>0 下降 / <0 上升） |
| `remaining_mood` | Decimal | 时段结束后的心情 |
| `sustain_hours` | Decimal | 还能维持/恢复多久（工作=到红脸、宿舍=恢复满；不变为 Infinity） |
| `state` | str | 中文状态描述 |
| `ledger` | MoodLedger | 该干员的完整流水账 |

**BaseResult**（base）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `operators` | list[OperatorResult] | 每个干员的结果 |
| `layout_sustain_hours` | Decimal | 布局可维持时长（无人红脸；无人会红脸为 Infinity） |
| `bottleneck` | str / None | 最先红脸的干员名 |

**OperatorResult**（base 中单个干员）：

| 字段 | 类型 | 说明 |
|---|---|---|
| `name` | str | 干员名 |
| `facility_label` | str | 所在设施中文名 |
| `mood` | Decimal | 心情值（当前或时段推进后） |
| `sustain_hours` | Decimal | 工作=布局可维持时长；宿舍=min(恢复满时间, 布局可维持时长) |
| `mood_at_end` | Decimal / None | 到达 `layout_sustain_hours` 时的心情 |

**WorkRestRatio**：

| 字段 | 说明 |
|---|---|
| `consumption` / `recovery` | 工作消耗 x / 休息回复 y |
| `work_time_full` | 满心情可连续工作 24/x |
| `recover_time_full` | 从零回满 24/y |
| `ratio` | 最大工休比 y/x |
| `work_share` | 最大工作时长占比 y/(x+y) |
| `max_work_per_day` | 24 小时内最长可工作 24y/(x+y) |

**布局 / 干员 / 设施**（构造签名）：

- `Operator(name, mood=MOOD_MAX, skill_ids=[], trait=None, factions=None, elite=2, level=1)`
  —— 干员（`elite`/`level` 控制技能解锁）
- `Facility(ftype, level=1, operators=[], atmosphere=None, name="", deputies=[], slots=None, enabled=True)`
  —— 设施房间
- `BaseLayout(facilities=[])` —— 方法：`facility_of` / `get_operator` / `all_operators` /
  `all_deputies` / `of_type` / `count_of_type` / `count_in` / `all_dormitories` / `facilities_in` /
  `operators_in` / `working_operators` / `base_operators` / `control_center` / `validate`
  （`get_facility` 只取第一个，已废弃）
