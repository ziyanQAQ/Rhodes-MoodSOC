## 0. 一句话概括

这是一个 **纯 Python 标准库** 的建模工具，把《明日方舟》基建中的干员 **心情** 抽象为一块
**电池**，用 **BMS-SOC 安时积分法（库仑计数 / Ampere-Hour Integration）** 做数学建模，回答两个问题：

> - **single**：输入「干员 + 基建布局 + 目标时段」→ 该干员剩余心情 + 其余干员心情无限时还能工作多久；
> - **base**：输入「基建布局」→ 每个干员的心情 + 该布局"没有一个干员红脸"可维持的最长时长。

规则来源：
- `resources/心情消耗回复和工休时间.docx`（需求文档，心情消耗/回复/工休的**计算规则**；
  ⚠️ 该 docx **不入库**（2026-09 从仓库撤下、只留在提交历史里），所以本机可能没有它，
  规则以 `documents/02-数值规则.md` 与代码为准）；
- `resources/moods_skills.txt` + `resources/operators.txt`（**真实技能库与干员↔技能映射**，
  含精英化解锁等级、value 千分值、作用 family **与分类模板 `template_id`/`params`**，由
  `scripts/generate_skills_data.py` 一键生成 `mood_soc/skills_data.py` 数据表）；
- `documents/05-技能分类大纲.md`（**技能分类大纲：六轴 + 模板字典**，新增技能先查这里）；
- `resources/skills_registry.txt`（上游 755 条 buff 的**覆盖台账**，防漏用）；
- `resources/factions.txt` + `factions_supplement.txt`（**干员↔阵营/标签表**，由
  `scripts/generate_factions.py` 从上游 `cc.g.*` / `cc.tag.*` 生成，28 组；人工补充仅异格者）；
- `resources/variable_producers.txt`（**变量产出者表**：人间烟火/热情值/无声共鸣 的产出端，
  逐条注明上游 buff 出处；见 `mood_soc/variables.py`）；
- `documents/07-设计史.md`（**架构诊断与重构设计**：运行时派发/布局模型/记录层的改造蓝图）。

> 技能数值以两份 txt 为**权威来源**（docx 中的技能示例值已过时，不要作为技能数值依据）。

## 1. 目录结构与分层（高内聚、低耦合）

**一句话分层**（依赖严格单向向下，箭头 = 只能往下 import）：

```
        ui/   ← 只做 tkinter 画与点（视图；状态在 store.Session 上）
         │
        api/  ← 程序接口：JSON 进 / JSON 出（供 Rust 调用，不依赖 tkinter）
         │
       store/ ← 数据管理层：排班模型 / 整周期轨迹 / 输入解析 / 结果序列化 / **会话状态**
         │
      mood_soc/ ← 只回答"给定一个布局，谁的心情怎么变"（纯计算，不读文件、不管 IO）
         │
        data/  ← 干员与技能数据 + 领域基元 + 数据路径的唯一出口
```

### 1.1 数据为什么分成 `data/` 与 `resources/` 两条线

**一句话**：`data/` 放"**要 import 的表**"，`resources/` 放"**要读文件的东西**"。

| | `data/` | `resources/`（仓库根） |
|---|---|---|
| 形态 | `.py`（能 import）与 `.txt`（CSV 表，生成器的输入） | 样例 `.json` / 说明 `.md` / 报告 `.md` / 需求 `.docx` |
| 典型内容 | 技能库 `moods_skills.txt`、台账 `skills_registry.txt`、阵营表、生成物 `skills_data.py` / `operator_names.py` | MAA 排班样例、4 种导入格式的样例、`输出JSON结构说明.md`、`skill_verify_report.md` |
| 谁写 | 生成器（`scripts/generate_*.py`） | 人工放样例；`verify_skills.py --report` 写核对报告 |
| 为什么不合并 | 表是**代码的延伸**（import 即用、可被静态检查）；样例/文档/报告是**项目级资产**，只按路径读，不该混进 Python 包里 | |

三条规矩：

1. **路径只有一处**：`data/paths.py`。全项目（含 `scripts/`、`tests/`）一律
   `from data.paths import X`，不再各自拼 `Path(__file__).parent.parent / "resources"`；
   `tests/test_layers.py` 会扫描源码、发现手拼路径就报错。
2. **生成器只写 `data/`**（`skills_data.py` / `operator_names.py` / `factions.txt`）；
   `resources/skill_verify_report.md` 是唯一例外 —— 报告是**给人看的产物**，不是代码数据。
3. **领域基元下沉 `data/domain.py`**：`FacilityType` / 容量表 / 心情上下限。
   这是为了**断开循环导入**（见 §1.3），顺带也符合"游戏给的事实归数据"。

> 样例与报告**不放 `data/` 里**（曾短暂放过 `data/resources/`，已改回）：`data/` 是
> Python 包，测试与打包时会被整体遍历/收集，把样例 JSON 与报告混进去只会让"数据表"
> 这个概念变糊；而样例是给人看的、也要能被 `.gitignore`/发布策略单独对待。

### 1.2 为什么需要一个 `store/`（数据管理层）

`mood_soc` 只回答"给定一个布局，谁的心情怎么变"；而"**多班轮换能不能永动**"
（周期切成 12h+6h+6h、每班布局不同、心情跨班连续）是另一个层次的问题，
再加上四种排班/蓝图 JSON 的解析、结果序列化，这些都属于**状态与 IO**：

| 模块 | 回答的问题 |
|---|---|
| `schedule.py` | 这个排班跑一个（或 N 个）周期，每个人的心情曲线长什么样；**「不在基建」的人（`detached`）是一条平线** |
| `session.py` | **当前在算的是哪一套**：排班 + 全部可调项 + 唯一的重算入口 |
| `sources.py` | 手上这份 JSON 是哪种格式、怎么变成班次（含顶层 `detached` 名单） |
| `layout.py` | 一份场景 dict 怎么变成 `BaseLayout`（含 `build_detached` 宽松解析） |
| `serialize.py` | 结果怎么变成 JSON（`inf → null`、6 位小数） |

**关键收益**：`Session` 同时被 `ui/`（tkinter 视图）与 `api/`（程序接口）使用，
所以"界面上能调的一切"与"程序接口能调的一切"是**同一份语义、同一条重算路径**。
以前这些状态散在 `ui/app.py` 的实例属性里，程序接口只能重写一遍 —— 两份迟早分叉。

### 1.3 依赖方向（严格单向，有测试盯着）

```
main.py / tests / scripts
   ↓
ui/（视图）        api/（程序接口）        ← 两者互不 import
   ↓                    ↓
        store/（状态与 IO）
   ↓
mood_soc/（纯计算）
   ↓
data/（数据与领域基元）      ← 只允许依赖 Python 标准库
```

三条硬规矩（`tests/test_layers.py` 静态扫描源码）：

1. `data/` 与 `mood_soc/` **不许** import `store` / `ui` / `api`；
2. `store/` **不许** import `ui` / `api`；`ui/` 与 `api/` **互不** import；
3. `api/` / `store/` / `data/` 的**代码**里不许出现 `tkinter`（程序接口要能在无图形环境跑）。

> **唯一的例外**：`mood_soc/__init__.py` 里 `build_base_layout` 从 `store.layout` 取
> （为了 `from mood_soc import build_base_layout` 这个历史公开 API 不破）。
> 它是**顶层的 re-export**，不构成模块级环：`store.layout` 本身只依赖 `mood_soc.battery/config/models`。

**为什么必须这样**：`data/conditions.py` 与 `data/skill_model.py` 要用 `FacilityType` / `MOOD_MAX`，
而 `mood_soc/config.py` 属于计算包 —— 一旦数据包 import 它，就会连锁
`mood_soc/__init__ → rules → skills → data.skills_data → data.conditions`，
形成"数据包要 import 计算包，计算包又要 import 数据包"的环
（实测报错：`cannot import name '_cond_alone_in_facility' from partially initialized module`）。
把领域基元下沉到 `data/domain.py` 之后链条单向，环就消失了。

改代码时的经验法则：
- **改数值/阈值/公式** → 只动 `mood_soc/config.py`；**改设施/容量/心情上下限** → 只动 `data/domain.py`；
- **加技能** → 改 `data/moods_skills.txt` 等表 → 重跑生成器（见 §6 管道）；

## 6. 数据流（一次完整测算怎么走）

```
用户输入（dict/JSON）
  └─ scenario.build_base_layout(data)          # 解析层：字符串/对象 → Operator/Facility/BaseLayout
       └─ 可选 main.py 内置 DEMO_SCENARIO 或 load_scenario(文件)
            ├─ single：rules.evaluate(world, name, hours)   → MoodResult
            └─ base：  rules.evaluate_base(world, hours)    → BaseResult
                 └─ battery.ampere_hour_integration         # 数学层：钳位积分
                      └─ output.mood/base_result_to_dict()  # 输出层：JSON dict
                           └─ output.dump_json() 写文件到 results/（CLI 同时打印到 stdout）
            （--trace，single 时）simulator.simulate(world, name, hours, step)
                          └─ 每步 rules.compute_net_rate 重算 → ampere_hour_integration 推进
```

技能数据管道（与测算主流程分离）：
```
Kengxxiao/ArknightsGameData  building_data.json（上游，非本仓库）
  └─ scripts/classify_skills.py --agd <仓库>     # 挂模板 + 生成覆盖台账 + 零遗漏校验
       ├─ data/moods_skills.txt      （clause 级，+template_id/params）
       └─ data/skills_registry.txt   （buff 级 755 行台账）
            └─ scripts/generate_skills_data.py
                 └─ data/skills_data.py（SKILLS / DEFAULT_OPERATORS / SKILL_EQUIPS /
                          TRAITS / OPERATOR_FACTIONS / SPREAD_SKILL_IDS / VARIABLE_PRODUCERS）
                      └─ mood_soc/skills.py re-export → rules.py 使用
```

> **生成物只 import 数据包**：`data/skills_data.py` 从 `data/skill_model.py` 拿
> `Skill`/`SkillEquip`/`SkillKind`、从 `data/conditions.py` 拿条件函数、从 `data/domain.py`
> 拿 `FacilityType`。**绝不 import `mood_soc`**（那会连锁 `rules`/`models`，
> 让"生成器无法重新生成自己"）。生成器侧的注意事项见 `data/__init__.py` 与
> `scripts/generate_skills_data.py` 的 `_load_templates_module()` 注释。

程序接口的数据流（Rust ↔ Python）：

```
Rust ──NDJSON（一行一请求）──► api.server ──► api.ops.<op> ──► store.Session
                                   │                              │
                         api.protocol（请求/响应）        store.schedule（轨迹）/ mood_soc（速率）
                                   ◄──── 一行一响应 ─────────────┘
```

**解析解 vs 数值解的区别（重要）**：
- `remaining_mood_after` / `remaining_work_hours` / `evaluate` / `evaluate_base` 是**解析解**：
  假设速率恒定（single 的"其余干员心情无限"、base 的"到第一个红脸前无人红脸"）。
  速度快、结果确定。
- `simulator.simulate` 是**数值解**：逐步推进，每步**重新计算所有干员**速率，
  因此能正确表现"有人中途红脸 → 他/她的技能失效 → 速率随之改变"的联动效果。
  它**深拷贝** world，不修改调用方对象；返回 `[(时间, 心情), ...]` 轨迹。

